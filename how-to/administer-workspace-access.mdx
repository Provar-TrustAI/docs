Everything about who can get into your workspace — and what they can reach once they're in — is administered from one surface: **Workspace settings**. This how-to walks the admin jobs end to end:

- Invite people to the workspace and manage the invite lifecycle (pending, expired, resend, revoke)
- Change a member's **workspace role**, inside the guardrails that keep a workspace from locking itself out
- Group people into **teams** so project access can be granted once, to the whole team
- Grant **per-project access** (Viewer, Editor or Admin), directly or via a team, and read where each person's access comes from
- **Transfer a project's ownership** when the person who created it moves on
- Trace any access change in the in-context **access history**
- Read your workspace's **credit** usage and the **connected orgs** the whole workspace shares

This is a hands-on admin surface, so you work in the UI directly.

## Prerequisites

- A **Trust AI account** in the workspace you want to administer
- A workspace role that can manage members, teams, and access — **Owner** or **Admin** (the app describes the Admin role as "Manage members, teams & access")

Both halves of that gate are real. A member or guest never sees the **Workspace Settings** row in the sidebar footer, and if they reach the surface by a saved link they get a card reading "Workspace management is admin-only" instead of the tabs. The server enforces it independently: an admin-only read like the members roster is refused before the identity provider is even called, so hiding the door is a convenience, not the control.

## Open Workspace settings

Click **Workspace Settings** in the sidebar footer (it sits above your user chip, outside any one project). The page that opens is titled **Workspace settings** — release notes sometimes call this surface the *Access Center* — and it has six tabs:

| Tab | What it holds |
|---|---|
| **Members** | People in this workspace, their roles, and the teams they belong to. |
| **Teams** | Groups that bundle project access so you grant it once, not per person. |
| **Project access** | Who can open each project — directly or inherited through a team. |
| **Credits** | Your workspace credit pool, how much you have used this billing month, and where it went. |
| **Connected orgs** | The Salesforce orgs your workspace is connected to, and the projects that use each one. |
| **General** | Settings that apply across every project in this workspace. |

Each tab is a stable, bookmarkable route, so a refresh or a shared link lands on the right tab. The page opens on **Members** by default.

<Note>
  A June 2026 release note describes this surface consolidating "six tabs into four". That was true of that release; **Credits** and **Connected orgs** landed afterwards. Six is the current count.

  The fifth tab is deliberately *not* called "Connections" — that name belongs to a project's own **Settings → Connections** tab, which lists the agents that one project tests. One word cannot name both.
</Note>

## Two role vocabularies, one rule

The surface uses two distinct vocabularies — keep them apart:

- **Workspace roles** describe someone's standing in the workspace: **Owner**, **Admin**, **Member**, **Guest**. Ownership is never reassignable from this surface; Admins manage members, teams, and access; Members get standard access to the projects they're granted; Guests are external and project-scoped, with no teams.
- **Project access tiers** describe what a grant on one project confers: **Viewer** (read), **Editor** (read and change) or **Admin** (change, plus share and archive). All three are grantable from the dialog. A fourth tier, **Owner**, sits above them — conferred when the project is created, never granted, and moved only by **Transfer ownership**.

One rule ties them together: **project content is always gated by a project grant, and no workspace role is an exception — Owner included**. A workspace Admin who has no grant on a project doesn't see its content, and neither does the workspace Owner; the roles reference renders those cells as "Needs grant" rather than a blanket allow.

<Warning>
  The member sheet renders the Owner's role as a read-only line, "Owner — full access to every project in the workspace." Read that as administrative standing, not as a content key. At this release the content check resolves purely from the project grant, so a workspace Owner with no grant on a project is denied its contents exactly like anyone else.
</Warning>

Wherever you pick a role — the invite dialog and the member sheet — a **What can each role do?** link opens a read-only reference drawer summarizing what each workspace role is allowed to do, across every project. You never have to leave the flow to check.

## What a grant tier actually gates

| You want to | You need |
|---|---|
| Open the project and read its contents — requirements, scenarios, sessions, evaluators, evaluation runs | **Viewer** |
| Create, edit **and delete** the project's contents — personas, evaluators, scenarios, requirements — start an evaluation run, and edit the project's own name and description | **Editor** |
| Grant or revoke other people's access to the project | **Admin** on the project, or workspace **Owner** or **Admin** |
| Archive or restore the project, or delete an evaluation run | **Admin** or **Owner** on the project |
| Transfer the project's ownership, or delete the project | The project's **Owner**, or workspace **Owner** or **Admin** |

Three consequences worth knowing before you promise someone access:

- **Editors own the whole authoring loop.** An Editor creates, edits *and deletes* personas, evaluators, scenarios and requirements, and can fix a typo in the project's own name. Naming a project is authored content, not a lifecycle decision — it destroys nothing and anyone who can do it can undo it.
- **Project content is gated by the grant alone.** A workspace Owner or Admin *without* a grant on a project is denied its content exactly like anyone else. Workspace standing confers no reading.
- **Two acts are the deliberate exception.** Deleting a project and transferring its ownership both admit a workspace Owner or Admin with no grant on it — the offboarding backstop for a project whose owner has left. Neither lets them read the project.

<Note>
  Every permission refusal names your role, the action, and the remedy, so nobody has to guess which of the tiers above they are short of. The template reads **"Your Viewer role doesn't have permission to delete personas. Contact a project admin to change your role."** Two refusals end differently on purpose, because no project admin can help: project deletion and ownership transfer both close with **"Only the project's owner, or a workspace admin, can …"**. Someone with no grant at all hears **"You don't have access to this project. Contact a workspace admin to request access."**
</Note>

## Invite members

<Steps>
  <Step title="Send the invitation">
    On the **Members** tab, click **Invite**. The **Invite to workspace** dialog takes an **Email address** and a **Workspace role** — a card each for **Admin** ("Manage members, teams & access."), **Member** ("Standard access to granted projects.", the default), and **Guest** ("External; project-scoped, no teams."). Owner is never offered: ownership is conferred, not assigned. Check **What can each role do?** if you're unsure, then click **Send invite**.

    **You should see:** the dialog close and the invitee appear as a row in the roster with an **Invited** pill — the header count reads like "4 members · 1 pending".
  </Step>

  <Step title="Track the invite lifecycle">
    The person gets an email invitation; until they accept, their row carries an **Invited** pill (or **Expired** once the invitation lapses) and no join date. The row's menu offers the lifecycle actions:

    - **Resend email** on a pending invitation (or **Resend invitation** on an expired one)
    - **Revoke invitation** to withdraw it — the row drops out of the roster

    Once the invitee accepts, the row becomes a full member with a role badge, team chips, and a **Joined** date.
  </Step>
</Steps>

<Note>
  The Members roster is read live from your workspace's SSO identity provider — the same identity your organization signs you in with. If your directory changes, the roster reflects it; there is no separate member list to sync. Which provider backs your workspace is a deployment choice, and nothing in this flow changes with it. See [Multi-tenancy](/concepts/multi-tenancy) for how identity maps onto your tenant.
</Note>

## Change a member's workspace role

Click a member's row to open their detail sheet: identity at the top, then a **Workspace role** picker with the same Admin / Member / Guest cards, their **Teams**, and a remove action in the footer.

Three guardrails protect the workspace while you're in here — each disables the option and explains itself inline instead of failing after the fact:

- **The Owner's role is not a picker.** It renders as a read-only line — "Owner — full access to every project in the workspace." — and ownership isn't reassignable from this sheet.
- **You can't demote yourself out of admin.** An admin stripping their own access would be a self-lockout — "You can't remove your own admin access." Another admin has to do it.
- **The last administrator can't be demoted.** "Promote another admin before demoting the last one." — otherwise no one could manage the workspace.

Any other role change is a single click on the target card; the row's role badge repaints when it lands.

## Remove a member

The member sheet's footer holds the remove action. The same two hard guards apply: the **Owner can never be removed**, and the **last remaining administrator can never be removed** ("Promote another admin before removing the last one."). For anyone else, removal takes them out of the workspace and **sweeps their direct project grants with it** in the same operation — no orphaned access is left behind, and if the directory removal fails the swept grants roll back with it. Access they had only through a team ends with their team membership.

## Build teams

Teams exist so you can grant project access once instead of per person.

<Steps>
  <Step title="Create the team">
    On the **Teams** tab, click **New team**. The **Create a team** dialog takes a name (for example, "Risk & Compliance") — click **Create team**. The dialog tells you what comes next: "Add members and grant project access once you've created it."

    **You should see:** the team appear in the list with a member count.
  </Step>

  <Step title="Add people to it">
    Click the team's row to open its sheet. Under **Members**, click **Add member…** — it opens a picker that autocompletes against the workspace roster, with a **Search people…** field. Pick someone and the popover closes; they're added.

    You are not asked to transcribe an address. If you type a full, well-formed email that matches nobody on the list, the picker offers an **Add \<that address\>** row so you can still add it verbatim — the escape hatch for someone the roster doesn't list yet. The team name is editable in place from the sheet's header.
  </Step>

  <Step title="Know what deleting a team does">
    **Delete team** sits in the sheet's footer. A team that grants no project access is deleted straight away. If the team still grants project access, the app stops you with an explicit confirmation — "This team still grants project access. Deleting it revokes those shared grants — anyone who reached those projects only through this team loses access immediately. Members stay in the workspace. This can't be undone."
  </Step>
</Steps>

## Grant access to a project

<Steps>
  <Step title="Open the project's access panel">
    On the **Project access** tab, click a project's row. The sheet that opens is headed by the **project's own name**, with its description underneath (or, for a project with no description, the line "Who can reach this project — and how."). It holds two sections, and they behave differently when empty: **Teams with access** is drawn only when a team actually holds a grant, while **People with access** is always drawn — with no direct grants it reads "No people have a direct grant yet."

    The same access surface is also mounted inside each project, at Project Settings → **Members**, where it is headed **Project access** — "Who can reach this project — and whether it's a direct grant or inherited from a team". Grants made in either place are the same grants.
  </Step>

  <Step title="Add a grant">
    Click **Add access**. The **Grant access to [project]** dialog has a **Role** toggle — **Viewer**, **Editor** or **Admin**, with Editor preselected — and a **People** / **Teams** tab pair listing the candidates, filtered by one search field that spans both tabs. Click a person to grant them the selected role directly, or a team to grant everyone in it at once. A status pill reads back what you're about to hand out ("Granting as Editor"), and **Done** closes the dialog.

    Granting **Admin** needs no extra permission of its own: anyone trusted to share a project may share it at the tier they hold themselves. What a project Admin cannot do is hand the project away — that is the separate step below.

    Candidates are filtered by whether they already hold a grant **at all**, not by the tier you have selected: someone with any direct grant on the project is absent from **People** even when you switch the toggle to another tier. To change an existing grant, use the inline role control on its row rather than looking for the person here.

    <Frame caption="Editor is preselected of the three tiers, and the candidate list is shorter than the roster: Marcus and Priya are missing from it because they already hold a grant, visible in the panel behind.">
      <img src="/images/workspace-grant-access-dialog.png" alt="The Grant access to Acme refunds CSAT dialog: a Role toggle offering Viewer, Editor and Admin with Editor selected, a People / Teams tab pair, a search field, and two candidate rows each with an add button. Behind it the project's access panel lists the Risk & Compliance team under Teams with access and three people under People with access — the owner's row showing a static Owner badge, the other two an inline Viewer / Editor / Admin picker — above a Transfer ownership button and an Add access button." />
    </Frame>

    **You should see:** the new grant appear in the panel's **People with access** or **Teams with access** section with its role badge.
  </Step>

  <Step title="Read the provenance, adjust, or revoke">
    Every grant row tells you *how* the access exists: a **Direct** pill for a per-person grant, a **via [team]** chip when the access is inherited through a team. A person can carry both at once.

    Every grant row's tier is changeable inline between **Viewer**, **Editor** and **Admin**, and each row has a revoke action — with one exception. The project owner's own access is conferred by ownership rather than granted, so its row shows a static badge reading **Owner**, with no tier picker and no revoke. Trying to re-tier or revoke it through the API is refused in those terms: *"The project owner's access can't be changed or removed. Transfer ownership first — the previous owner becomes an admin."*
  </Step>

  <Step title="Hand the project on with Transfer ownership">
    A project has exactly one owner, so making someone else the owner takes it from whoever holds it. That is why it is a transfer and not a grant: **Transfer ownership** sits in the access panel's footer, beside **Add access**.

    The button appears only for someone the server would authorize — the current owner, or a workspace Owner or Admin re-homing a project whose owner has left — and it is hidden entirely when there is nobody else on the project to hand it to.

    The confirm dialog is titled **Transfer ownership?** and names both halves of the swap: "A project has one owner. Whoever you choose becomes the owner of [project]. You become an admin."

    Two rules shape who you can pick:

    - **The new owner must already be on the project.** Ownership is a promotion, not an invitation, so a stranger is never quietly added. Aim the transfer at someone with no grant and the refusal quotes their email address back and tells you the step you are missing — give them access to the project first, then transfer ownership to them. Teams are not candidates either; a project is owned by a person.
    - **The outgoing owner steps down to Admin**, keeping full operational control of what they built. The swap is atomic, so there is never a moment with two owners or none.

    **You should see:** the panel repaint with the **Owner** badge on its new holder, and your own row drop to an editable **Admin**.
  </Step>
</Steps>

## Trace changes in the access history

Both the **Members** and **Project access** tabs carry a **View access history** button. It opens a right-anchored drawer — no navigation away from what you were doing — described in the app as "Every authorization decision and access change in this workspace, newest first. Select a person to trace how they reached the projects they can see."

The feed is a table of **Person · Action · Resource · Outcome · When**, newest first. Two kinds of row are interleaved, and the **Outcome** column is how you tell them apart:

| Row | Outcome reads | Clickable |
|---|---|---|
| An **authorization decision** — someone tried to reach something | **Allowed** or **Denied** | Yes — opens that person's provenance |
| A **permission change** — a grant, a revoke, an invite sent or withdrawn, a team edit | **Change** | No |

So a grant you just handed out does not appear as "Allowed"; it appears as a **Change** row, tinted by what it did. Behind the feed, every access decision and permission change is written to a durable, append-only audit trail; a permission change that can't be audited doesn't happen.

## The Credits tab

**Credits** tracks how much of your workspace credit pool you have used this billing month. The **Credit usage** card carries a used-percentage meter and three figures — **Used**, **Pool**, and **Remaining** — plus a **Where your credits went** breakdown and the timestamp it was read at. **The pool resets monthly.**

Two states are worth recognizing:

- **No pool yet.** Usage is metered but nothing is capped, and the card says so.
- **Past the pool.** The card reads "You have gone past your credit pool for this billing month." When a workspace is capped and reaches its limit, runs are refused with a clear message telling you to contact your admin, rather than failing obscurely.

## The Connected orgs tab

**Connected orgs** lists the Salesforce orgs your *workspace* is connected to — one card per org, showing which projects use it, its connection state, and how it signs in (for a connection made the recommended way, **Admin authorization**).

Every card offers **Delete**, which removes the connection from Trust AI across every project that uses it. **Disconnect** — which also tears down the app Trust AI deployed in your Salesforce org — appears **only on connections made by admin authorization**, because those are the only ones with a Trust AI–deployed app to remove; a connection wired to an app your own admin created offers **Delete** alone. Both actions are destructive and both ask you to confirm.

This tab is where you see connections your projects share. Reading a row, reusing an org, and choosing between the two removals are covered in full in [Manage Salesforce connections](/how-to/manage-salesforce-connections). Creating one is a per-project job, done on that project's own **Settings → Connections** tab — see [Manage a project's connections](/how-to/manage-project-connections) for that tab, and [Connect a Salesforce Agentforce agent](/how-to/connect-agentforce) for the Salesforce setup itself.

## The General tab

**General** holds the settings that apply across every project in the workspace. At this release that is **Conversation capture**: a **Capture TrustAI agent conversations** switch (off by default) with an explicit **Save changes** commit. When on, conversations with the in-app agent across every project are saved into one auto-managed project for review and evaluation; turning it off deletes that project and everything captured in it, so the off-switch asks you to confirm.

<Note>
  Workspace administration is also available on the wire — members, invites and their lifecycle, teams, per-project grants, roles, and the audit feed. Request and response shapes live in the [API Reference](/api-reference).
</Note>

## Common stumbles

<AccordionGroup>
  <Accordion title="I can't demote or remove someone">
    Check who you're acting on. The **Owner** is never removable and their role is never reassignable here; the **last remaining administrator** can't be demoted or removed (promote another admin first); and you can't strip your **own** admin access — another admin has to. In each case the option is disabled with the reason inline.
  </Accordion>

  <Accordion title="An Admin can't open a project">
    Expected. A workspace role governs administration, not project content — project content is always gated by a project grant, admins included. Grant them **Viewer**, **Editor** or **Admin** on the project (directly or via a team) from **Project access**. The same is true of a workspace **Owner** without a grant.
  </Accordion>

  <Accordion title="An Editor can't archive a project">
    Expected — the three lifecycle acts sit at three different tiers. Renaming and editing the description are **Editor**; archiving and restoring are **Admin** on the project; transferring ownership and deleting are the project's **Owner** or a workspace Owner or Admin. Grant them **Admin** on the project from **Project access** if archiving is what they need.
  </Accordion>

  <Accordion title="I can't find the permanent-delete button for a project">
    There isn't one. A project's **Settings → General** offers **Archive project**, which hides it from active views while preserving its history, settings, members and artifacts — and an archived project is restored from the **Archived projects** group in the project switcher. There is no Danger zone and no destructive delete anywhere on the surface.
  </Accordion>

  <Accordion title="The roles reference calls the Member role &quot;Editor&quot;">
    The **What can each role do?** drawer labels the third workspace role **Editor**, while the roster and the invite dialog call the same role **Member**. It is one role under two labels, not two roles. Read the drawer's row as the workspace **Member** role; **Editor** as a *grant* tier is a different thing entirely — it is what a person holds on one project.
  </Accordion>

  <Accordion title="Someone I invited isn't in the roster as a member">
    They probably haven't accepted yet — look for their row with an **Invited** pill (the header count shows "· N pending"). If the pill reads **Expired**, use the row's menu to **Resend invitation**. Invitations are delivered by email to the address you entered.
  </Accordion>

  <Accordion title="Where did the Roles & permissions and Access audit tabs go?">
    They're no longer tabs — each became an in-context reference. The roles matrix opens as the **What can each role do?** drawer from any role picker, and the audit feed opens as the **View access history** drawer from **Members** and **Project access**. Old bookmarks to either surface still resolve.
  </Accordion>

  <Accordion title="Deleting a team warned me people would lose access">
    That's the point of the warning: a team bundles project grants, so deleting it revokes them — anyone who reached a project *only* through that team loses access immediately, while the people stay in the workspace. If that's not what you want, revoke or re-grant access per project first.
  </Accordion>
</AccordionGroup>
