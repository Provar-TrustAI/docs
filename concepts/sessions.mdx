A Session is one complete conversation between a user and an agent — every message, tool call, and intermediate step captured as it happened. Sessions are the evidence layer of TrustAI: [Annotations](/concepts/annotations) grade them, [Evaluations](/concepts/evaluations) can run directly against them, and evaluator accuracy is measured against the human verdicts you record on them. [Scenarios](/concepts/scenarios) are where you author what to test; Sessions are where you review and grade what actually happened.

## What's in a Session

A Session is a tree of nested structures:

- **The Session itself** — top-level metadata: its Source, timestamps, the Model and agent version it ran against, and where it was simulated from.
- **Turns** — each message exchange between the user and the agent, with an optional response-latency readout per turn. {/* ACCURACY-AUDIT-PENDING */} A turn can also carry **pictures** — images sent with the message, kept with the conversation and handed back when you reopen it.
- **Tool calls inside a Turn** — function name, arguments, return value. Often the most diagnostic data in a Session.
- **Agent steps** — the trace between question and answer. The transcript labels four kinds:

  | Step | What it shows |
  |---|---|
  | **Thinking** | The model's reasoning in plain language |
  | **Model call** | A summary of one underlying model request — the friendly model name leads it ("Claude Opus 4.8 · 1180 in / 142 out"), and the kicker reads "Model call · 1180 in / 142 out" only where the platform published no model id. Raw payload sits behind an opt-in **Input** / **Output** disclosure |
  | **Tool used** | A function the agent invoked mid-turn |
  | **Routed to** | A routing decision — which downstream agent or skill took the turn |

  Reasoning is provider-dependent — where a runtime can't emit it, the transcript simply shows no Thinking steps rather than a blank frame.

{/* ACCURACY-AUDIT-PENDING */}
A simulated conversation closes with one plain-English line saying why it stopped. It reads **This conversation ended because** and finishes with one of: *the customer got what they needed*, *the agent could not help with it*, *the customer gave up*, *the agent ended or transferred it*, or *it reached the length limit before finishing* — falling back to *the customer chose to stop* where the reason isn't one this build recognises. Where the simulated customer explained itself, its own words follow on a second line, quoted verbatim rather than paraphrased. A conversation with no recorded ending renders nothing at all, so read a missing line as "not recorded", never as "unknown".

Think of a Session as a fully-resolved record: not just what the user said and what the agent said back, but every decision the agent made on the way to its response. Annotations and evaluation results attach to the Session as a whole — you grade the conversation, not an individual Turn.

## Where Sessions come from

Sessions have three origins, and every session wears a **Source** chip that tells you which:

| Source | How the session was created |
|---|---|
| **Scenario** | Simulated from a scenario — by running it, generating sessions from it, or evaluating it. The session links back to the scenario it came from. |
| **Playground** | An interactive capture finalized without a scenario link. Note that the [Playground](/concepts/playground)'s own **Save as a scenario** flow always attaches a scenario, so a conversation you save there lands as **Scenario**, not Playground — and one you never save does not become a session at all. |
| **External** | Synced from a connected agent runtime — a real conversation your agent already had. |

A session linked to a scenario always shows **Scenario**, and its **Details** tab carries a **Simulated from** card naming the scenario and persona behind it.

Session IDs reflect origin too: sessions generated in-product get `RUN-` ids (`RUN-000014`), synced external sessions get `SES-` ids (`SES-000013`). Both draw from one per-project counter, and old links keep resolving either way.

### Connected runtimes

**Backfill reaches exactly one platform: AWS Bedrock AgentCore.** Your runtime emits invocation logs to CloudWatch and TrustAI's pipeline pulls them through a cross-account IAM role you grant during [Connect an AWS Bedrock AgentCore agent](/how-to/connect-agentcore); each invocation becomes a Session in your Project.

**Sync now** in the Sessions header opens a picker of your project's connected agents, grouped by platform. The picker lists *every* connected agent, but only an AgentCore agent actually pulls anything — pick a Salesforce Agentforce, Claude Managed Agent, or Conversational HTTP agent and the sync returns nothing and says historical session sync is supported only for AWS Bedrock AgentCore. Sessions from those platforms arrive as they are produced, written by a scenario run or a Playground conversation rather than by backfill. Ingestion is read-only: TrustAI never modifies the source runtime or its logs.

#### What a Salesforce Agentforce session carries

A conversation served by a connected Agentforce org arrives with the org's own evidence attached.

{/* ACCURACY-AUDIT-PENDING */}
At the foot of the fly-in's **Evaluations** tab — below every TrustAI result, never mixed in among them — a **Salesforce also scored this** section reports how Salesforce graded its own agent, turn by turn. There is one card per turn, each carrying **Task resolution** and **Instruction adherence** with Salesforce's written reasoning quoted as Salesforce wrote it, plus a line of its own on any turn where Salesforce flagged its own reply as unsafe. Read it as a contrast signal against your own evaluators rather than a second verdict in their vocabulary: it carries no Pass / Fail pill, and it renders nothing at all until the org's scoring lands — no empty state, no waiting banner.

{/* ACCURACY-AUDIT-PENDING */}
Two things also shape the transcript itself. A **Model call** step carries the detail of one underlying model request, alongside the Thinking, Tool used, and Routed to steps every transcript can hold. And where an action returned Salesforce records, the transcript renders them as labelled cards rather than raw payload: a single record is shown whole, while a list of several is shortened to one line per field and capped at ten cards, closing with a line that accounts for the rest — "…and 4 more records."

## In the app

The Sessions list is where you review, grade, and evaluate captured conversations. The table and panel behaviors shared across list surfaces — sorting, the column menu, range selection, the keyboard contract — are described in [Tables and panels](/concepts/tables-and-panels); here is what the surface offers:

- **Sortable table** — six system columns show by default: **Session ID** (the readable `RUN-` / `SES-` id), **Transcript**, **Routed To**, **Tools Called**, **Turns**, and **Date**. Four more ship hidden — **User**, **Duration**, **Source**, and **Tags** — one click away under **Hidden columns** in the **Add column** menu. The reserved **Verdict** annotation column also starts visible alongside the six; every other annotation column starts hidden. Column and filter configurations persist as [saved views](/concepts/saved-views) your team can share.
- **Filtering** — **Add filter** offers four dimensions: **Date**, **Routed To**, **Tags**, and **Turn count**. A fifth, **User**, joins them only where the loaded sessions carry an end-user identifier.
- **Typed annotation columns** — every project starts with three: **Verdict** (pass / fail), **Severity** (minor / major / blocker), and **Reviewer note**. **Add column → New annotation column** adds your own, typed **Pass / Fail**, **Score** (1–5), **Category** (single choice), **Tags** (multiple from a palette), or **Comment**. Verdict and severity cells edit inline, right in the table.
- **Column control** — one column menu handles show/hide and drag-to-reorder, and the order is remembered per saved view. Shift-click a second checkbox to select a whole range of sessions at once.
- **Bulk actions** — selecting sessions raises a bar with **Evaluate** (the primary action), **Tag**, **Download** (CSV export of the selection), and **Clear selection**.
- **Fly-in detail panel** — click any session to open a panel with five tabs: **Transcript** (default), **Annotations**, **Evaluations**, **Test Data**, and **Details**. **Test Data** sits between Evaluations and Details and reports what TrustAI set up, read back, and cleaned up around this one conversation — see [Test data](/concepts/test-data). The header carries the session's evaluation verdict as a pill, an **Evaluate** button, a **Tag** button, and an overflow menu offering **Download transcript**, **Copy session ID**, and **Copy link**.
- {/* ACCURACY-AUDIT-PENDING */}**Pictures in the transcript** — an image sent with a turn renders inline in the bubble. Click it to open it over the whole window, and leave by <kbd>Esc</kbd>, the close control, or a click outside the picture. Where a picture can't be shown, the row keeps the file name and says which case it is: never saved with the conversation, or saved but not loadable here.
- {/* ACCURACY-AUDIT-PENDING */}**Quick evaluation in place** — **Evaluate** in the fly-in header grades this one conversation and mints no run. A **Queued** card appears on the **Evaluations** tab, turns to **Running**, and counts the checks off as they land — "Scoring check 2 of 3…". The progress is held on the server, so it survives a reload and a colleague watching in another tab sees the same state. [Evaluate sessions](/how-to/evaluate-sessions) is the recipe.
- **Keyboard navigation** — <kbd>J</kbd> / <kbd>K</kbd> cycles through sessions, <kbd>F</kbd> toggles fullscreen, <kbd>Esc</kbd> exits fullscreen first and then closes the panel.
- **Details tab** — a **Session properties** block of ten rows: Session ID, Run date, Triggered by, Source, Model, Turn count, Duration, Routed to, Tools called, and Tags. Simulated sessions carry a **Simulated from** provenance card above it.
- **Transcripts are immutable** — there is no Delete Session action, and a session's conversation can't be edited. What you *can* write are the annotation values and tags layered on top; tags autocomplete from one vocabulary shared with Scenarios.

Earlier releases had you curate sessions into datasets and replay them against new agent versions. That workflow is retired: regression testing now runs through [Scenarios](/concepts/scenarios), which simulate fresh conversations against the [Agent Version](/concepts/agent-versions) you pick at evaluation time — and Sessions became something you evaluate directly, in place.

## Sessions vs traces — same data, different name?

If you've used observability tools (Langfuse, Phoenix, LangSmith) you may have heard the data called a "trace." TrustAI deliberately uses **Session**:

| Term | Implies |
|---|---|
| Trace | Engineering observability — debugging a single execution |
| Session | A complete user interaction — a unit of agent behavior worth judging |

The distinction matters because the workflows differ. Traces are for engineers reading logs. Sessions are for **QA Practitioners** grading behavior and authoring scenarios, and **Agent Owners** judging results. Both are valid lenses; TrustAI deliberately picks the term that maps to its core users.

## What a Session carries

Out of the box, every Session carries:

- Origin: the **Source** chip (Scenario / Playground / External) and the readable `RUN-` / `SES-` id
- Provenance: the linked scenario and persona (for simulated sessions), the **Model** row — replaced by an **Agent** row naming the Salesforce agent on an Agentforce session — and the agent version
- Time: when the conversation happened and when it was captured
- Routing: the **Routed To** route, plus tool calls made along the way
- Human signal: annotation column values (Verdict, Severity, and any custom columns) and tags
- Automated signal: the session's evaluation verdict — **Pass**, **Fail**, or one of two distinct neutrals, **Not evaluated** (nothing ran) and **Not graded** (something ran but produced no behavioural score). Five outcomes leave a run's pass-rate denominator, and one of them belongs to the agent: where an action the agent itself runs returns an error, the conversation reads amber **Couldn't test** on that run's results — excluded from the score like an environment problem, never excused as one. Back on the Session, a run that ended that way reads **Not graded**.

Not all of it is filterable. The table filters on **Date**, **Routed To**, **Tags**, and **Turn
count** — plus **User**, where the loaded sessions carry an end-user identifier; the rest is there to read, sort, and export. To narrow by something the filter set doesn't
cover — Source, say, or a verdict — show that column, sort on it, or ask the
[Trust Agent](/concepts/trust-agent) for the sessions you want.

## Working with Sessions

Everything you do with a Session happens from the Sessions list or by asking the [Trust Agent](/concepts/trust-agent). You filter the table, open a session to read its transcript, set a Verdict inline, tag it, or evaluate it — all without leaving the surface. You can also ask the Trust Agent to find and read sessions for you — "show me failed sessions from yesterday" — and evaluating them is launcher-driven from the list or the panel (see [Evaluate sessions](/how-to/evaluate-sessions)).

Developers who want the underlying endpoints can find full request and response shapes in the [API Reference](/api-reference).
