The [Trust Agent](/concepts/trust-agent) is the in-app assistant that helps you do evaluation work on a project. When it wants to read your data it just streams the answer. When it wants to **write** — create, update, delete, or run a record — it needs your permission first.

There are two ways it gets that permission, and knowing both is the difference between reading the agent correctly and being surprised by it:

- **A permission card.** The default. The agent stops, replaces the composer with a card, and waits for your decision.
- **A standing approval.** Once you have approved a repeated write "in this chat", the next write of that same kind commits with **no card at all** — you see the result, not a request.

This page covers both paths, plus the question cards the agent raises when it needs information rather than permission.

<Note>
  The Trust Agent is the in-app assistant, not an [Agent Version](/concepts/agent-versions) (the agent under test). The two share the word "agent" but are different concepts — this page is about approving writes the *in-app assistant* proposes.
</Note>

This how-to picks up where [Work with the Trust Agent](/how-to/work-with-the-trust-agent) leaves off — that page covers driving the agent and the clarify-first flow. Here, you'll learn to handle the three interrupt cards the agent uses to ask for your input:

- A **permission card** — gates a write before it runs
- A **single-question card** — one open-ended clarification
- A **multi-question flow card** — a stepped set of clarifications

After this, you'll be able to review a proposed change, approve it (and watch it land for real), reject it with a note, answer the agent's questions, grant and turn off a standing approval, and find the resolved decision in the transcript afterward.

## How the approval gate works

When the agent decides to perform a write and no standing approval covers it, it surfaces a **permission card** in the place where the composer normally sits — the text input disappears and the card takes its slot. At that point the agent run **halts** at the tool call and waits: no further turns run until you decide.

Permission cards gate **writes specifically**. A read-only request — "list my sessions," "what failed in this evaluation" — streams its result straight back (often as a [clickable object table](/concepts/trust-agent)), with no card and no approval needed. This holds even when a read and a gated write land in the same turn: the read has no side effects, so it still returns its result while the write waits for you. Only the write is held.

<Warning>
  Approving a write **executes it for real**. The Trust Agent runs the approved change on the live agent run path — the mutation persists in your project; it is not a preview or a dry run. Treat every approval as a real edit to your data.
</Warning>

<Info>
  **The approval you gave is what authorizes the write.** The server, not your browser, decides whether a write may execute: it only accepts a decision for a gate it raised itself, and it binds that decision to the write the card was actually about. A different write chained into the same turn does not inherit your approval — it asks again.

  A write is also expected to stay inside the project and organization you are working in. See [Multi-tenancy](/concepts/multi-tenancy) for the platform detail.
</Info>

## The permission card

When a write is proposed, the permission card greets you with a **write preview** — not a bare record ID. Depending on what the write does, you can see:

- **The diff** — the field-level before-and-after for an update
- **The dependencies** — the linked records a delete would affect
- **The proposed end state** — what the record will look like after the change

The write preview always speaks in human terms — a delete shows the record by its label and lists what depends on it, so you can see the blast radius before you commit to it. When the write carries structured detail like that, the card also offers a **View proposal** link that opens a right-side panel showing the record as it would look after the change. A simple create with nothing structured to diff shows the agent's plain description and no link.

The preview also keeps proposing tense. Until you approve, nothing has happened — a pending delete is badged **Pending delete** (and other writes **Pending approval**), never a false "Deleted." If the panel says a record is gone but you haven't approved anything, that's a bug, not the design.

## Approve, dismiss, or reject

Once you've read the preview, you have three ways to resolve a permission card.

<Steps>
  <Step title="Approve to execute">
    Pick an approval option, then confirm. The agent writes the option labels itself, so they name the actual work — a card filing a requirement offers **File it**, a card generating a scenario offers **Generate it**.

    **Approving once covers the batch that card represented, not one record.** If the agent is partway through a repeated series — filing four requirements, generating scenarios — a single approval lets the rest of that series through **for the remainder of that turn**. It does not carry into your next message: the next turn asks again.

    Three kinds of write are held back from that batch behavior and are approved strictly one write at a time: a **delete**, **authoring an agent profile**, and a **bulk edit that has a requirement mixed into it**. These are the same three a standing approval can never cover — see the exclusions under [Standing approvals](#standing-approvals).

    When the agent expects to keep repeating the same kind of write, the card also offers a **for-this-chat** option, worded for what it would keep doing. That one is a standing approval — see [Standing approvals](#standing-approvals) below. Deletes never offer it.

    The confirm button reads **Approve** for either approval option, and **Delete** (or **Delete N items**) on a delete card.

    Once you confirm, the agent run resumes from where it halted and performs the write — the change lands in your project. Watch the [side rail](/concepts/trust-agent) **Outputs** section: the record the agent created, updated, or ran shows up there as a row you can open in a fly-in.

    **You should see:** the card resolve, the run continue, and the affected record reflect the change when you re-open it. The write is real — re-query the record and the mutation is there.
  </Step>

  <Step title="Dismiss to decline">
    If you don't want the change, **dismiss** the card with the × in its top-right corner. The write does not run, and the agent waits for your next message instead of acting. A resolved row still lands in the transcript — it reads "You dismissed the request. I'll wait for your next message." — so the declined decision is on the record.

    **You should see:** no change to the record, and the composer return so you can redirect the agent.
  </Step>

  <Step title="Reject and tell the agent why">
    If the proposed write is close but wrong, choose **Reject — and tell me why (optional)**. An inline note field opens inside that option; type your reason (or leave it blank) and the confirm button becomes **Send rejection**. Your reason goes back to the agent, so it can adjust rather than guess.

    **You should see:** your rejection and your reason echoed into the transcript ("You rejected: *your note*"), and the agent respond to your reasoning on its next turn.
  </Step>
</Steps>

<Note>
  A permission card is not the same as a plan confirmation. In Plan mode the agent proposes a task list and waits at a plan-confirm bar — one tap on **Approve & run** starts the work, or you can type a go-ahead in the composer and it does the same thing. That's a different gate: it approves a plan, not a write. A permission card is the per-write checkpoint, and it's what executes the change. See [Work with the Trust Agent](/how-to/work-with-the-trust-agent) for Plan mode.
</Note>

## Standing approvals

A **standing approval** is the durable, chat-wide version of the same decision. You grant it by choosing the card's for-this-chat option instead of the one-time one, and from that moment the agent stops asking for that kind of write in that chat.

It is not a session convenience. The grant is recorded on the server against the chat, so it survives a page reload, a browser restart, and a switch to a different machine. Reopen the chat tomorrow and it is still there.

### What you actually see once a grant is live

Two things change, and the second one is the one to internalize.

1. **A chip appears in the composer.** It reads, for example, **create requirements in this chat · Active until Aug 13**, with an × beside it. It stays visible for as long as the grant is live, wherever the chat itself is on screen — the full page and the docked panel both show it. Collapse the agent all the way to the pill and the composer goes with it, so reopen the chat to see (or turn off) the grant. Screen readers hear it prefixed with "Standing approval active:".
2. **The next matching write raises no card.** The agent performs it and reports the result. There is no gate, no halt, no confirm button — the approval you already gave is what authorized it.

That second point is why the chip exists. A standing approval is deliberately never invisible: if the agent can write without asking, you can always see that it can, and you can always take it back.

### The grant is scoped, and it expires

A standing approval binds to a **kind of write**, not to one record and not to your whole account:

| Dimension | What it covers |
| --- | --- |
| Chat | The one conversation you granted it in. Other chats are unaffected. |
| Action | One verb — create, update, or run — on one kind of record. "Create requirements" does not authorize deleting them. |
| Lifetime | **Seven days** from the moment you approved, shown on the chip as "Active until *date*". After that the agent asks again. |

### Turn a grant off

Choose the × on the chip. Its accessible name is **Turn off: *the grant's label*** — for example "Turn off: create requirements in this chat". The chip disappears and the next write of that kind raises a card again.

There is no confirmation step and nothing to undo — turning a grant off only removes the agent's permission to skip the card. Writes it already made stay made.

<Warning>
  Three things a standing approval can never do, no matter what you grant.

  - **It never covers a delete.** An irreversible removal is confirmed every single time, and the for-this-chat option is not even offered on a delete card.
  - **It never covers authoring an agent profile.** That write replaces the profile every evaluation in the project reads from, so it is confirmed each time.
  - **It never lets a requirement ride along in a bulk edit.** A grant for scenario edits covers a bulk change to scenarios. If a requirement is mixed into that same batch, the whole batch falls back to a card — a scenario grant can never quietly commit a requirement change.
</Warning>

## Answer a question card

Sometimes the agent doesn't have enough to act yet. Instead of a permission card it raises a **question card** — also in the composer slot — and pauses until you answer. There are two shapes.

### A single-question card

For one open-ended clarification, you get a single-question card. It offers the **drafted choices** the agent thinks are likely, plus a write-in field ("Or type your own answer…") so you're never boxed into the offered answers. The card is dismissible if you'd rather steer the agent a different way.

### A multi-question flow card

When the agent needs several inputs, it raises a **multi-question flow card**. It's stepped: questions come one at a time with a progress row ("Question N of M"), and you can go **back** to a previous question to change an earlier answer before submitting. Nothing is sent until you submit the batch — then all your answers go to the agent together. Each question carries the same drafted choices and write-in option as the single-question card.

## Find the decision in the transcript

Every resolution — an approval, an answer, or a dismissal — is recorded back into the transcript as a **resolved row** that echoes what you chose. An approval's resolved row quotes the option you picked, so a standing approval reads differently from a one-time one later. For a multi-question flow, the resolved row echoes each per-question answer. This is your audit trail: it persists after the turn completes, so reopening the chat later still shows what was asked and what you decided.

## A pending approval survives a reload

You don't lose the gate if your connection drops, you reload, or you close the tab before deciding. When you reopen the chat, a card that was still awaiting your answer **rehydrates as a live, answerable card** — back in the composer slot, with the composer still gated — and resolving it resumes the halted run exactly as if you had never left. Already-resolved approvals rehydrate too, in the order they happened, so a reopened chat reads the same as it did live.

**You should see:** after a mid-decision reload, the same permission or question card waiting in the composer slot; answer it and the run picks up where it halted.

## When the agent is minimized

You don't have to keep the full agent open to catch an approval — but the two collapsed states behave differently.

- **Collapsed to the pill.** The pill grows a pulsing **needs you** badge, and the agent **auto-expands to the docked panel** so the card surfaces without you tapping anything. That auto-expand fires only from the pill, and only for a blocking gate — the agent will not pop itself open just because it is working.
- **Already in the docked panel.** The card is already on screen, so nothing expands. The docked header (and the full-page header) shows an **Awaiting your answer** badge instead — a longer label than the pill's, for the room it has.

<Note>
  There may be a brief wait before a card appears. That's the model thinking — its time-to-first-token — not a hang. The agent fills the wait with a live **Thinking** timer and a working indicator rather than a dead gap, and the card paints as soon as the model reaches the write. There's no fixed timing; it depends on the model in use.
</Note>

## Accessibility

The approval flow is keyboard- and screen-reader-friendly.

- **Announcement.** The composer slot the cards land in is a polite live region, so a screen reader announces the interrupt's title and body when it appears — you are told a decision is waiting without having to go looking. It does not re-announce every time you change a selection inside the card.
- **Focus.** When a card appears, focus moves into it automatically.
- **Named controls.** The standing-approval chip's × is a real focusable control whose accessible name states both the action and its target ("Turn off: create requirements in this chat"), so it is never ambiguous which grant you are removing.

Resolving or dismissing a card should return focus to where it was, and the flow is built to meet WCAG AA contrast.
