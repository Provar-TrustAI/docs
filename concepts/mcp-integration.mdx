Trust AI is a [Model Context Protocol](https://modelcontextprotocol.io) (MCP) server. An MCP client you already use — Claude Code, Codex, or anything else that speaks the protocol — connects to your workspace with a URL and one browser click. From then on, your own agent can do evaluation work in Trust AI without anyone opening the product.

This page explains the surface: what an external agent can reach, how a person grants it access, and what Trust AI still holds onto regardless of what was granted. [Connect an MCP client](/how-to/connect-mcp-client) covers the setup itself.

<Note>
  Two different agents are in play on this page, and they are not the same thing. Your **MCP client** is an outside agent calling Trust AI. The [Trust Agent](/concepts/trust-agent) is the assistant inside the product. They reach many of the same capabilities, and neither one's permissions carry over to the other.
</Note>

## What an external agent can do

The surface is built around one loop: describe what the agent under test must do, build the checks that prove it, run the conversations, and read the verdicts.

A connected client can get oriented in a project and then keep working in it without repeating the project on every call. It can write requirements and connect them to the scenarios that cover them and the evaluators that judge them. It can draft scoring rules from a plain-language goal, save evaluators, and read the ones the project already holds. It can create scenarios, add the personas who act them out, attach and detach evaluators, set a scenario's expected output, and attach a picture by naming where it lives, so a simulated customer can show it to the agent mid-conversation.

From there it can launch an evaluation over the scenarios it chose, poll for progress, and read the results per scenario. When a verdict needs a second opinion, it can gather everything required to judge one conversation — what was being tested, what was said, what each judge concluded, and what the run left behind — in a single read.

Two things are worth holding onto, because both fail quietly:

- **Grading resolves off the scenario.** Linking an evaluator to a requirement records which evaluator judges that requirement. It does not attach the evaluator to the scenarios linked to it, and a scenario is graded only by the evaluators attached to the scenario itself. Link and attach are two calls, and the platform says so in the result of the first one.
- **Launching spends.** Every scenario in a run becomes a real conversation against your connected agent, on your workspace's credits. A repeat of an identical launch returns the run already under way rather than starting a second one, so a client that retried after its own deadline passed does not double-spend.

## The tool surface

Six tools cover the whole surface. Each one covers a capability area and takes an operation name plus that operation's arguments, so the tool list a client carries on every turn stays six one-line descriptions rather than dozens of full schemas.

| Tool | What it covers |
| --- | --- |
| `trustai_project` | Who you are, which workspace and projects you can reach, a project's current state, and naming a project for the rest of the session |
| `trustai_requirements` | Writing and reading requirements, and connecting them to the scenarios and evaluators that prove them |
| `trustai_evaluators` | Reading this project's evaluators, saving new ones, and drafting scoring rules from a plain-language goal without saving anything |
| `trustai_scenarios` | Scenarios and their personas, the evaluators attached to them, expected output, and the pictures a simulated customer can show the agent |
| `trustai_runs` | Launching an evaluation, checking how far along it is, and reading how it went |
| `trustai_adjudicate` | Gathering the evidence needed to judge one evaluated conversation |

Operations land per capability, so which ones a tool carries changes over time. That is why no document is the live answer to "what can this tool do".

### Schemas are read per tool, not carried per turn

Every tool's description names a schema resource addressed as `trustai://schema/<tool>` — `trustai://schema/trustai_scenarios`, for instance. A client reads that resource once, for the tool it is about to use, and gets the operation names and the argument shape for each of them. Nothing else is paid for until it is needed.

The refusals point back at the same place. A client that guesses an operation name is told which ones exist and where the arguments are documented; a client that sends the wrong argument shape is told what was wrong with it and sent to the same resource. Both are recoverable on the next turn without a person in the loop.

### The original per-capability tools

An older surface is still served from the same endpoint: a set of tools named with a dot rather than an underscore — `trustai.get_project_state`, `trustai.query_data`, `trustai.read_file`, `trustai.analyze`, and four writes. They predate the six above and publish one tool per capability with its full argument schema.

Keep the two shapes distinct when you read a client's tool list. The dotted names are the earlier surface; the underscored six are the one to build on.

### Trust Agent recipes arrive as prompts

The recipes bundled with the [Trust Agent](/concepts/trust-agent) are also published as protocol-native MCP prompts, so a connected client loads the same playbooks by name instead of reinventing them. Only the names and one-line descriptions travel while the client is connected; the body of a recipe arrives when it is invoked. They are the same versioned source the product uses, not a client-specific copy.

## Consent: the three access levels

Connecting is an authorization flow the client walks on its own once it has the URL. The only part a person sees is a single consent screen, reached through your workspace's SSO identity provider, which names the app that is asking, the account it would act as, and the workspace it would act in.

The screen offers three answers:

- **Read only** — the connection can look at projects, scenarios, runs, and results, and nothing else.
- **Read and write** — the same reads, plus creating and changing requirements, evaluators, scenarios, and runs. Every change still stops and asks a person to approve it.
- **Read and write, act mode** — the same changes, made without stopping to ask each time. Every change is still recorded.

A client that asked for writes without asking to read anything sees **Write access** in place of the middle option, with the act-mode variant beside it. Only the options the request actually covers are rendered, so nothing on the screen is wider than what was asked for. Refusing has its own control rather than a radio button.

<Warning>
  **Act is a person's choice, made in a browser, and nothing else can reach it.** A client may ask for read and write access. It can never ask for act mode, and no tool call, argument, prompt, or session setting turns it on afterwards — it exists only because someone chose it at the consent screen, and revoking the connection revokes it too.
</Warning>

A grant is the overlap of what the client asked for and what the person picked, so it is never wider than either. When the overlap is empty — a client that asked only to write, answered **Read only** — nothing is minted and the client is told it was denied.

## Three different things are called "Act"

The word does three jobs in this product, and they are separate mechanisms with separate grants. None of them implies either of the others.

| Where you see it | What it is |
| --- | --- |
| **Act** mode in the Trust Agent | One of the assistant's three in-product operating modes (Ask, Plan, Act). It still stops for every write that changes something. |
| **act mode** on an MCP connection | A property of one bearer token, granted at the consent screen, that skips the per-change approval for that connection only. |
| **Standing approval** in the Trust Agent | A durable, chat-wide grant inside one conversation with the assistant. It grants nothing to any MCP connection. |

Granting act mode to your MCP client changes nothing inside the Trust Agent, and a standing approval you gave the Trust Agent changes nothing about what your MCP client must stop for. See [Approve an agent write](/how-to/approve-agent-writes) for the in-product side of this.

## The approval gate

Every change a connected client proposes passes the same gate, and the order of its first two steps is deliberate.

<Steps>
  <Step title="The connection's access is checked first">
    A read-only connection is refused here, in plain English, **before** an approval card is ever composed:

    ```
    This connection is read-only, so it can't run 'trustai_requirements.create'.
    Reconnect TrustAI from your MCP client and choose read and write access when asked.
    ```

    A credential someone deliberately narrowed can never generate approval prompts in their workspace for calls that could not have run.
  </Step>
  <Step title="The change is described">
    The platform builds the same plain-language card the Trust Agent uses — what would change, in a sentence a person can act on, naming the project it runs against.
  </Step>
  <Step title="A person answers, or act mode answers for them">
    On an ordinary read-and-write connection the call waits for a decision. On an act-mode connection the card is composed and recorded exactly the same way, and approved without pausing.
  </Step>
  <Step title="The wait has a budget, and it says so while it lasts">
    A waiting call holds for up to five minutes. That is longer than most clients tolerate on a silent connection, so the wait reports progress while it runs — *"Waiting for this change to be approved."* — rather than looking like a hang. An unanswered request times out and the change never runs.
  </Step>
</Steps>

The decision arrives out of band: the waiting call cannot prompt anyone itself, so the person driving the client finds what is pending and answers it on a separate request, which wakes the call. Only the principal whose call is waiting can see it or answer it — someone else's pending approval is not listed, and asking for one returns the same answer as having nothing pending. There is no approval inbox in the product for this; discovery is an API call the blocked client makes.

## The approval ledger

Every gated change a connected client proposes lands in a durable ledger, keyed by the workspace, the person, and the identity of the token that made the call. The ledger stores the card that was rendered and the arguments behind it, so what was approved is recoverable later in the same words the approver read.

It records how the decision was reached, and act mode is not hidden inside that: a change approved because the connection carries act mode is stamped as such, distinctly from one a person answered. The credential itself never appears — a bearer token is never stored in the clear, and the capability that answers an approval is never written to a log, a trace, or a refusal message.

## What act mode does not skip

Act mode removes one thing: the pause before each change. Everything else still applies.

- **Workspace tool permissions.** An admin who disables or restricts a Trust Agent tool has restricted that capability, not one route to it. The same write arriving through an MCP operation clears the same grant, so the MCP surface is never a way around a control a workspace turned on deliberately.
- **Project access.** Every call resolves your role on the target project through the same permission engine the rest of the product uses. Act mode grants no membership you did not already have.
- **The production launch guard.** A project connected to a live customer org refuses to launch a run unless the call explicitly confirms that is what it means. The refusal names the org, because *which* production org is the whole decision. Act mode does not satisfy that confirmation.

## Tenancy and the workspace boundary

A bearer token is bound to one workspace and one person, and everything it reaches is resolved inside that boundary.

Cross-workspace existence is never leaked: a project in another workspace and a project that does not exist come back as the same refusal, so a caller cannot use the difference to learn what another workspace holds. A project you can see but are not a member of answers differently, because that is a membership problem with a remedy — ask an owner to add you — rather than a boundary.

Refusals are written for the caller in English, not relayed from a database or a driver. A failure the platform cannot explain in the caller's terms comes back as one generic sentence, with the real detail kept on the server's own trace. See [Multi-tenancy](/concepts/multi-tenancy) for the boundary the whole platform enforces.

The consent screen itself cannot be embedded in another page, so a grant can never be collected by a site framing it.

## The token, and how to revoke it

Approving the consent screen mints a bearer token that carries the access level chosen, and nothing wider. It lasts 90 days. When it expires, the same browser hop runs again — there is nothing to re-paste, and no secret anyone copies by hand at any point.

A person can list what they have connected — the client's name, the access it was granted, the last few characters of the token, and when it was created, last used, and revoked — and revoke any of it. Revocation takes effect on that client's very next call.

<Info>
  **There is no screen for this in the product yet.** Listing and revoking connected clients is available on the wire only; request and response shapes live in the [API Reference](/api-reference). Removing a server from your client's own configuration is not revocation — it deletes the local entry and leaves the credential live.
</Info>

## What MCP does not reach yet

Parity with what the product itself can do is incomplete on purpose, and the gap is an enumerated list rather than an accident: a capability that is not on the surface is named in a conformance test, so a capability cannot quietly appear or disappear.

Two absences are worth knowing before you plan around them:

- **Comparing two runs is not exposed.** Run comparison has no screen in the product either — see [Evaluations](/concepts/evaluations) for where that stands.
- **Annotations are not exposed.** A human verdict recorded against a session is in-product work today.

Other capability areas still on that list include simulating a scenario on its own, a scenario's test data, agent versions and their profiles, session deletion, and imports and syncing.

## Observability

Every tool call, including a refused one, emits one tool span:

- The tool name and the tenant context — project, workspace, person — are stamped **before** the access check runs, so a refusal is recorded as "this person attempted this call on this project" rather than as silence.
- Arguments and results ride the span, truncated with an explicit marker when they are too large to carry, rather than dropped.
- A gated change carries the state of its approval, so activity can be filtered by whether it was approved, rejected, or never answered.
- A failure carries what kind it was, so an access refusal and a tool error are not one bucket.

The spans follow the same conventions as the Trust Agent's own tool calls, so both sit in one trace view.
