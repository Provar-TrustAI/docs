The Trust Agent is the in-app assistant that helps you do evaluation work inside a [Project](/concepts/projects). You ask it to find sessions, generate scenarios, draft an evaluator, run an evaluation, or analyze a regression — and it works in the open: streaming its reasoning, surfacing real records you can click into, planning before it acts, and asking for your approval before it changes anything. On a project that isn't finished yet it goes further: it walks a fixed authoring workflow — connect, capture requirements, write scenarios, build and attach evaluators, fill in expected output, run — and refuses to take those steps out of order. See [The workflow the agent enforces](#the-workflow-the-agent-enforces) below.

It lives at `/projects/:id/agent` and is the default, flag-free experience on every project. The legacy agent implementation is gone — there is no `?v2`, `?agui`, or `?legacy` flag to opt into; the Trust Agent you see is the only one there is.

<Note>
  **The Trust Agent is not an Agent Version.** They share the word "agent," but they are different concepts:

  - The **Trust Agent** (this page) is *your* assistant inside TrustAI — the thing that helps you build and run evaluations.
  - An **[Agent Version](/concepts/agent-versions)** is the *customer's agent under test* — a pinned snapshot of the agent you are judging.

  The Trust Agent helps you evaluate Agent Versions. It is never itself "a version." Everywhere this page says "the agent," it means the Trust Agent.
</Note>

## The three shells

The Trust Agent runs from a single instance that can show up in three shells, and your conversation moves with you between them:

- **Full page** — the agent occupies the project content pane, with the streaming transcript, composer, and side rail.
- **Docked panel** — a compact panel overlaying whatever tab you're on, so you can keep a conversation going while you work elsewhere. The docked header carries its own **Chats**, **Expand to full screen**, and **Close** controls.
- **Collapsed pill** — a minimized **Trust Agent** indicator that gets out of your way until you need it.

It is one mount, not three separate widgets. Minimizing the full view to the dock drops you back on the project tab you came from with the conversation intact beside it — same transcript, same composer, same mode and model chips — and re-expanding restores the full view with the whole turn history still there.

When a project has no active agent task, the agent resolves to the minimized pill so it stays out of the way.

The embed below is the clearest way to feel the three shells. Minimize a running chat to the dock, collapse it to the pill, then re-expand it — the conversation state carries across.

### Recent chats and persistence

A chat selector lists your recent chats, most-recent first, so you can move between conversations without losing your place. The project's left nav keeps a **Recent chats** group for the same reason.

Transcripts are durable, not just saved. Streamed turns, the agent's response blocks, and approval decisions persist in their true event order — through a page reload, a dropped connection, or closing the tab mid-stream — so a reopened chat matches what you saw live. That durability covers the parts that matter most: a pending approval gate comes back as an answerable card with the composer held until you decide, and a message you send while the agent is still responding is queued rather than lost — the composer shows it with a **Sends when Trust Agent finishes** note and a **Cancel** control.

A reply that was cut short comes back the same calm way whichever way it was cut. Reopen the chat and you get a quiet **This reply was interrupted.** note with a one-tap **Continue** action. That note covers two things: a connection that dropped mid-stream, and a turn you stopped yourself with **Stop**. The two are stored as different outcomes, but the transcript reads the same for both — no separate "cancelled" label ships — so it will not tell you which one happened. Continue resumes from the saved context; it picks the work back up rather than reattaching to the original live stream.

Starting a *new* chat opens a Welcome page — it does not start streaming on its own. Its composer carries the same mode, model and **Thinking** controls a live conversation does, so you can set all three before your first message. Under them sit four starter pills — **Evaluate agent**, **Improve requirements**, **Summarize evaluations**, **Connect agent** — and it is the same four at every project state, because the recipe behind the leading pill walks a bare project through its own prerequisites. Picking a pill expands two ready-made prompts; picking a prompt pre-fills the composer, and the prompt *you* submit is auto-sent as the conversation's first turn. Nothing runs until you send it.

In the full view the composer is pinned to the bottom of the screen, and the project's left nav (**New chat**, **Playground**, **Requirements**, **Scenarios**, **Sessions**, **Evaluators**, **Evaluations**, **Project Settings**) stays visible beside the agent — the assistant is seated *inside* the app, not floating over it. **New chat** is the agent's entry in that nav.

## The streaming transcript

The agent thinks and answers in the open. Reasoning, text, and tool-call arguments all stream live, token by token — a turn does not buffer silently until it finishes and then dump a wall of text. Because of that, an approval card can paint mid-turn, the moment the agent reaches the tool call that needs your decision, rather than only after the whole turn completes.

### Where the reply's time went

Every settled reply closes with one quiet line naming the total and the single biggest slice of it — **Answered in *42s* · *31s* thinking**, or *using tools*, or *waiting for you*. Expand it and you get a proportion bar with per-phase totals: **Thinking**, **Using tools**, **Writing the answer**, **Waiting for you**. A phase that took under a second gets no row, and a reply where every phase was that fast says so rather than showing an empty list. A whole reply under a second reads **Answered in under 1s** — never *0s*, which would claim it took no time at all.

The line only reports what it watched. A chat reopened from history carries none — that turn happened somewhere you weren't — and neither does a turn still paused at an approval gate, because it has not answered yet.

## Tool results as clickable records

The Trust Agent doesn't describe your records in paragraphs — it hands you the real things. When a tool result returns multiple records, they render as a **clickable object table** right in the chat: real, human-readable records with their reader-visible handles (`SCN-000008`, `SES-000010`) and a human summary, never a bare UUID. Click one and the real record's fly-in opens in context.

References carry their live state with them. A finished evaluation that produced no behavioural score reads **Completed · Not graded** — not a fabricated pass, and not the different label **Not evaluated**, which means no evaluation exists at all.

### The in-chat scenario workspace

A scenario reference doesn't bounce you out of the conversation. Clicking one opens the **full** scenario detail over the chat — the same tabbed panel the Scenarios list opens, with **Personas & Goals**, **Expected Output**, **Test Data**, and **Sessions** — and the Sessions tab drills one level further into a run's transcript, evaluations, and annotations without leaving the chat.

Runs launch from there in place, too: the panel's **Run & evaluate** and **Run only** controls start the run you asked for over the conversation, instead of sending you to the Scenarios list to pick the mode a second time.

## The side rail

While the agent plans and works, a side rail tracks what's happening, in four sections in this order:

1. **Progress** — the plan. Step counts and live execution status tick as the agent works through its task list. The section stays hidden until there is a plan.
2. **Context** — what the agent has read for this task. It **leads with a Connected agent card** naming the agent under test, its platform, and a health chip — **Not checked**, **Healthy**, **Degraded**, or **Unreachable** — followed by one compact count row per record type it reviewed.
3. **Outputs** — what the agent created, updated, or ran, per entity, each deep-linking into a fly-in. Work still in flight shows as **Generating…** for a session and **Running…** for an evaluation until the real row lands.
4. **Attachments** — the files attached to the active task. Click a file and a readable preview opens in place — no download required — for PDF, Word, Markdown, text, CSV, and JSON.

Context rows are compact by default: a row like **10 scenarios** is an **expand toggle**, not a dead label. Open it and you get the individual records that count summarizes, each clickable into its real fly-in.

The rail stays visible across the whole conversation — it doesn't reset or vanish when you send a follow-up — so it remains a stable map of the work from planning through execution. Counts in the rail show the latest count per item type, not a confusing running sum.

## Human-in-the-loop approvals

The Trust Agent stops for you before it does anything consequential. Approvals use an **interrupt shell** that replaces the composer in its slot and hosts five kinds of card:

- A **permission card** — gates a write.
- A **single-question card** — one clarifying question.
- A **multi-question flow card** — a short sequence of clarifying questions, shown as **Question *N* of *K*** with **← Back** and **Next →** between them.
- A **connect-agent card** — the secure in-chat gate for connecting the agent you want to test.
- A **choose-agent card** — picks which Salesforce agent a just-provisioned connection should use.

All five halt the run the same way: the agent's turn pauses at that tool call, and only your decision resumes it. Every card can also be waved off rather than answered — question cards with **Skip**, a permission card with its floating **×**, which approves nothing and hands the turn back with *You dismissed the request. I'll wait for your next message.* A question card offers a free-text **Other** answer when the agent asks for one — that is a per-question choice, not something every card carries.

### What a permission card asks

A permission card names the write in plain language — *Create the evaluator 'Refund tone judge'?* — with a **3 fields changed** summary and a **View proposal** control that opens the full write preview: the field-level old-versus-new **diff**, the **dependencies** a delete would affect, and the **proposed end state**, all before you decide. Approving actually executes the write on the real agent run path. It is not a preview that quietly does nothing.

You get three scopes, not one button:

| Scope | What it does |
|---|---|
| **One time** | Approves exactly this write. The agent writes the label itself — "Create it", "Run it" — so the button names the actual action. |
| **Always … in this chat** | Creates a **standing approval** — for example, "Always create evaluators in this chat". Offered for create, update, and run actions, and only when the agent proposes it. |
| **Reject** | A row that *is* a note field, placeholder **Reject — and tell me why (optional)**. Type a reason or leave it blank. |

The footer's primary control follows what you picked: **Approve** for either grant, **Send rejection** once the reject row is selected. A delete card is the exception — its primary control names the destruction and its scale, **Delete *N* items**, in a danger tone, and it reverts to a neutral control the moment you select reject, because rejecting a delete is a cancellation rather than a destructive act. Your decision is recorded in the transcript afterwards — **You approved: Create it**, **You rejected: *&lt;your note&gt;*** — so the audit trail a reopened chat shows matches what happened live.

<Warning>
  **A permission card halts the run — unless a standing approval already covers that write.** A write covered by a live standing grant commits with no card and no pause. That is the point of granting one, and it is worth understanding before you do.
</Warning>

### Standing approvals

Granting "Always … in this chat" binds the approval to a specific *action* — the combination of the tool, the verb, and the kind of record it touches. Every later write of that same action in that chat commits without a card. A *different* action — a different verb, a different record type — is gated afresh.

A standing approval is always visible and always reversible while it is live: the composer shows a chip reading **&lt;action&gt; in this chat · Active until Jul 7**, and its inline control is **turn off**. Turn it off and the very next equivalent write asks again.

Some limits are deliberate:

- **Deletes never offer the chat scope.** An irreversible delete is confirmed every single time, whatever else you have granted.
- **Saving an [Agent Profile](/concepts/agent-profile) is never covered either.** Authoring a profile replaces the picture every later evaluation reads, so it is confirmed each time.
- **Bulk edits to existing requirements stay gated.** Saving a *new* requirement can ride a standing grant; changing or removing ones already filed cannot, even when they arrive inside a batch that is otherwise covered.
- **Starting an [Automatic Full Run](/how-to/run-an-automatic-full-run) is never covered.** An unattended run spends real credits driving live conversations against your connected agent with nobody watching, so it is confirmed every time.
- **A one-time approval still covers the batch the card represented.** If the card asked about saving twelve scenarios, approving once commits all twelve in that turn rather than stalling on the second one — but that coverage ends with the turn.

### Connecting an agent from inside the chat

The connect-agent card is a secure credential gate, not a chat message. Whatever you type into it — an API key, a consumer secret, a private key — is **write-only**: it is held in the browser, posted straight to the connections service, and never echoed back. It never enters the transcript and it **never reaches the model**. The card's result carries only the outcome: whether it connected, the agent and environment names, and the connection's health.

If your workspace has already connected the same Salesforce org in another project, the card offers to **reuse** that connection — cloning it into this project so it points at the same already-provisioned org, with no admin authorization and no re-provisioning.

When a connection is provisioned by admin authorization, its secrets stay server-side, so agent discovery runs there too: a follow-up **choose-agent card** refreshes the saved connection's agent list and lets you pick your agent **by name**, in the chat, without reconnecting.

The full approval flow — the card types, the rich previews, and what "approve and execute" actually does to your data — is the subject of its own guide: [Approve an agent write](/how-to/approve-agent-writes).

## The composer, modes, and skills

The composer is where you drive the agent, and it's rich: an **Attach files** chip for pulling in documents, an **@** picker for mentions, a **/** palette for slash commands and skills, an inline model chip, a **Thinking** chip for how hard the agent works before it answers, an **Ask** / **Plan** / **Act** mode toggle, and a plan-confirm bar. While a turn is genuinely running, a **Stop** control appears centred above the input. It's also forgiving: the textarea auto-grows as you type, an unsent draft survives navigating away — even leaving the project or reloading — and a message you send while the agent is mid-reply is queued for the next turn, not dropped.

Where those controls sit depends on the shell. The full view has room to show them all in one row. The **docked panel** does not, so mode, model and **Thinking** collapse behind a single composer settings menu there — attach stays out in the open, because burying an upload is how attachments stop being found. The new-chat launcher carries mode, model and **Thinking** as well, so the first message of a conversation starts on the settings you meant.

### Attach files

The **Attach files** (+) chip accepts document and text files — PDF, Markdown, plain text, CSV, JSON, and Word (`.docx`). Attached files are handed to the agent with the run so it can actually read them, and they persist in the side rail's **Attachments** section with an in-place preview. Attach is disabled until the conversation has a first message — the chip's tooltip says **Send a message first to attach files**. The launcher's own attach chip is never greyed, because that surface is the one that creates the conversation.

<Note>
  **Three things are called attachments; keep them apart.** The Trust Agent's **Attach files** chip takes documents, and the picker greys out a `.png` because the agent's composer is not wired for images at all. The rail's **Attachments** panel is where those documents live afterwards. A **picture** — an image inside a conversation with the agent under test — is a third thing entirely: it belongs to the [Playground](/concepts/playground) and the session transcript, where the composer control reads **Attach images**.
</Note>

### Stopping a turn

**Stop** appears centred above the input whenever a turn is genuinely in flight, and only then. It never shows while a question or permission card owns the composer slot — nothing is running there to stop; the agent is waiting on you. One click ends the turn: the partial reply is kept rather than thrown away, and the run stops instead of grinding on.

Stopping is not a failure and raises no error card. What you get back is the calm cut-short note described above — **This reply was interrupted.** with **Continue** — the same one a dropped connection leaves.

### Ask, Plan, Act

The mode toggle picks how the agent works. The labels are human — **Ask**, **Plan**, **Act** — never raw wire tokens:

| Mode | What it does |
|---|---|
| **Ask** | Clarifies real ambiguity first, then asks for approval before each write — the most cautious mode. |
| **Plan** | Researches and proposes a task list for you to confirm. No writes happen at all; the mode cannot even raise an approval card. |
| **Act** | Plans and executes end-to-end without stopping for optional clarification — but still asks for approval before every write. |

<Warning>
  **Act does not skip approvals.** What Act drops is the optional back-and-forth: it decides, plans, and works through the steps without pausing to check in. Every mutating write still stops at an approval card and waits for you — unless you granted that action a standing approval in this chat.

  The mode toggle's own subtitle currently reads "plans and executes end to end without pausing for approval." That copy is stale. The runtime is the authority, and the runtime waits.
</Warning>

In **Plan** mode the agent refines the *existing* plan instead of throwing it away and starting over. When a plan is ready and the run is idle, a confirm bar appears above the composer reading **Plan ready · *N* steps** with an **Approve & run** button (labelled *switches to Act*) — one tap moves the conversation from planning to execution. Typing a go-ahead in the composer takes the identical path; the button is just the faster way to say it.

### Clarify-first

Underneath the modes, the runtime enforces two gates. On a request that is genuinely ambiguous about *which* records to act on or *how* to scope the work, the agent's first move is a clarifying-question card with the real candidates as choices — not a prose "which one did you mean?". And planning stops for your confirmation before any write executes. The agent would rather ask than guess.

### Next-step chips

After a reply the agent offers **one** next-step chip at most — a single follow-up in plain English, like **Build a refund evaluator** or **Show SCN-000008 detail**. One, not a menu: the cap is enforced on both sides of the wire, deliberately, because a row of three competing suggestions is a row people stop reading. Clicking a chip pre-fills the composer with a ready-to-send prompt; it never sends on its own. You always get the last look before anything runs.

On a project that has done nothing at all — no sessions, no scenarios, no evaluators, no runs — the row leads with a standing **Show me where to start** chip instead. It pre-fills a question about where the project is up to, and the agent answers it by reading the project's real state (see [The workflow the agent enforces](#the-workflow-the-agent-enforces)). The chip disappears the moment any real work exists, because a "where do I start" prompt on a project mid-flight is noise.

### The model, and how hard it thinks

Two chips sit side by side in the control row, and they are coupled: the second offers only what the first supports.

The **model** chip picks which model the conversation runs on. It is a price-performance control — its hover says so, *Model — the price and quality the Trust Agent runs at* — and each row in the menu names a model with its vendor and a one-word posture underneath it, *frontier*, *balanced* or *fast*. What is in that menu is the Claude models your workspace offers: the catalog is served by the back end and a deployment can narrow it, so read the menu rather than any list written down elsewhere. Your choice takes effect on the next message and the conversation carries on. The menu deliberately shows **no cost or latency figure** — you choose how much horsepower a conversation gets, not a billing readout in the middle of your work.

The **Thinking** chip sets how much the agent works through a problem before answering, one message at a time. Four depths ship, each with its own plain sentence:

| Depth | What it does |
|---|---|
| **Standard** | Answers straight away. Fastest and cheapest. |
| **Brief** | Thinks a little before answering. |
| **Balanced** | Works through the problem before answering. |
| **Thorough** | Thinks hardest. Slower, best for complex work. |

**Balanced** is the default on every model that offers a choice, so an ordinary turn already thinks before it answers. The chip shows only the depths the selected model declares, and it disappears entirely for a model that declares one — a control with a single option is a control that does nothing. Switching models resets the depth to the new model's default. Inside a conversation the menu closes with **Applies from your next message. It never changes a reply you already have.**; on the new-chat launcher it reads **Applies to this conversation, starting with your first message.** instead, because there is no earlier reply to protect.

<Warning>
  **A depth is that model's own scale, not a shared ladder.** **Thorough** on one model and **Thorough** on another are not the same amount of thinking and do not cost the same. Compare a depth against the same model, never across two.
</Warning>

### Skills

Skills are first-class: reusable recipes the agent can run on demand, backing the **/** palette and surfacing in the transcript as [skill receipts](#the-streaming-transcript). Skills are workspace-scoped, and they come in two kinds.

<Tabs>
  <Tab title="Built-in skills">
    The recipes that ship with the product — connecting an agent, exploring it, generating scenarios, building an evaluator, running an evaluation, authoring security coverage, analyzing failures, and more. One of them, **/autorun**, does the whole arc in a single approved pass: see [Run an Automatic Full Run](/how-to/run-an-automatic-full-run). In the skills editor each is marked **Built-in**.

    **Built-in skills are read-only.** Open one and you can read the whole recipe, but every field is disabled, there is no Delete, and there is no Save. Their slugs are reserved on the server as well, so a workspace skill can never shadow or override one. What you can always do is *run* them, from the **/** palette or by asking.
  </Tab>
  <Tab title="Workspace skills">
    The recipes your team writes. **+ New skill** creates one; selecting an existing workspace skill opens it pre-filled for editing, with Save and Delete available, and the **/** palette refreshes as you change it. In the transcript a workspace skill's receipt carries the **Workspace skill** chip.
  </Tab>
</Tabs>

Creating, editing, enabling and disabling the ones your team owns is its own recipe: [Manage Trust Agent skills](/how-to/manage-trust-agent-skills).

An **@**-mention is pre-loaded and grounded: mention a known entity and it's handed to the agent directly, so the agent skips a redundant search to go find it.

The tools the agent drives inside the product are also published over a standard protocol, so an agent *outside* TrustAI — the assistant in your editor, a job in your pipeline — can do the same work without this chat surface: see [MCP integration](/concepts/mcp-integration).

## Grounding: what the agent knows before it writes

Three guardrails keep authored coverage tied to evidence, and to the right order, rather than to the model's imagination.

**The connected agent's profile is pinned per session.** At a conversation's first run, one [Agent Profile](/concepts/agent-profile) revision is resolved for the project's connected agent and pinned to that session. Every later turn — including a resume after an approval — reads that same snapshot, so a profile refresh landing mid-conversation never changes what the agent has already been reasoning from. The profile is injected as hidden context, never as a transcript message: you won't see it in the conversation, and it carries only the profile's humanised facts — no identifiers, no secrets. Where there is no captured profile, the agent is told so explicitly rather than handed an invented one.

**Expected output is gated on having read the real data.** Before the agent can save a scenario's expected end-state records, it must first have read that scenario's own records — or the project's connected data store — in this session. It is a runtime gate, not a prompt suggestion: an ungrounded write is refused, and the refusal names the store you have to go read first, rather than quietly committing.

Know the gate's one deliberate limit: it fires only when a store can be **positively confirmed**. A project with no connected data store, or one whose store is momentarily unreachable, is not blocked — the gate never fails a write over evidence it cannot see. So treat it as a guard against inventing an end state next to real data, not as proof that every expected record was checked against a store. The rule it protects is simple: a scenario states the objective, never the procedure. Expected records come from recorded evidence of the connected agent, not from memory.

**Each authoring step is gated on the one before it.** This is the runtime, not the prompt: generating scenarios, saving an evaluator, setting expected output, setting test data, simulating and running are each refused until the earlier artifact actually exists, and several tools refuse outright until an agent is connected. The refusal comes back as something the agent can act on — it names the missing step and offers to take you through it — which is why the agent will sometimes route you *backwards* from what you asked for. The steps themselves are in [the workflow below](#the-workflow-the-agent-enforces).

The agent can also read the connected agent's own definition straight from its platform — system prompt, model, tools, MCP servers, and skills — as a metadata-only read that starts no conversation. It's the fastest way for the agent to learn what it is testing, and where a platform exposes no definition, it says so and falls back to watching a conversation. What it learns is written back as a reviewable Agent Profile revision, not as chat text.

## The workflow the agent enforces

The Trust Agent doesn't wait for you to know what to ask — and it doesn't let the steps happen out of order. Underneath the conversation sits a router that reads the project's real state on **every** turn, never a position it remembered from earlier in the chat, names the single next step, hands over to exactly one recipe for it, and then checks the artifact actually landed before it moves on.

The core workflow is six steps. Each one is finished when the project *has* something, and it is something you can go and see for yourself:

| # | Step | Finished when the project has |
|---|---|---|
| 1 | Connect the agent | A usable agent connected to the project |
| 2 | Capture requirements | At least one saved [requirement](/concepts/requirements) stating what to test |
| 3 | Generate scenarios | Scenarios written, each linked to the requirement it covers |
| 4 | Build evaluators | One evaluator per requirement, attached to that requirement's scenarios and linked back to it |
| 5 | Fill in expected output and test data | The applicable expected actions, routes and test data saved on each scenario |
| 6 | Run the evaluation | A prepared evaluation run against the connected agent |

<Warning>
  **Step 2 is a gate, not a nudge.** Ask the agent to generate scenarios before a single requirement is saved and it refuses — **Draft and save the requirements first. I can guide you through that now before we continue.** — and routes you into capturing them instead. The later steps chain the same way: setting expected output, setting test data, simulating and running all refuse until each requirement has an evaluator created **and** attached to its scenarios. A plan that skips requirements dead-ends. [Capture requirements](/how-to/capture-requirements) is the recipe for that step.
</Warning>

Exploring the agent, shaping personas, adding adversarial security coverage aligned to the OWASP Agentic Top 10 (2026), and curating scenarios are all **enrichment**. The agent offers them where they add something, and they can make a step stronger — but none of them blocks a step, replaces one, or is a reason to skip one.

**"Show me where to start" picks up wherever you actually are.** It is not a tutorial that restarts. The agent says what the project already has, in one plain sentence, before it says what to do next — so coming back after a week lands you on the next real step rather than at the top, and work you did in the UI between chats counts. Everything it reports is state you can check yourself in the project's own tabs.

When the agent generates test coverage, it creates flat, persona-and-goal [scenarios](/concepts/scenarios) — no transcripts yet — and simulation happens later, at evaluation time, when fresh conversations are played out per persona against the pinned agent version. Generated scenarios land directly in your project's one flat Scenarios list — there is no intermediate collection to manage.

## How the Trust Agent runs

You don't need to know the plumbing to use the agent, but a little context helps. The Trust Agent runs on one unconditional streaming runtime: the front end consumes a streaming event protocol, and the back end emits those events from the agent loop, with the model streaming over an OpenAI-compatible path. The agent's markdown is rendered **in your browser**, from the streamed text, through a sanitizing pipeline — nothing arrives as pre-built HTML. This is the single runtime on every project; there's no second implementation behind a flag.

This is the seam where latency lives, and it's worth being precise about it: any wait you feel is the **upstream model's thinking time**, surfaced honestly by the Thinking timer and a working indicator. It is not a runtime timer, not an SLA, and not a bug. How long it takes depends on the model you selected, the depth you asked for, and the infrastructure it runs on — which is exactly why the agent shows a live timer while you wait and an [**Answered in …** breakdown](#where-the-reply’s-time-went) afterwards, instead of promising a number.

### What a turn costs

A Trust Agent turn is charged for what it **consumed**, not at a flat rate per message: the charge comes from the turn's real token usage. So a short question bills a fraction of a credit, a long turn that thought hard and called several tools bills more, and choosing a deeper **Thinking** level costs more than a shallow one on the same model. A turn that produced no reply at all — no prose, no tool call — is not charged; a turn that failed *after* it had already produced something is. Where the credits went has its own surface: see [Track credit usage](/how-to/track-credit-usage).

<Note>
  The internal routes and runtime details behind the Trust Agent are implementation, not a public API. There is no agent-runtime endpoint to call directly — you drive the agent through the app.
</Note>

### When something goes wrong

Four distinct states, four distinct surfaces — the agent never papers one over as another:

| What you see | What happened |
|---|---|
| **The Trust Agent hit an unexpected error and stopped. Please try again.** | The turn itself failed, and the server said so. |
| **The Trust Agent couldn't finish this reply. Please check your connection and try again.** | The request never got as far as a verdict — a dropped network, a response that never streamed. |
| **This reply was interrupted.** with **Continue** | The reply was cut short: either the connection dropped mid-stream, or you stopped the turn yourself. Continue resumes from the saved context. |
| **Couldn't load this conversation** with **Retry** | The chat history could not be read. The conversation is not lost; the read failed. |

The first two paint the same card where the reply would have been, and it is not a dead end. The card carries one plain sentence — never a raw error — the hint **You can try again, or pick a different model first.**, the same model chip the composer carries, and a **Try again** button that re-runs the turn on whatever model is selected when you press it. Switch first if you think the model was the problem.

That card belongs to the live session. Reopen a chat that failed earlier and you get the stored transcript, not the notice.

## Security and scope

Write execution is **tenant-scoped and server-anchored**. An approved write executes only within your own organization and project, and execution is bound to the specific approval the server itself raised — a decision the browser claims but the server never issued is ignored, and the write only previews. The agent cannot act on another organization's data. The platform side of that boundary lives in [Multi-tenancy](/concepts/multi-tenancy).

Tool permissions are a workspace **restriction** model, not an allowlist, and the difference matters:

- **The default is allow-all.** A tool with no permission rule is available. A workspace that never opens the admin surface gets every tool the Trust Agent offers it.
- **A workspace opts a tool *out*** — disabling it, or restricting it to a role — from Workspace Settings.
- **A restriction is enforced twice.** A restricted tool is dropped before the agent's tool surface is built, so the model never learns it exists, and it is re-checked at call time so a stale or replayed call still fails closed.

<Note>
  Read that as written: the Trust Agent's tool surface is open by default and narrowed deliberately. If a tool should be unavailable to your team, someone has to turn it off.
</Note>

The Trust Agent surface is designed to meet WCAG AA contrast, and the interrupt cards are reachable by keyboard and screen reader, not only by mouse.
