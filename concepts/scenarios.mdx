A **scenario** is one test case worth scoring your agent on: a name, the goal a simulated user is trying to accomplish, the personas who pursue it, and an authored **expected output** — the grading contract that says what a passing conversation looks like. Every project has one flat **Scenarios** list, and each scenario carries a stable, reader-visible id like `SCN-000123`. You define a scenario cheaply, run it to simulate real conversations, and learn its expected output from a session you like — that loop is the heart of evaluating an agent in Trust AI.

<Note>
  **Formerly Datasets.** Earlier releases organized test cases as rows inside collections. As of v2026.06.30.1 those collections are gone: there is one flat Scenarios list per project, each scenario is a first-class entity, and the conversations it produces are real [Sessions](/concepts/sessions) linked back to it. The surface lives at `/projects/:id/scenarios`; the old `/projects/:id/datasets` address redirects there, so stale bookmarks still land in the right place.
</Note>

<Note>
  **Scenarios is not the Trust Agent, and not an Agent Version.** All three use the word "agent" nearby, so it is worth pinning them apart:

  - **Scenarios** (this page) are the *test cases* you score an agent against.
  - The **[Trust Agent](/concepts/trust-agent)** is your in-app *assistant* — the thing that helps you create scenarios, draft evaluators, and run evaluations.
  - An **[Agent Version](/concepts/agent-versions)** is the *agent under test* — the pinned build of the customer's agent whose behavior you are judging. (The pin is by reference, not a frozen copy: a version can be renamed, and past runs then show the new label.)

  You score an Agent Version against your scenarios, and the Trust Agent can help you do it. None of the three is the same thing.
</Note>

## What's in a scenario

- **A name and a stable id** — the id renders as `SCN-000123` everywhere, so a scenario keeps the same handle in results, links, and conversations with teammates.
- **A user goal** — what the simulated user is trying to accomplish ("Get a refund for a duplicate charge"). The goal drives the simulation; a scenario with a goal and no persona still simulates.
- **Personas** (optional) — reusable, project-scoped actors that role-play the user. Attach more than one and a run produces one session per persona (see [Personas](#personas)).
- **Expected output** — the authored grading contract: expected behavior, expected actions, and expected routes (see [Expected output](#expected-output-the-grading-contract)).
- **Files the simulated user can send** (optional) — pictures the simulated customer can hand the agent mid-conversation, each with a description under **What each file shows**. The agent under test receives the real file; the simulated user never sees it, and decides from your description alone when — or whether — to send one.
- **Test data** (optional) — a plan describing the records this test needs and what happens to them afterwards (see [Test Data](#test-data-the-plan-a-scenario-runs-on)).
- **Tags** — drawn from one shared project vocabulary, so the same tag autocompletes on Scenarios and Sessions alike.
- **Linked sessions** — the real conversations this scenario has produced, listed on the scenario itself.

## The Scenarios list

Open **Scenarios** in the left nav to get the flat table, newest first: an **ID** column with the `SCN` handle, the scenario name, the **User Goal**, **Personas** as removable pills, **Expected routes** and **Expected actions** chips, attached **Evaluators**, a **Verdict** column, and a **Sessions** count. Name, goal, personas, evaluators, and Verdict are all editable inline — click the cell, change it, done. The table and fly-in behaviors shared across list surfaces are described in [Tables and panels](/concepts/tables-and-panels).

### The Verdict column

**Verdict** is a Pass / Fail toggle you set yourself, on the scenario. It is not an evaluation result and no judge writes to it — it's your judgment of whether this test case is one the agent should be passing.

It exists for one specific job: **calibration**. The Calibrate tab in an Evaluator's panel compares that judge against your scenario verdicts on the same material, and it has nothing to sample until some scenarios are marked. If you have wondered where to record the labels a calibration run needs, this column is the answer — not the Verdict [annotation](/concepts/annotations) on Sessions, which feeds the separate evaluator-accuracy figure on run results.

### Every Run affordance opens the launcher

**Run** doesn't start anything on its own. Whichever way you reach it — the header's **Run** split-button, the bulk-actions bar after selecting scenarios, or **Run & evaluate** in a fly-in — you land in the shared **Evaluation launcher** modal first. You confirm what to evaluate, which agent version to run against, and how many times to **Repeat each test case**; nothing is enqueued until you launch from inside it.

What happens next depends on what you launched:

| Launch | Where you end up |
|---|---|
| **Run only** (simulate, no grading) | Stays on the Scenarios list, live in-flight badges settling as each finishes |
| A **quick evaluation** from a session fly-in | Stays put — the fly-in reports the verdict, and the graded conversation also lands on the Evaluations list |
| **Run & evaluate** | Navigates to the new run's detail page |

So "stay on the list and watch the badges" is the ungraded story. A graded run takes you to its results, because that's where the grading it just produced lives.

A **quick evaluation** grades one session in place from its own fly-in, and it is visible well beyond that fly-in. It announces itself with a **Quick evaluation started** toast, reports progress as **Scoring check 2 of 3…** while the judges land, and finishes with a **Quick evaluation finished** toast carrying a **View** action. Its row on the Evaluations list wears a muted **Quick** pill and opens the conversation it graded rather than a run-detail page, because it mints no run record — which is also why that row carries no Cancel and no Delete. For the full recipe, see [Evaluate captured sessions](/how-to/evaluate-sessions).

When a targeted scenario carries a test data plan or structured starting records, the launcher states what the run will write into the connected store: a line beneath **This will run** counting the records it creates and the read-backs it performs, closing with the cleanup promise **"Removes only the records each test created."** That line appears from every **Run** affordance, not just the one with its own scenario picker.

Runs ride out model-capacity throttling with automatic retry, and a capacity hiccup is excluded from quality metrics — it never masquerades as a drop in agent quality.

## The scenario fly-in

Click a scenario to open a two-level fly-in over the list. The first level is the scenario itself, with workflow-ordered tabs:

- **Personas & Goals** — edit who pursues the goal and what the goal is, and attach the **Files the simulated user can send** so the simulated customer has something to hand over mid-conversation.
- **Expected Output** — the grading contract editor (next section).
- **Test Data** — the environment this scenario runs against and the plan it runs on (below).
- **Sessions** — every conversation this scenario has produced, with a live count in the tab label. Click a session to stack a second-level panel over the first with that session's transcript, annotations, and evaluations — you drill in without ever losing your place in the list.

The panel's **More** menu carries **Run & evaluate**, **Run only**, and **Delete scenario**.

### Test Data — the plan a scenario runs on

The **Test Data** tab answers a different question from Expected Output. Expected Output is the *agent behavior* contract; Test Data is about the records a test needs and what becomes of them afterwards.

It opens with the environment, because that part is settled for you: the tab names the connection selected for the agent you're testing, marks it **Always used**, and states the promise — Trust AI acquires, runs, resets, and releases that environment every time.

Below the environment sits the scenario's **plan**: one reviewable description of the test-data work, rendered as five expandable step cards whose titles are full sentences — **"Create what this test needs"**, **"Run the conversation"**, **"Read back what the agent created"**, **"Check what should happen"**, and **"Clean up everything this test created"**. A scenario with no plan shows a **No test data yet** hero instead, offering **Add manually** and — where the connection supports drafting — **Set up with AI**. Those two, and **Edit plan** once a plan exists, all open the same docked drawer, whose tabs are **AI**, **Form**, and **JSON**. A drafted proposal is always yours to read before it replaces what is stored.

Two things sit beside the plan rather than inside it. **How this test runs** is its own accordion and describes the run, not the records: whether this scenario **Runs alongside other tests (recommended)** or **Runs alone**. **Advanced test data** keeps the record-level controls — structured starting records, expected-state records, and file import — for the cases that need them.

Cleanup is not optional and no surface offers to switch it off. The plan's clean-up card states its own scope: **"Removes the records this test created and tagged for the run — seeded records included."**

The tab only offers what your connector actually supports, so you won't find a control here that can't do anything.

## Expected output — the grading contract

The keystone of a scenario is its **Expected Output** tab: the place you author what a passing conversation looks like. The editor has three sections:

- **Expected behavior** — LLM-judge [evaluator](/concepts/evaluators) cards that grade qualities like tone, scope, or safety. The picker surfaces the evaluators best suited to this scenario first, under **Recommended for this scenario**, ahead of the full catalog.
- **Expected actions** — the tools the agent must (or must not) use, with per-action parameter checks. Add one with **Add action**.
- **Expected routes** — where the conversation should be routed. Add one with **Add route**.

The add-menus lead with **vocabulary the product learned from your real sessions** — the actions and routes your agent has actually used, each with a "seen in N sessions" hint — so the easy path grounds the contract in observed behavior rather than guesses.

That list is an assist, not a gate. Type a name that hasn't been observed and the menu offers to add it anyway (**Add "…"**), which is how you assert on behavior the agent *should* have but hasn't yet exhibited. Before any sessions exist, the menus are honestly empty and say so — the intended order is define something cheap, run it, then tighten the contract against what you actually saw.

This is why the recommended order is to define the scenario cheaply first and author expected output *after* you have sessions: run the scenario, read the conversations, find one that went the way you want, and write the contract from what you see. The **Missing expected output** saved view keeps track of the scenarios still waiting for that step.

## Running a scenario

Running a scenario simulates one session per attached persona — each persona genuinely pursues the goal against the agent under test. There are two run modes, both available from the list's **Run** split-button, the fly-in's **More** menu, and the empty Sessions tab:

- **Run & evaluate** — simulate and grade. Creates an evaluation whose results land in [Evaluations](/concepts/evaluations), scored per persona under one headline stat — **Conversations passed**, captioned with the conversation set it was measured over.
- **Run only** — simulate without grading. You get the sessions to read, and no run appears in the Evaluations list. This is the cheap way to produce the raw material for expected output.

The split-button's primary **Run** action is the default graded run; the chevron offers the explicit choice.

Every conversation a run produces is a **real Session**, linked back to its scenario. It appears on the scenario's Sessions tab and on the [Sessions](/concepts/sessions) surface, carrying a **Source** chip that reads **Scenario** and a **Simulated from** provenance card pointing back at the scenario that produced it. Nothing is throwaway: you can read, annotate, and re-grade these sessions like any other.

### How a simulated conversation ends

A simulated conversation closes by saying why it stopped. The line begins **"This conversation ended because "** and finishes with one of: *the customer got what they needed*, *the agent could not help with it*, *the customer gave up*, *the agent ended or transferred it*, or *it reached the length limit before finishing*. Where the simulated customer explained the decision itself, its own words are carried through verbatim.

Read it as evidence, not as a verdict — two transcripts of the same length can stop for opposite reasons, and this is the line that tells them apart. A conversation with no recorded ending renders nothing at all, so an absent line means the record doesn't say, not that the outcome is unknown.

Grading has one more state worth knowing here. When an action the agent itself runs returns an error, the conversation is not scored a pass or a fail: it reads amber as **Couldn't test** and leaves the pass-rate denominator, summarized as **"Not scored because an action the agent runs returned an error."** A run that hit them shows an amber count beside its pass rate, so a green rate never renders uncaveated.

### The define → run → learn loop

Putting the pieces together, the opinionated workflow is:

<Steps>
  <Step title="Define cheap">
    Create the scenario with just a name, a goal, and personas. Skip expected output — the create modal tells you so: you'll set it later, usually from a session you like.
  </Step>
  <Step title="Run">
    **Run only** to simulate one session per persona without grading.
  </Step>
  <Step title="Learn from a good session">
    Read the sessions on the scenario's Sessions tab. When one goes the way you want, open **Expected Output** and author the contract from the actions and routes you just watched.
  </Step>
  <Step title="Run &amp; evaluate">
    From now on, graded runs score the agent against the contract — and every [Agent Version](/concepts/agent-versions) can be held to the same standard.
  </Step>
</Steps>

For the step-by-step recipe, see [Simulate with scenarios](/how-to/simulate-with-scenarios).

## Where scenarios come from

- **New scenario** — the header button opens a short form: name, goal, personas. Expected output is deliberately deferred.
- **Save as a scenario** from the [Playground](/concepts/playground) — an exploratory conversation you liked becomes a scenario with that conversation attached as its first linked session.
- **Add recommended scenarios** — a starter catalog of ten adversarial probes, one per OWASP Agentic Top 10 failure mode. Adoption arrives graded: the safety checks that score each probe are created once and attached to the scenario as it lands, so a run grades it without you picking judges. The confirm step offers **Add without tailoring** or **Add & tailor to your agent**, which hands the batch to the [Trust Agent](/concepts/trust-agent) to customize each check against your connected agent's real tools and rules in the background. A catalog probe carries a name, a goal, its category, and that prose guidance — never expected actions, test data, or reference material, so it is still yours to ground in your own data. See [Recommended scenarios](/concepts/trust-library) and [Adopt the recommended security scenarios](/how-to/adopt-recommended-security-scenarios).
- **Ask the [Trust Agent](/concepts/trust-agent)** — describe the behavior you want covered and let the assistant draft scenarios for you; it pauses for your approval before it writes anything.

Note that **Source** on a session is a different idea from where a *scenario* came from: a session's Source chip is exactly one of **Scenario**, **Playground**, or **External**, and records how that conversation entered the system.

## Personas

A **persona** is a reusable, project-scoped actor that role-plays the user — a character with the traits and constraints that shape how it pursues a goal. Personas are shared across the project, so the same actor can drive many scenarios, and they always render by name.

Open **Manage personas** in the Scenarios page header to list, create, edit, and delete them in place. Personas live at the project level; the project's default persona is protected and can't be deleted.

Attach several personas to one scenario to test the same goal from different angles — an impatient customer, a confused first-timer, an adversarial probe. Each run scores every persona on its own, so the results tell you *which kind of user* your agent fails, not just whether it fails.

## Deleting a scenario

Delete is safe by design, with three outcomes:

- **Blocked** — a scenario referenced by evaluations can't be deleted; you'll see "Can't delete: used in N evaluations." instead of a confirm.
- **Confirm with disclosure** — if the scenario has produced sessions, the confirm names exactly what survives and what doesn't: *"Those sessions are kept (they retain a frozen snapshot); only the link is removed. Deleting also removes this scenario's expected-output rubric and test data."* Both the rubric **and** the test data go with the scenario.
- **Instant** — a scenario with no evaluations and no sessions deletes immediately.

Because sessions are frozen snapshots and evaluations pin what they scored, deleting or editing a scenario never rewrites history: past results stay exactly as they were recorded.

## API surface

Scenario reads and edits go through the `/v1/scenarios` family — list, get, update, delete (with a pre-delete check), the recommended starter catalog, and each scenario's expected output. That family is the whole surface: there is no `/v1/datasets` API. Full request and response shapes live in the [API Reference](/api-reference).
