A Saved View is a named, persisted combination of filters, sort order, and column layout for a list surface. Instead of re-applying the same filters every time you open Sessions or Scenarios, save the configuration once and return to it with a click. Views are stored server-side and shared across the project, so the whole team works from the same lenses.

## Why Saved Views exist

Teams develop recurring lenses on their data: "sessions from the last 24 hours," "scenarios missing expected output," "the failed results in this run." Without Saved Views, each team member rebuilds those filters by hand every time. A Saved View captures the configuration once so the whole project works from the same lens.

## Which surfaces have them

Not every list has Saved Views, and the ones that do don't all offer the same controls. This is the map:

| Surface | Filters | Column control | Saved Views |
|---|---|---|---|
| [Sessions](/concepts/sessions) | Yes | Yes | Yes |
| [Scenarios](/concepts/scenarios) | Yes | Yes | Yes |
| [Requirements](/concepts/requirements) | Fixed chips | Yes | Yes |
| A run's results | Yes | Yes | Yes — scoped to that run |
| The [Evaluations](/concepts/evaluations) run list | No | No | No |

Requirements is the newest list to carry Saved Views, and its filter slot is the one deliberate difference between the four surfaces that have them. Instead of a popover you build a query in, it carries three fixed chips — **All**, **Gaps**, and **Failing** — and those three are its entire filtering vocabulary. The chip you have selected is part of the view like any other filter, so a view saved on **Gaps** reopens on **Gaps**. Everything else is the standard kit: show, hide, reorder and resize columns, save a view, set one as your default, and open a requirement's fly-in full screen.

The Evaluations list is deliberately lighter: it offers a search box and sortable columns, and nothing else. There is no filter popover, no column menu, and no view picker on it. If you are looking for the place to save a lens over evaluation *results*, that's inside a run, not on the list of runs.

Views on a run's results belong to that run — open a different run and you get that run's views, not the ones you built elsewhere.

## What's in a Saved View

- **Filters** — which items to include
- **Sort order** — which column to sort by and in which direction
- **Column layout** — which columns are visible, their left-to-right order, and their widths. Each view remembers its own layout, so switching views restores the arrangement you saved.
- **The search box** — whatever you typed into the toolbar search is part of the view too. This surprises people: a view that looks "modified" when you expected it clean is often just a leftover search term.
- **Surface binding** — a view belongs to one surface and is never offered on another

## Built-in views

Every view is one of two kinds, and the difference decides what you're allowed to do with it.

**Built-in views** ship with the project so a list is never a blank slate:

| Surface | Built-in views |
| --- | --- |
| Sessions | **All sessions**, **Recent sessions** (last 24 hours) |
| Scenarios | **All scenarios**, **Missing expected output** |
| Requirements | **All requirements** |
| A run's results | **All results** |

Built-ins are read-only in the interface. While one is active the view picker offers no **Rename view**, no **Delete view**, and no **Set as default** — rather than showing you disabled buttons, the app leaves those three rows out and the menu ends at the list of views. Clicking **Save view** on a built-in falls through to **Save as new view**, so the shared starting points stay stable for everyone.

**User-created views** are the ones you make. They carry the full set: rename, delete, and set-as-default.

## Default views

Mark a view as your default and that surface opens with it pre-applied. Defaults are per-user and per-project — yours doesn't change anyone else's — and the picker marks the current one **Default**.

**Set as default** is offered on a user-created view that isn't already your default, and it drops out once it is. It is not offered while a built-in is active, so the picker gives you no way to make **All requirements** or **All sessions** your landing view. Save the arrangement you want as your own view and set that as the default instead.

## Views as run scopes

<Note>
  **Only the Sessions source takes a view.** In the evaluation launcher, choosing **Sessions** as what to evaluate gives you a view picker. Choosing **Scenarios** gives you a scenario picker instead — you select the scenarios individually, and no Scenarios view is consulted.
</Note>

For the Sessions branch, TrustAI resolves the view to its concrete session list on the server at launch time, so time-window filters anchor to the moment you launch: picking **Recent sessions** always means the last 24 hours as of *now*, and the same view yields a fresh set on every run.

If you were counting on a curated Scenarios view to scope a run, it won't — pick the scenarios in the launcher, or narrow the list first and select from it.

## In the app

- **View picker** — the toolbar dropdown lists the surface's views and switches between them. On a user-created view it also offers **Set as default**, **Rename view**, and **Delete view**; on a built-in, those three are absent.
- **Save view** — the toolbar's save button is always visible, and is disabled with an explanatory tooltip when there's nothing to save. Its adjacent chevron menu offers **Save as new view** and **Reset view** — and **Reset view** is itself disabled unless you're on a user-created view with unsaved changes.

Saved Views are managed from the toolbar of each list surface. Developers who need the underlying endpoint detail can find the Saved Views family in the [API Reference](/api-reference).
