An Annotation is a piece of **human judgment** attached to a [Session](/concepts/sessions). You record it in typed **annotation columns** on the Sessions surface — a pass/fail verdict, a severity, a score, tags, or a reviewer note — and it becomes data the rest of Trust AI can use. The human **Verdict** is the ground truth every [Evaluator](/concepts/evaluators) is measured against: it grades the judges.

Without Annotations, Evaluator scores are unaccountable — the app can tell you what its judges decided, but not how often those judges agree with a person.

## The annotation column model

Annotations live in a project-wide schema of typed columns. Each column holds one value per Session, and every project starts with three seeded columns:

- **Verdict** — a Pass / Fail judgment of the whole Session. This is the human ground-truth channel that evaluator accuracy is measured against.
- **Severity** — a single choice among **minor**, **major**, and **blocker**.
- **Reviewer note** — a free-text comment.

You add your own columns from the Sessions table's add-column menu with **New annotation column**. Five types are available:

| Type | Holds |
|---|---|
| **Pass / Fail** | A binary verdict |
| **Score** | A numeric rating (1–5) |
| **Category** | A single choice from options you define |
| **Tags** | Multiple tags from a palette |
| **Comment** | A free-text note |

A column's **name is editable; its type is not.** Once values exist, changing a column's type would silently invalidate every value already written against it, so the app doesn't allow it — for any column, not just the seeded three. If you need a different type, delete the column and create a new one.

Session annotations are **whole-conversation**: each value judges the Session as a unit. There is no per-Turn annotation — if a specific exchange is what matters, say so in a **Reviewer note** or a **Comment** column.

## Two levels of human verdict

Human judgment is recorded at **two** levels, and they are separate records with separate consumers. This trips people up, so it's worth being precise:

| | Session verdict | Scenario verdict |
|---|---|---|
| **Where you set it** | The Verdict annotation column on [Sessions](/concepts/sessions) — inline or in the fly-in | The **Verdict** column on the [Scenarios](/concepts/scenarios) list, visible by default |
| **What it judges** | One captured conversation | One test case |
| **What reads it** | **Evaluator accuracy** on evaluation results | **Calibration** in the Evaluator panel's Calibrate tab |

The consequence worth internalising: **calibrating a judge does not read your Session verdicts.** The Calibrate tab grounds on scenario pass/fail verdicts, and says so in its own empty state — *"Add a pass/fail column to your scenarios and mark some rows."* Annotating a hundred Sessions will move the evaluator-accuracy number and leave the Calibrate tab empty.

## Where you annotate

Annotation happens where the Sessions already are — there is no separate review surface:

- **Inline in the Sessions table.** **Verdict** and **Severity** cells are editable directly in the table, so a reviewer can sweep down the list without opening anything. The Verdict column shows by default; other annotation columns can be shown from the column menu.
- **In the Session fly-in.** The fly-in's **Annotations** tab is the full schema-driven editor for every column, alongside the **Transcript**, **Evaluations**, and **Details** tabs. The same panel appears when you drill into a session from a scenario. An edit made in a table cell repaints any open panel for that Session, so the two never disagree.

To work through Sessions in volume, filter the list to the slice you care about — the filter offers **Date**, **Routed To**, **Tags**, and **Turn count** — and save the configuration as a [saved view](/concepts/saved-views). To narrow by something outside that set, show the column and sort on it. Selecting multiple Sessions raises the bulk-actions bar (**Evaluate** · **Tag** · **Download**); **Tag** applies tags from a vocabulary shared across Scenarios and Sessions, with autocomplete.

## Two verdicts, one rule

A Session can carry two verdicts at once, and they never overwrite each other:

- The **automated verdict** — the pill produced by [Evaluations](/concepts/evaluations): **Pass**, **Fail**, **Not evaluated** (nothing ran), or **Not graded** (something ran but produced no behavioural score). Only automated results set it.
- The **human Verdict annotation** — your Pass / Fail judgment in the Verdict column.

The rule: **your Verdict annotation grades the judges — it never overwrites the automated verdict.** When a Session carries both, Trust AI compares them, and the agreement rate surfaces as the **Evaluator accuracy** headline on evaluation results. A Session where the two disagree is exactly the signal worth investigating: either the agent's behavior is subtle, or the Evaluator's rubric needs work.

### The one place human judgment does change a score

That rule is about the **Verdict annotation column**, not about human input generally. The [Groundedness judge](/concepts/evaluators) has a separate mechanism — **adjudication** — where a reviewer's call genuinely rewrites the automated result.

In a Groundedness report, each claim the agent made carries a judged verdict — **Supported**, **Contradicted**, **Unsupported**, **Unknown**, or **Conversational**. A reviewer can override one to any of those five, with an optional note, and **revert** puts the judge's verdict back. The claim counts, the **% grounded** figure, and the check's pass/fail then recompute, and the parent result's roll-up updates with them. The recompute is deterministic: no model re-runs, and the judge's original verdict is kept alongside yours so the report can still show what it had said.

<Note>
  Adjudication is a correction to a specific claim, not a global override. It exists because a claim-by-claim judgment is exactly the kind of thing a person can check faster than a model can — and it's scoped to Groundedness. Nowhere else does a human entry move an automated score.
</Note>

## Annotations vs Evaluator scores — different things, paired

Annotations and Evaluator scores are structurally similar — a judgment attached to a Session — but they come from different sources and answer different questions:

| | Annotation | Evaluator score |
|---|---|---|
| **Source** | Human reviewer | Any of the four evaluator kinds — LLM judge, Structured match, Outcome grounded, or Groundedness judge |
| **Question answered** | "Was this actually acceptable?" | "Does this pass the rubric, at scale?" |
| **Cost per Session** | Reviewer minutes | LLM tokens / compute |
| **When applied** | During review, any time after capture | At Evaluation time, programmatically |
| **Role** | Ground truth for evaluator accuracy | Sets the automated verdict |

The relationship is **calibration**: Evaluator scores earn trust to the degree they agree with a person on the same material. Which material depends on which surface you're looking at — the Calibrate tab on [Evaluators](/concepts/evaluators) uses your **scenario** verdicts, and the Evaluator accuracy figure on a run uses your **Session** verdicts.

## Workflows

The common annotation patterns:

  </Card>
  <Card title="Sweep the table" icon="table">

  <Card title="Bulk tag a slice" icon="tags">
    Filter to a slice, select all, hit **Tag**. Tags share one vocabulary across Scenarios and Sessions, so the same label works for filtering on both surfaces.

  <Card title="Add a review dimension" icon="sliders-horizontal">
    When pass/fail is too lossy, create a **Score** or **Category** column with **New annotation column** — "tone 1–5," "failure mode" — and grade the slice against it.

## What annotated data feeds

Annotations justify their cost downstream:

1. **Evaluator accuracy** — a human Verdict on an evaluated Session sharpens the judge-vs-human agreement number on evaluation results. This is the primary payoff: it tells you whether to trust the automated scores. One qualifier: the comparison uses the combined **LLM judge** verdict only — any judge failing counts as a fail — and structural scores are excluded, so annotating Sessions graded solely by a **Structured match** evaluator won't move the number.
2. **Evaluator calibration** — when accuracy is low, the disagreeing Sessions show you exactly where the rubric misjudges. Refine the Evaluator and re-run. To drive the Calibrate tab itself, mark verdicts on **scenarios**, not sessions.
3. **Review-driven evaluation** — filter to the Sessions your review flagged, select them, and hit **Evaluate** to grade them with your judges. Annotation is not a prerequisite: you can evaluate Sessions you haven't annotated at all.

All three close the loop described in [the evaluation loop](/concepts/evaluation-loop) — Annotations are what keep the automated half of that loop honest.

## Working with Annotations

Annotating is one of the few genuinely hands-on tasks in Trust AI — the judgment is the point, so no agent does it for you. You can ask the [Trust Agent](/concepts/trust-agent) to find the Sessions worth reviewing ("which sessions from this week have no verdict yet?"), then grade them yourself inline or in the fly-in.

For reading or writing annotation columns and values programmatically, the endpoint details live in the [API Reference](/api-reference).
