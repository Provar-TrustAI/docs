Trust AI runs a [Model Context Protocol](https://modelcontextprotocol.io) (MCP) server that publishes a small, fixed subset of the **Trust Agent's** tools — the same read and write operations the agent performs inside the product, reached over a standard protocol instead of a bespoke integration.

It is a second door onto those operations, not the door the product uses. The Trust Agent inside Trust AI dispatches its tools directly; the MCP server is a separate transport over the same implementations. What makes it worth explaining is that the transport is where the surface becomes explicit: a fixed allowlist, a declared shape per tool, an access check per call, and a trace for every invocation including the refused ones.

<Warning>
  **There is no supported way for you to point your own MCP client at Trust AI.** The server authenticates on a signed-in Trust AI session, and connecting an external client that way is an internal path only — not a customer integration. There is no MCP configuration surface anywhere in the product. Read this page as an explanation of how the Trust Agent's tools are governed, not as setup instructions.

  A customer-facing path would need issued, revocable **MCP tokens** in place of a session — that is a design direction, not something in this release. Earlier drafts of this page promised OAuth; no such work is planned.
</Warning>

## What MCP is

MCP is an open protocol that standardizes how AI applications discover and invoke tools exposed by external systems. A server publishes a tool surface; any client that speaks the protocol can discover the available tools and call them, with no custom SDK per client. For protocol details, see [modelcontextprotocol.io](https://modelcontextprotocol.io).

## The eight tools

The Trust Agent's own tool registry is much larger than what MCP publishes. The MCP surface is a deliberate allowlist of **eight** tools — four reads and four writes — and a build-time conformance test fails if the running server ever serves a tool that isn't on it.

**Read tools.** These run immediately; there is no approval step.

| Tool | What it does | Project role |
| --- | --- | --- |
| `trustai.get_project_state` | Summarizes a project: entity counts, setup flags, and the most recent evaluation run | Viewer |
| `trustai.query_data` | Lists and filters one entity type at a time, capped at 1,000 rows per call | Viewer |
| `trustai.read_file` | Returns the extracted text of a file attached to a Trust Agent task | Viewer |
| `trustai.analyze` | Runs a failure analysis over a completed evaluation run — a short note on each failure, then named themes. Takes 30–60 seconds | Viewer |

**Write tools.** Each one previews first and then waits for an explicit approval.

| Tool | What it does | Project role |
| --- | --- | --- |
| `trustai.save_dataset` | Curates conversations into the project's scenarios. The tool name is historical; what it writes is your **Scenarios** list | Editor |
| `trustai.update_items` | Updates one item, identified by an item type and an id | Editor |
| `trustai.delete_items` | Deletes a batch of items of one item type | Owner |
| `trustai.run_evaluation` | Starts an evaluation run over the project's scenarios with one evaluator | Editor |

There is **no session-sync tool** on this surface. Syncing conversations from a connected platform is not something MCP can trigger — earlier drafts of this page said otherwise and were wrong.

### What `query_data` accepts

`query_data` takes one `entity_type` per call and returns the same envelope — `items`, `total`, `notes` — whatever you ask for, so one renderer handles every type. It accepts **eight** types: `sessions`, `scenarios`, `datasets`, `evaluators`, `evaluations`, `personas`, `agent_versions`, and `requirements`.

A [`requirements`](/concepts/requirements) read returns each requirement together with its server-computed rollup — health, linked scenario and evaluator counts, pass rate, last evidence — rather than the raw record. A caller never derives a requirement's health itself; the read hands it over already computed, so two clients cannot disagree about it.

`datasets` is the odd one. The dataset container it was named for is retired; the type survives as an alias and returns exactly what `scenarios` returns — the project's flat Scenarios list. Prefer `scenarios`.

An unrecognized value doesn't fail silently or throw a server error: the tool returns a structured error listing every accepted type, so a calling agent can correct itself on the next turn.

## Who can call what

MCP is not a way around project access. Every tool resolves the caller's role on the target project through the same permission engine the rest of the product uses, and each tool asks for a **different** tier:

- **Reads need Viewer.** All four read tools authorize at the lowest project tier.
- **Most writes need Editor.** Curating scenarios, updating an item, and starting an evaluation are content writes.
- **Deletion needs Owner.** `delete_items` authorizes at the project's top tier, so a project Editor cannot delete through MCP even though they can create and update.

Two boundaries are worth stating plainly, because they are not what an older description of this surface implied:

- **A project in another workspace is denied, not adopted.** A caller whose session belongs to a different workspace than the project simply has no membership there and is refused. Nothing is moved or reconciled to make the call succeed.
- **An authorization outage denies.** If the permission check itself cannot complete, the call fails closed as a temporary, retryable failure rather than resolving to an allow.

A project that doesn't exist and a project you can't see return the same error. Existence is never leaked across workspaces — see [Multi-tenancy](/concepts/multi-tenancy).

## The approval gate

Every write goes through the same sequence, and it is the reason a write tool can be exposed at all:

1. **Preview.** The tool builds a structured description of exactly what would change and validates the request.
2. **Ask.** The call blocks on a pending approval while the calling agent surfaces the prompt to a person.
3. **Decide.** An approval runs the write and returns the result. A rejection returns a structured refusal.
4. **Expire.** An unanswered request **times out after five minutes** and the write never runs. The window is deliberately short because the caller holds an open connection for its whole duration.

Three details of that gate are easy to miss:

**Only one of the four writes can be dry-run.** `save_dataset` takes a `preview` flag, and it defaults to preview — call it plainly and you get the description of the change back with nothing written and nobody asked. The other three have no such flag: `update_items`, `delete_items`, and `run_evaluation` always build their preview and then always go to approval. There is no way to rehearse a delete.

**The decision arrives out of band.** The waiting call cannot prompt anyone itself, so the decision is posted on a separate request, which wakes it. Only the same signed-in user the call was issued under can decide it — one person cannot approve a write another person triggered, and an attempt to do so is indistinguishable from an unknown request. Endpoint shapes live in the [API Reference](/api-reference).

**Batch writes are checked per item kind, not per tool.** `update_items` and `delete_items` are polymorphic: the item type is an argument, and there are exactly two — `dataset_row`, which edits a scenario in your **Scenarios** list, and `requirement`. A `requirement` item is a requirement write, so it is checked against the same workspace tool permission the dedicated requirement tools carry: the batch shape is never a way around a restriction an admin has set on those tools. Deleting a requirement follows the same rule the rest of the product does — a draft is removed, an active one is archived and keeps its history. An unknown item type comes back as a structured error listing the accepted set.

The same approval pattern applies when you drive these writes through the Trust Agent in the product — see [Approve agent writes](/how-to/approve-agent-writes).

## What is deliberately held back

The exposed eight are a minority of the agent's registry. At this release the registry holds 27 tools, so 19 are named exclusions. Held back today:

- **The agent's own prompt scaffolding** — the reads it uses to assemble its skills and suggest next steps. An external caller brings its own model and prompt; these would expose how the Trust Agent builds a turn without serving any caller need.
- **Reads and writes that ship on the in-product runtime first** — the Agent Profile reads (the captured profile, its tool catalog and recorded schemas, its source manifest), the data-connection discovery reads, and the writes for [Requirements](/concepts/requirements), expected output, and scenario test data. These are shipped product surfaces; what is held back is the MCP transport for them, which is a deliberate later step once the in-product path is proven. Do not read this list as a list of unreleased features.
- **Writes whose shape isn't final** — exactly three: saving an evaluator, generating scenarios, and simulating a scenario. The surface commits to a stable shape per tool, so a tool that would still change stays off it.
- **One authoring tool that exists only for Trust AI's internal self-evaluation.**

Every held-back tool is named in a conformance test alongside its rationale, so a tool cannot quietly appear on or disappear from the MCP surface: a new tool in the registry fails the build until it is either exposed on purpose or excluded on purpose.

## Observability

Every tool invocation — including a denied one — emits one OpenInference tool span:

- Tool name and tenant context (project, workspace, user) are stamped **before** the access check runs, so a refusal is recorded as "this user attempted this tool on this project", not as silence.
- Input arguments and results are recorded on the span, truncated with an explicit marker when they are too large to carry rather than dropped.
- Writes carry the approval state, so runs can be filtered by whether a person approved, rejected, or never answered.
- Failures carry an error kind, whether they came from the access check or the tool itself.

Because the spans follow OpenTelemetry and OpenInference conventions, MCP activity sits in the same trace view as the agent runtime's own tool calls.
