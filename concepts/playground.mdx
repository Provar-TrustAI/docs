The Playground is where you run the agent under test directly: pick a connected agent, **chat** with it live, or **simulate** a persona pursuing a goal against it — and save any conversation worth keeping as a [scenario](/concepts/scenarios). It sits between building scenarios and running [evaluations](/concepts/evaluations): you drive an agent by hand here before grading it at scale.

The Playground is a per-project surface at `/projects/:id/playground`. It is project-scoped — the agents you can pick, the conversations you can drive, and the History you can browse all belong to the project you are in.

<Note>
  **The Playground is not the Trust Agent.** They are two different chats, on two different routes:

  - The **[Trust Agent](/concepts/trust-agent)** is *your* in-app assistant at `/projects/:id/agent` — it does evaluation work for you (finds sessions, builds scenarios, runs evaluations) and stops for your approval before it writes.
  - The **Playground** (this page) at `/projects/:id/playground` is where you chat with and simulate against the *agent under test* — the customer's [Agent Version](/concepts/agent-versions) you are judging.

  They do not share a thread, and they do not share a runtime. When this page says "the agent," it means the connected agent under test, not the Trust Agent.
</Note>

## In the app

The Playground is a full-screen chat surface — there is no floating dock here. The topbar carries the agent picker on the left and its icon actions on the right: **Agent profile**, **Playground history**, and **New session**, plus **Save this conversation as a scenario**, which only renders once a session has started. So an empty Playground shows three icons and a live conversation shows four. The composer sits at the bottom. Its tools cluster shares a bar with the send action and carries two controls, in this order: **Attach images**, then the **Chat / Simulate** mode toggle.

### The agent picker

The topbar carries a grouped agent picker. Connected agents are grouped by their source system — one group header per system, collapsing to a single header when every agent comes from the same one — and each option shows the agent's own label plus a one-line description.

The picker renders the agent build's label: its identity in the source system it is connected through. That is never a UUID, but it is also not guaranteed to be prose — a build label can read as an identifier for some connectors. Everywhere the surface writes a *sentence* about the agent — the greeting, the composer placeholder, the simulate status row, the History meta line — it uses the connection's display name instead, which is the name you set in Project Settings with identifier syntax smoothed out.

Once a session starts, the picker locks to a static `system / agent` breadcrumb, so the whole conversation runs against one agent.

### The agent profile entry point

The topbar's info button opens the [Agent Profile](/concepts/agent-profile) fly-in for the selected agent, pinned to that build. It opens over the Playground and never navigates away, so you can check what the agent claims to do without losing the conversation you are in. If no profile has been generated for that build yet, the fly-in says so and offers **Generate profile**.

### The Chat / Simulate toggle

Before a session starts, the composer carries a segmented **Chat / Simulate** toggle — two options, labeled exactly **Chat** and **Simulate**. This is a mode switch. It is not the Trust Agent's **Ask / Plan / Act** mode toggle; those modes belong to the Trust Agent and have no equivalent here. Once you send a first message, the toggle collapses to the agent-name hint — a session is committed to the mode it started in.

## Chat — manual streamed conversation

**Chat** is a manual conversation with the connected agent. You send a message; the agent streams a real reply back live, the same way it would in production — nothing is canned or pre-recorded. Send another message and it continues the same thread; the agent picker stays locked to your chosen agent and the conversation accumulates.

Under the surface, a Chat session is a [simulation](#how-the-playground-runs) with no persona: the first message you send opens the run, and each message after that drives the connected agent for the next reply. You don't have to think about that to use Chat — it behaves like an ordinary conversation — but it is why a Chat conversation can be saved as a scenario and re-run later, just like a simulated one.

## Attach a picture

A message can carry pictures as well as words. **Attach images** — the paperclip in the composer's tools cluster — opens your file picker, and dragging a picture onto the composer does the same thing. The accepted formats are **PNG, JPEG, WebP, or GIF**.

Each picture you pick lands on a strip directly above the composer, so you can see what is riding the message while you are still writing it, and take something off it you did not mean to send. A caption is optional: a picture on its own is a first-class turn, so you can send a screenshot and nothing else and the agent answers about what it is looking at. The same control sits on the composer in **Stay in the loop**, so a turn you are steering can carry one too.

**Attach images** stays closed until you have picked an agent — it says **Choose an agent above before attaching an image.** — because the picture has to be addressed to something.

### When a picture is refused

The product states its own limits, at the moment they bite, rather than as a list you have to remember. Three rules govern one message: how large a single picture may be, how many pictures one message may carry, and how much everything on one message may total together. A file that breaks one of them keeps its place on the strip as a chip carrying the reason and naming the file — a refusal you can read beats a toast that has already gone — and a refusal that is about the *message* rather than about one file sits beside the strip instead. A file that is not a picture the product can send is turned away the same way, with the formats it does accept named in the same sentence.

Nothing about a refused pick is sent. Swap the file and carry on.

### Which agents can be sent a picture

The attach control renders for whichever agent you have selected; it does not check first whether that agent can receive a picture. At this release only an agent connected through **Salesforce Agentforce** accepts one.

The two ways this goes wrong fail at different moments, and the banner says which. Send a picture to any other agent and the turn is refused before anything runs, under **Your message wasn't sent** — nothing was sent, nothing was invoked, nothing was charged. A Salesforce org that is not entitled to image upload gets further before it stops, so that one ends under **The agent run failed**. Either way the picture does not reach the agent, and what you read is the product's account of the failure rather than the platform's own words passed through — see [When a run fails](#when-a-run-fails).

### How a picture reads back

A picture is shown as a picture, not as a file name. It renders inline at the head of the turn that carried it, sized to the bubble, and clicking it opens it over the whole window at its own size — press `Esc`, choose **Close**, or click outside it to go back to the conversation. That holds in the Playground and on the [Sessions](/concepts/sessions) panel, which are the same conversation read back through the same transcript.

When the picture itself cannot be shown, the turn names the file and says which of two different things happened, rather than painting a broken image:

- **This picture wasn't saved with the conversation, so it can't be shown here. It was still sent.** — nothing failed and nothing can be retried; there was nowhere to keep the bytes.
- **This picture couldn't be loaded. It was still sent — only the preview is missing here.** — the bytes are stored and this surface could not read them, so reopening the conversation may well work.

Both sentences end on the same fact, and it is the one that matters: the agent got the picture either way.

<Note>
  {/* ACCURACY-AUDIT-PENDING */}
  **Grade what the agent did about a picture, not the picture.** A check reads the conversation, so a scenario built from a conversation that carried a picture is best asserted on the route the agent took, the tool it called, or the answer it gave — not on the image itself.
</Note>

## Simulate — persona and goal driven

**Simulate** turns the conversation over to a persona. Toggle to **Simulate** and a **Simulate a conversation** dialog opens, with three fields in this order:

<Steps>
  <Step title="Write one goal">
    **Goal** is the first field and takes focus when the dialog opens. Describe what the persona is trying to accomplish — "Get a full refund to the original card." An empty goal always keeps **Simulate** disabled.
  </Step>
  <Step title="Pick exactly one persona">
    A single-select persona picker. A simulation needs a concrete persona to role-play, so the project's default persona is deliberately not offered here — you choose a specific persona, not the implicit fallback. The first persona on the roster is pre-selected, so on a project that already has personas the goal is the only field you have to fill in.

    **A project with no personas of its own is the exception, and it is the state a new project starts in.** With nothing to pre-select, the picker opens on **Choose a persona…** and **Simulate** stays disabled no matter how complete the goal is — the button needs a goal *and* a selected persona. Create one inline from the picker; a persona you create is auto-selected for the run.
  </Step>
  <Step title="Choose a run mode">
    Two run modes control how much you stay involved:

    - **Full auto** — "Simulates the whole conversation end-to-end". The persona's user turns and the agent's replies alternate automatically until the conversation resolves or hits its turn cap.
    - **Stay in the loop** — "Suggests each user turn as you go". The persona's next message lands in the composer as a draft; you confirm it or edit it before it sends, so you can steer the conversation as it goes.
  </Step>
</Steps>

Press **Simulate** and the conversation auto-drives turn by turn: the chosen persona role-plays the user pursuing the goal, the agent replies, and both stream live while you watch. In **Full auto** the composer is replaced by a live status row reading "{persona} is talking with {agent}…". The run is capped at six user-and-agent exchanges rather than running forever — long enough to see the agent's behavior, short enough to stay legible.

### Why a conversation ended

A simulated conversation closes with one plain-English line saying why it stopped, led by **This conversation ended because** and completed by one of: *the customer got what they needed · the agent could not help with it · the customer gave up · the agent ended or transferred it · it reached the length limit before finishing*. An ending this build does not recognize falls back to the neutral *the customer chose to stop*.

Read *the customer* literally: that is who the simulated user is playing. The persona is the configuration behind it, which is why the line never names one.

Where the simulated customer explained its own decision, its words follow on a second line, in quotes and verbatim. That is reported speech — the simulated customer's account of why it stopped, not the product's summary of it.

A conversation with no recorded ending renders nothing at all. There is no "Unknown" and no empty placeholder, so never read a missing line as a verdict — a conversation captured before this shipped simply has nothing to say. The same line appears on the [Sessions](/concepts/sessions) panel and on an evaluation result's transcript, so a conversation says the same thing about itself wherever you open it.

### The agent's trace

The transcript shows more than the agent's replies. Each agent turn can carry two layers of trace:

- **An inline peek above the bubble.** Only two kinds of step surface here: **Routed to** — which route or sub-agent the agent picked — and **Tool used** — a tool or skill it called. A route that repeats the previous turn's route is suppressed, so the peek marks changes rather than restating the obvious.
- **An expandable trace below it.** The bubble grows a **Show agent steps** toggle carrying the step count. Expanded, it lists every step for that turn, with each step's raw **Input** and **Output** payloads behind the disclosure rather than spilled onto the surface.

A live Playground run only ever produces route and tool steps, so that is what both layers show. A past conversation reloaded from History can also carry **Thinking** steps, from a transcript captured with a richer step vocabulary; those appear in the expandable trace only, never in the inline peek.

The Playground never labels a step **Model call**. That label exists on other transcript surfaces, but the Playground's projection has no path to it — anything that is not a route or a tool step is folded into **Thinking**.

### Records the agent looked up

When the agent under test answers out of Salesforce, the records it found are rendered as labeled blocks rather than as data: the object's name and the record's own title as a heading, then one labeled line per field, in the platform's own field order. Record ids never appear as text — not the record's own, and not a related record's — so the transcript reads as a conversation rather than as a query result.

One record and a list of them are handled differently on purpose. A single record is the answer, so it renders whole. A list gists instead: each field value collapses to one line, the list stops at ten records, and any it did not render are counted in a closing line rather than dropped silently. A field whose value cannot be read as a value is left out rather than dumped onto the surface.

## Save a conversation as a scenario

Any conversation worth keeping — a **Chat** or a **Simulate** session — can be saved as a [scenario](/concepts/scenarios). Once a session starts, a **Save this conversation as a scenario** button (a database icon) appears in the topbar and stays visible for the whole session. It becomes actionable once the conversation has at least one user message and one agent reply; before that its tooltip reads **Send a message and get a reply first**, and pressing it tells you the same thing rather than doing nothing.

Trigger it and a **Save as a scenario** dialog opens — the same lightweight intake a new scenario gets anywhere else:

- **Name** (required) — a short, descriptive scenario name.
- **Goal** (required) — what the user was trying to achieve. A Simulate session pre-fills this with the run's goal; for a Chat you write it yourself.
- **Personas** (optional) — a Simulate session pre-selects the persona that drove the run; a Chat starts empty. Each attached persona means one simulated session per run later.

Behind the dialog the transcript shows an agent turn with 'Routed to Refunds & Returns' and 'Tool used lookup_return' peeks." />
</Frame>

The dialog summarizes what you're capturing as a turn count — total turns, how many from you, how many from the agent — and **Save scenario** does two things at once: it creates a flat scenario in the project's Scenarios list, and it finalizes the conversation you just ran as that scenario's linked [session](/concepts/sessions). The conversation is not re-typed: the live run itself becomes the scenario's session, with its **Source** shown as **Scenario**.

Pictures are the one thing that really is copied. Any picture the conversation carried is copied into the new scenario's own file library — oldest first, and a picture you sent twice counted once — and the copy has its own life there. It is the scenario's file from then on, not a pointer back at the conversation. Each copy arrives with an empty description, which matters on the other side: on a [scenario](/concepts/scenarios) it is the description, not the image, that the simulated user reasons from.

A scenario's library holds fewer, smaller files than one message may carry, so a picture-heavy conversation can bring more than a scenario will take. Nothing is dropped quietly — the save says what came across and what did not.

Notice what the dialog does *not* ask for: an expected output. Its own sub-text says why — "You'll set expected output later — usually from a session you like." A freshly saved scenario is deliberately incomplete: it shows up as missing expected output (the Scenarios list ships a built-in **Missing expected output** view for exactly these), and you author its grading contract later in the scenario's Expected Output editor — often from the very conversation you just saved. Define cheap, run, then learn the expected output from a real session.

### After a save

Saving closes the run out. The surface resets to a fresh, empty Playground and confirms with **Saved as a scenario.**

When the conversation carried pictures, that confirmation carries a second line, written by the product and always leading with what came across before it accounts for anything that stayed behind: how many pictures made it into the scenario, then — only if some did not — which files they were and which rule they hit, the scenario's file limit or its size limit. A save that carried no pictures says nothing about them at all.

The conversation you saved is finished — it cannot be saved a second time — but it is not gone: it stays in History, and it is now a real session on the [Sessions](/concepts/sessions) surface with a stable id.

<Note>
  **Saving creates two things you can find later.** The scenario lands in the project's flat [Scenarios](/concepts/scenarios) list with a stable id like `SCN-000123`; the conversation lands on the [Sessions](/concepts/sessions) surface as that scenario's linked session. There is no separate copy — the scenario's Sessions tab and the Sessions list are showing the same conversation.
</Note>

### Saving is what makes a session

This is worth being precise about, because it changes what you should expect to find later.

**A Playground conversation you never save does not become a session at all.** Driving a conversation here opens a run against the connected agent, but nothing lands on the Sessions surface until you save it as a scenario. Start a new session, navigate away, or dismiss the save dialog and the run is simply left unfinalized — no session row, nothing on the Sessions list, nothing to evaluate. The conversation is not lost: History still lists it and still reopens its full transcript. It just isn't a session.

Saving is the only thing that turns a Playground conversation into a session, and because saving always attaches a scenario, a saved Playground conversation always reads **Source: Scenario** — never **Source: Playground**. The Sessions list's **Playground** source value exists for interactive captures finalized without a scenario link; the Playground's own save flow does not produce one.

Because a saved conversation is a real session, you can grade it directly, as it is: sessions are first-class evaluation targets, and the Sessions surface's primary **Evaluate** action grades the conversations that already happened. The [Sessions](/concepts/sessions) page owns that surface.

### Where the provenance card comes from

A session's details show a **Simulated from** card only when the session carries a frozen point-in-time snapshot of the scenario and persona it ran under. That snapshot is written when a scenario-linked run is finalized, which covers both paths into a scenario: the Scenarios surface's **Generate sessions** flow, which links the scenario up front, and the Playground's save-as-scenario, which links it at the end.

So a saved Playground conversation does get a **Simulated from** card. A saved **Simulate** run shows both the scenario and the persona that drove it; a saved **Chat** run had no persona, so it shows the scenario alone. Sessions with no scenario link — external and uploaded conversations — carry no snapshot and render no card at all.

## History — past conversations

The Playground keeps a **History** menu of the project's past simulated conversations, newest first, capped at the 30 most recent. A run with no turns yet is left out. When there is nothing to show it reads **No past sessions yet.** The menu leads with the rule that surprises people most, in its own words: **Conversations remain in History when you start a new one.**

Each entry shows a title, a meta line, and a relative time:

| Run type | Title | Meta line |
| --- | --- | --- |
| Simulate | The run's goal | `{persona} · N turns · simulated` |
| Chat | The first user message | `{agent} · N turns` |

Titles clamp at a word boundary rather than mid-word, and fall back to "Conversation" when there is nothing to derive one from.

History is real, persisted, server-side data — the project's actual runs, not mock entries and not something kept only in your browser. It survives a hard reload and shows up no matter which browser you signed in from. Note what it lists: **runs, not sessions.** A conversation you never saved has no session, and it is still here. Starting a new session clears the current conversation from the surface — past conversations live in History, not in the composer.

<Note>
  **History is not filtered to conversations you drove here.** It lists every simulated run in the project that has turns, whoever started it — which includes the conversations the Scenarios surface's **Generate sessions** flow produced and the ones an [evaluation](/concepts/evaluations) drove against a scenario. Those land in the same shape as a Playground **Simulate** run (the run's goal as the title, `{persona} · N turns · simulated`), so a project that has generated sessions or run an evaluation will show entries nobody opened the Playground for. They open read-only like any other past conversation.
</Note>

### Reopening a past conversation

Pick an entry and its full transcript reloads from the server into the Playground view, rendered through the same transcript components it streamed through live. Its pictures come back too: they are fetched from where they were stored rather than from your browser, so they render inline as they did live and still open full-window on a click. One that genuinely cannot be shown names the file and says whether it was never saved with the conversation or simply could not be loaded here.

A reopened conversation is **read-only**. It is a finished snapshot with no live stream attached, so the composer is replaced by a banner reading **Viewing a past session.** with a **Start a new session** action. You cannot type into a past conversation, and you cannot save one this way — the save action needs a live run to finalize. **Start a new session** takes you back to an empty Playground.

## When a run fails

When a turn does not land, the composer is replaced by a banner. Its headline comes from the failure's own machine-readable code rather than from the wording of any one error, so there are exactly three of them:

- **Your message wasn't sent** — the turn was refused before anything ran. A picture the selected agent cannot be sent is the usual reason. Nothing was sent, nothing was invoked, nothing was charged, and the way out is to send something different.
- **This agent couldn't be reached** — there was nowhere to send the turn, because nothing is registered under the connector the selected agent names. Nothing about your message is wrong, so rewriting it will not help; a different agent, or an admin, will.
- **The agent run failed** — everything else. The agent was reached and the run broke.

Underneath all three is the same three-line body, and every line of it is the product's own copy rather than anything the agent's platform returned:

- **Who can help** — who owns this failure: the tested agent, the provider or its connection, TrustAI, or — said plainly, when that is the honest answer — that the failure did not identify its source.
- **Likely cause** — one sentence for that owner.
- **Next step** — what to do about it.

Raw provider prose, stack traces and vendor payloads deliberately never reach this banner. Free-form text from the far end of a connection is not reliable enough to tell you who can fix something, so the banner reads the typed evidence instead and says only what it can stand behind.

The turns that already landed stay on screen. The banner belongs to that run: start a new session to clear it.

## Running a saved scenario at evaluation time

The persona-and-goal simulation you drive by hand here is the same thing an evaluation runs automatically. Once a conversation is saved as a scenario, that scenario can simulate *fresh* conversations on demand: from the Scenarios list or the scenario's fly-in, **Run & evaluate** opens the Evaluation Launcher, you pick the agent to run against, and the run simulates a new conversation for each persona attached to the scenario — grading each one with the evaluators the scenario carries. A goal-only scenario with no persona still simulates one conversation from its goal. The split button's chevron also offers **Run only** — simulate without grading — when you just want more conversations to look at.

An adopted security probe is an ordinary scenario, so it takes the same path. The Playground is where you can play one of the [recommended scenarios](/concepts/trust-library) through by hand first — one goal, one agent, one conversation you watch — before you grade the whole set at once.

Two paths, one distinction: a scenario-sourced run always simulates fresh conversations; grading conversations that *already happened* — including the Playground conversations you saved — is the launcher's sessions mode, opened from **Evaluate** on the Sessions surface. Either way, every conversation a run grades is a real session: **Open session** on any result lands you on the exact conversation that was judged. The full execution anatomy — the launcher's entry points, the fan-out preview, and the run results — lives on the [Evaluations](/concepts/evaluations) page. This page names the capability; Evaluations owns the depth.

## How the Playground runs

You don't need the plumbing to use the Playground, but a little context helps.

A Playground conversation is a **simulation** — a project-scoped run record that exists from your first message onward. That is why History can list, label, and reopen your conversations, and why saving one as a scenario needs no copy step for the conversation itself: the run is already a persisted record, not a transient chat. Its pictures are the exception, and they are copied on purpose, so the scenario owns files of its own. A run is in one of three states — running, finished, or abandoned — and History does not filter on them: it lists every run in the project that has turns, whatever state it ended in. That is the mechanism behind the rule above — an unsaved conversation stays listed and reopenable precisely because History reads runs, not sessions.

The Playground and the Trust Agent **do not share streaming infrastructure.** The Trust Agent runs on its own agent runtime; the Playground streams its replies from the live simulation-invoke path, a separate stream carrying the agent's text, its route and tool steps, and its terminal state. The two surfaces stream independently and never share a conversation.

Any wait you feel before a reply streams in is upstream **model thinking time** — how long the connected agent's model takes to respond. It is not a fixed latency the Playground promises and not a bug; the time depends on the model and the infrastructure it runs on, which is exactly why the Playground streams the reply in as it lands rather than showing a countdown.

<Note>
  Your Playground conversations are **tenant-scoped**. Every run belongs to your organization and project, and you only ever see and drive your own org's data — a run from another organization isn't addressable, even by its identifier. The platform side of that boundary lives in [Multi-tenancy](/concepts/multi-tenancy).
</Note>
