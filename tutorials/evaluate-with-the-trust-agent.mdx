This walkthrough covers the full evaluation flow end to end. Instead of clicking through Requirements, Scenarios, Evaluators, and Evaluations by hand, you'll **drive the whole thing through conversation** with the [Trust Agent](/concepts/trust-agent) — the in-app assistant that drafts what you describe, shows you every write before it lands, and waits for your approval.

By the end you'll have a scored evaluation and a coverage picture that computes itself: requirements on file, scenarios linked to them, a judge attached to each, and a run that says which behaviours hold.

<Note>
  **The Trust Agent is not an Agent Version.** They share the word "agent," but the **[Trust Agent](/concepts/trust-agent)** is *your* assistant inside Trust AI — the thing you chat with in this tutorial. An **[Agent Version](/concepts/agent-versions)** is the *customer's agent under test* — the pinned snapshot the evaluation grades. In this tutorial you use the Trust Agent to evaluate an Agent Version; they're distinct concepts.
</Note>

Budget 30 to 60 minutes. Most of that is the agent thinking and the simulated conversations playing out — your part is answering a few questions and approving the writes.

## Before you start

You need one thing, and it is not optional:

- **A [Project](/concepts/projects) with a connected agent.** Most of the Trust Agent's authoring is refused outright without one — it will tell you *"Connect an agent before creating tests or running them. I can help you connect one now."* and offer to walk you through it in the chat. If you'd rather connect first, use the guide for your platform: [Agentforce](/how-to/connect-agentforce), [Claude managed agent](/how-to/connect-claude-managed-agent), [AgentCore](/how-to/connect-agentcore), or a [conversational HTTP agent](/how-to/connect-http-agent).

One thing to check while you are there: that the connected agent has a **captured [Agent Profile](/concepts/agent-profile)** — the record of the subject areas it serves and the actions it can take. You can get all the way to the last two steps without it, but not through them: the grading contract in step 6 is written against the agent's captured actions, so a build with nothing captured stops there. [Review an agent profile](/how-to/review-an-agent-profile) is the guide.

You do **not** need existing sessions, scenarios, evaluators, or requirements. You build them here, in the order below — and that order is the point of the page.

## The order is enforced, not suggested

The Trust Agent guides one core authoring workflow, and the runtime holds you to it. Each step refuses to run until the artifact before it exists, so a tutorial that skipped ahead would dead-end its reader at the first write. [The workflow the agent enforces](/concepts/trust-agent#the-workflow-the-agent-enforces) covers the mechanism; this page walks it.

| Step | Finished when |
| --- | --- |
| **1. Connect an agent** | A usable agent is connected to the project |
| **2. Capture requirements** | At least one saved requirement states what to test |
| **3. Generate scenarios** | Each new scenario is linked to the requirement it exercises |
| **4. Build evaluators** | One evaluator per requirement is attached to its scenarios and linked back |
| **5. Complete expected output** | The applicable actions, routes, and test data are saved on each scenario |
| **6. Run the evaluation** | A prepared evaluation has run against the connected agent |

Ask for a later step first and you don't get a refusal you have to decode. The agent checks what the project actually holds, names the earliest missing step, and offers to do that instead — it won't collect the later step's details or raise an approval card until the prerequisite lands. Underneath, the platform is returning a specific sentence for each missing artifact:

| The project is missing | What the platform refuses with |
| --- | --- |
| Any saved requirement | *"Draft and save the requirements first."* |
| Scenarios linked to those requirements | *"Create scenarios linked to every requirement first."* |
| An evaluator per requirement | *"Create and attach one evaluator for each requirement first."* |
| Those evaluators attached to the scenarios | *"Attach each requirement's evaluator to its scenarios first."* |
| Expected actions or routes on the scenarios | *"Create expected actions or routes for the scenarios first."* |

Each closes with the same offer — *"I can guide you through that now before we continue."* You will usually meet these in the agent's own words rather than as a quoted string: the refusal is handed to the agent as recovery data, and it explains the block and proposes the fix in the reply. Exploration, personas, security coverage, and data discovery sit outside this sequence entirely. They can strengthen a step; they never substitute for one.

<Tip>
  Landing on a project and not sure how far it got? Ask the agent, or use the **Show me where to start** chip described in step 1. It re-reads the project's real state rather than trusting what an earlier conversation said, so it is accurate even on a project somebody else left half-built.
</Tip>

## The walkthrough

<Steps>
  <Step title="Open the Trust Agent and say what you want tested">
    From your project, click **New chat** in the left nav. A new chat opens on a **Welcome** surface: a greeting, a one-line status about your last evaluation, a composer, and four starter-prompt pills beneath it — **Evaluate agent**, **Improve requirements**, **Summarize evaluations**, and **Connect agent**. That set is the same on every project, however far along it is. Clicking a pill expands its suggested prompts inline, and clicking a suggestion pre-fills the composer; nothing sends until you press send.

    <Warning>
      **Check the mode before you send.** The Welcome composer is a full composer, not a stripped-down launcher: it carries the **Attach files** control, the **Ask** / **Plan** / **Act** mode toggle, the model picker, and the **Thinking** chip. A mode you pick there is handed to that conversation's first turn, so the mode your first message goes out in is whatever the toggle reads — not a fixed default. Look at it before you send.
    </Warning>

    This tutorial runs in **Ask**, which is what the toggle starts on. Ask clarifies genuine ambiguity before it acts and stops at an approval card before every write. **Plan** researches and proposes a task list and cannot write or even raise an approval card; **Act** works straight through but still stops for approval on every write. Leave the model on whatever your workspace offers by default, and leave **Thinking** on **Balanced**.

    Now describe what you want tested, in your words, the way you'd brief a teammate — and put the actual rules in the message, because those rules are about to become requirements:

    > Our refunds agent goes live Friday and I need to trust it. Refunds go back to the original card 7-10 business days after the warehouse scans the return, returns are only accepted inside a 60-day window, and anything past the 10th business day must be escalated to the payments team the same day. The agent must never promise a refund amount it has not looked up. Capture that as requirements.

    <Frame caption="The Welcome composer carries everything the chat composer does — attach, the mode toggle, the model picker and Thinking — so the mode this conversation starts in is a choice you make here. Requirements sits above Scenarios in the project nav, with a count of the project's active requirements.">
      <img src="/images/agent-tutorial-welcome.png" alt="The Welcome surface of a project's Trust Agent: the greeting 'Hi, Dev. Let's get to work!', a one-line status reading 'You haven't run any evaluations yet. Try one from the prompts below.', and a composer holding the refunds brief typed out in full. The composer's tool row carries an attach control, an Ask mode toggle, a Claude Opus 4.8 model chip and a Balanced Thinking chip, with the send control at its right. Four starter-prompt pills sit beneath it — Evaluate agent, Improve requirements, Summarize evaluations, Connect agent — with Improve requirements active and its two suggested prompts listed below. The project's left nav shows Requirements with a count of 4 above Scenarios, Sessions, Evaluators and Evaluations." />
    </Frame>

    On a project with nothing at all in it — no sessions, no scenarios, no evaluators, no runs — the suggestion row under the agent's first reply leads with a standing **Show me where to start** chip. It pre-fills a request for a guided walk and, like every chip, never sends on its own. It disappears as soon as the project holds any real work.

    **You should see:** the Welcome surface with its four pills, and — once you send — the chat with your message as turn one, the project nav still on your left, and the composer's mode toggle reading **Ask**.
  </Step>

  <Step title="Let it draft the requirements">
    The agent leads with its **Capture requirements** skill, and it reads before it writes. Expect three receipts in the transcript before any prose: **Reviewed the project**, **Reviewed Capture requirements** carrying a **Core skill** chip, and **Reviewed project records**. That last one is it checking what is already on file, so a behaviour you have already written down comes back as an edit to that requirement rather than a second one saying the same thing.

    It works from whichever of three paths fits what you gave it:

    <AccordionGroup>
      <Accordion title="A brief you paste or type">
        What this tutorial does. The rules in your message get decomposed into atomic, testable requirements — one behaviour each, compound statements split apart, and each classified out loud as something the agent must do or must never do.
      </Accordion>
      <Accordion title="A document you upload">
        Attach a PRD, policy, or spec with the composer's **Attach files** control and ask it to file what the document implies. It reads the whole thing before proposing anything, scans it twice — once for what the agent must do, once for the boundaries it must never cross — and quotes the line each requirement came from.
      </Accordion>
      <Accordion title="Seeded from the connected agent, or a guided walk">
        With a captured profile to read, it can propose one draft per topic the connected agent genuinely serves, quoting any operating rule the platform declares. With nothing known about the agent yet, it runs a structured interview instead: purpose, happy path, boundaries, edge cases, failure modes, and what would make a reviewer mark a reply pass or fail.
      </Accordion>
    </AccordionGroup>

    It defaults to the document when you have one, falls back to seeding when there is a profile to read, and uses the interview for a greenfield agent.

    Whichever path it takes, **it writes every draft into the reply first** — numbered, one line each, title plus the behaviour that would pass or fail it — before it proposes anything. Read that list. It is where you catch a rule it split the wrong way or a "must never" it read as a "must".

    [Capture requirements](/how-to/capture-requirements) is the focused recipe, including the manual paths: **Requirements → Extract from document** for a file, or **New requirement** to type one in.

    **You should see:** the three receipts, then a numbered list of proposed requirements in the agent's reply, then a single approval card.
  </Step>

  <Step title="Approve the one batch card">
    A curated batch of requirements files behind **one approval card**, not one card per requirement. The card repeats the list you just read — every requirement by title with a one-line summary — above a **_N_ records in this batch** line, so you are never approving a count you cannot expand.

    | On the card | What it means |
    | --- | --- |
    | A numbered entry per requirement | You approve content you can see, not a total |
    | *"They're filed together: if any one of them can't be saved, none of them are."* | All-or-nothing. A batch never lands half-applied |
    | *"Nothing is saved until you approve."* | The gate is the card, not the message above it |
    | *"They become active as soon as you approve — you can edit or archive any of them later from the Requirements page."* | Or, on a draft batch: *"Saved as drafts — review and promote them from the Requirements page when you're ready; drafts don't count toward coverage."* |

    A batch tops out at 50 requirements; past that the agent has to split it. Two entries that say the same thing are refused before a card is ever offered, and so is one an existing requirement already captures.

    You can answer a card four ways, not two: approve it once, grant a **standing approval** for that action across this chat, reject it with an optional note, or dismiss it with the floating **×** and hand the turn back. [Approve agent writes](/how-to/approve-agent-writes) is the focused recipe for all four. Some writes a standing approval can never cover, and they are confirmed every single time: **deleting items**, **saving an agent profile**, and a bulk edit with a requirement mixed into it.

    <Frame caption="The card has taken the composer's slot — there is nothing to type into until you decide. This one offers the chat-wide grant as its middle choice, which the agent only does when it has written a specific label for the action; a delete never offers it.">
      <img src="/images/agent-tutorial-permission-card.png" alt="A permission card in place of the composer, asking whether to detach the Refund policy groundedness evaluator from eight behaviour scenarios while keeping each one's routes, tool assertions and remaining evaluators. Below the question a compact summary line reads '8 fields changed' with a 'View proposal' link, then three choices — 'Detach on all 8' selected, 'Detach Groundedness from these scenarios' as the chat-wide grant, and 'Reject — and tell me why (optional)' — with a floating close control at the top right and an Approve button at the foot. The transcript above lists the eight scenarios the write touches." />
    </Frame>

    Approve, and the write actually executes — this is not a preview that quietly does nothing. A **Created a requirement** receipt lands in the transcript, expanded into a clickable table of the real records: `REQ-1`, `REQ-2`, `REQ-3`, `REQ-4`, each with its title and description. The handle is a bare number, deliberately not zero-padded like a scenario's `SCN-000123`, because these are things people say out loud. Your decision is recorded above it as a resolved row, and it survives a reload.

    The side rail's **Outputs** section now lists the same records, and the project's left nav shows **Requirements** with a count of the active ones.

    **You should see:** `REQ-1` through `REQ-4` on the card's receipt and in the rail, a resolved approval row in the transcript, and exactly one next-step chip under the reply — something like **Create linked scenarios**.
  </Step>

  <Step title="Ask it to generate scenarios from the requirements">
    With requirements on file, the next step unlocks. Ask for it plainly:

    > Generate scenarios from those requirements.

    The agent drafts a focused batch — a persona and a goal each, no transcripts yet — and stops at an approval card before creating them. Approve it and the scenarios land in your project's one flat **Scenarios** list; there is no set or folder layer above them. Personas are drafted alongside them if the project has none.

    Then it does the part that makes coverage computable, without being asked: it reads the scenarios back and **links each one to the requirement it exercises**, several scenarios to one requirement where a requirement has more than one edge. Expect a second approval and a **Reviewed scenarios** receipt between the two.

    <Frame caption="Every row is a real record you can click into — named scenarios and requirements, never a bare identifier — and the rail keeps its own tally beside them: what the agent read under Context, what it changed under Outputs.">
      <img src="/images/agent-tutorial-object-table.png" alt="The Trust Agent transcript with two multi-record tool receipts expanded into clickable object tables — reviewed evaluators and reviewed scenarios — each row carrying a record's name and description with a link glyph at its end and a 'Show more' row beneath. The side rail beside them shows Context, headed by the Refunds Concierge connected-agent card with counts of 6 evaluators and 1 scenario, and an Outputs section reading '8 changes' that lists five named scenarios with 'Show more (3)'. Two resolved 'You answered…' rows sit below the tables." />
    </Frame>

    Read the links before you move on. This is the step where a scenario quietly attached to the wrong requirement turns into a coverage number you can't trust later. The agent flags genuine ambiguity in your requirements here too — a window that doesn't say whether its last day counts, for instance — because that reading is about to be baked into a rubric.

    **In the UI instead:** open **Scenarios** and use **New scenario**, or **Add recommended scenarios** for the starter library of adversarial probes. Link each one from its **Expected Output** tab, under **REQUIREMENTS**.

    **You should see:** the new scenarios in the rail's **Outputs**, each requirement's **Scenarios** count moving off zero on the Requirements list, and one next-step chip pointing at evaluators.
  </Step>

  <Step title="Create and attach an evaluator for each requirement">
    A scenario with nothing grading it proves nothing, so this step is where the coverage actually closes.

    > Build the evaluators and attach each to its scenarios.

    The agent builds judges **one per requirement**, not one broad judge per project. For each requirement that has linked scenarios but no evaluator, it writes a focused rubric from that requirement's own acceptance criteria, attaches it to that requirement's linked scenarios **in the same write**, and links it back to the requirement so health rolls up. Where the project has human-reviewed scenarios to sample, it calibrates on the same save and tells you the agreement.

    Because this is the same action repeated, the agent will often offer the **chat-wide grant** on the first card so you approve once instead of four times. Take it or leave it — it binds only to that action, in that chat, and its chip above the composer carries a **turn off** control whenever you want the per-write gate back.

    Each receipt reads **Created an evaluator** and says what it attached to, counting the scenarios rather than listing their ids — *attaching to 3 selected scenarios*.

    <Note>
      **A rubric is grading criteria only.** Response-format instructions, verdict-shape instructions, and hardcoded answer keys are rejected by the platform while the write is still a preview, so there is nothing to approve and nothing created. The rejection quotes the offending text and names the fix, and the agent is expected to revise and re-save rather than hand you a menu.
    </Note>

    **In the UI instead:** open **Evaluators** and click **Add recommended** — the catalog offers 11 curated LLM-judge presets, five under **Quality** and six under **Safety**, with three carrying a **Tailor first** badge because they're written against a generic agent. [Build your first Evaluator](/tutorials/build-first-evaluator) walks the manual path end to end, including calibrating a judge against verdicts you recorded yourself.

    **You should see:** one evaluator per requirement in the rail's **Outputs**, each requirement's **Evaluators** count off zero, and a follow-up linking the evaluators back to their requirements as evidence.
  </Step>

  <Step title="Finish the grading contract">
    Attaching a judge is not the whole contract, and this is the step most first-timers discover the hard way: a run is refused until each scenario also carries **expected output** — the tool calls it must or must not make, and the routes it must or must not take. An attached evaluator alone does not satisfy that gate.

    > Set the expected output on these scenarios.

    The agent grounds assertions in what the connected agent really exposes rather than inventing tool names. Where it has a captured [Agent Profile](/concepts/agent-profile) to read, it completes the applicable actions and routes from that recorded vocabulary itself, then sets any applicable test data and end-state checks, and only then offers to run.

    <Warning>
      **This step needs the connected agent's actions to have been captured.** Expected actions are saved against the agent's captured action catalog, so on a build with nothing captured there is nothing valid to write — and the agent says so rather than guessing, naming the connection as the place to fix it. Tool names you supply by hand don't get you past it either, which is the point: an assertion on a tool the agent may not have is worse than no assertion. A **required** one fails every run; a **disallowed** one passes every run and tells you nothing.

      If you meet that, capture the profile first — [Review an agent profile](/how-to/review-an-agent-profile) covers how capture works and what **Captured / Partial / Limited** coverage means — then come back and ask again.
    </Warning>

    The agent will not go around the gate, and there is no reason to want it to. Answer what it asks, get the catalog in place, and the assertions it writes are the ones the run can actually check.

    [Author expected output with the Trust Agent](/how-to/author-expected-output-with-the-trust-agent) is the focused recipe — what a write replaces, what it leaves alone, and how to read the proposal panel. Two things worth carrying from it: assertions are **required** or **disallowed** only, and **expected end state** — the data contract inside a scenario's test data plan — is a different contract from expected output, never the same thing.

    **In the UI instead:** open a scenario from the **Scenarios** list and use its **Expected Output** tab — **Expected actions** and **Expected routes** take a name each, with **required** or **disallowed** beside it.

    **You should see:** the agent either reporting the actions and routes it completed, or a question card naming exactly what it is missing and what it can do about it.
  </Step>

  <Step title="Run the evaluation">
    > Run the evaluation now — simulate every scenario against the connected agent and score them.

    A run is a write like any other, so it stops at its own approval card. Note that a standing approval you granted earlier for creating evaluators does **not** cover it: a standing grant binds to one action, and a different action is gated afresh.

    Before proposing the run the agent may ask how you want it scoped — how many conversations, whether to simulate live against the connected agent or grade sessions you already have. That arrives as a question card in the composer's slot, and the chat header switches to **Awaiting your answer**.

    <Frame caption="The card has taken the composer's slot and the header reads Awaiting your answer. On step two of three, Back and Next are both live, so an earlier answer is still yours to change before anything runs.">
      <img src="/images/agent-tutorial-clarify-card.png" alt="A multi-question flow card in place of the composer, framed 'You've already got 15 ready scenarios and 6 evaluators. Let me scope the run for Friday.' and headed 'Question 2 of 3' with a three-dot progress row. It asks how the conversations should be produced, offering two drafted choices — the first, simulating live against the connected agent, selected — plus a write-in 'Or type your own answer…' option, with Back and Next in the footer. The header reads 'Awaiting your answer', and a 'Reviewed the project' receipt and two object tables of reviewed evaluators and scenarios sit above the card." />
    </Frame>

    A question card can be single-question or a short flow of two to five, counted through as **Question 1 of 3** with **← Back** and **Next →** between them and **Submit** on the last. Both shapes take a write-in answer where the agent asks for one, and both carry **Skip**, which tells the agent to proceed with what it has rather than cancelling the turn. Your answers collapse into a resolved row afterwards that echoes every question and what you chose.

    {/* ACCURACY-AUDIT-PENDING: the run itself and everything downstream of it are described at behaviour level. The authoring steps above were driven end to end, but the run could not be started on the connection available for verification — its agent build had no captured action catalog, which stops step 6. */}
    Once it runs, the simulator holds a **fresh multi-turn conversation for every persona on every scenario** against the pinned Agent Version, then scores each one. Every conversation it plays out is saved as a real [Session](/concepts/sessions) whose **Source** reads **Scenario**, linked back to the scenario that produced it — so you can open the exact transcript the judge read. The rail's **Outputs** row reads **Running…** until the real run lands.

    **In the UI instead:** open **Evaluations** and use **New evaluation** — [Run your first Evaluation](/tutorials/run-first-evaluation) walks the launcher, including the repeat selector and the fan-out preview.

    **You should see:** an approval card for the run, then a run record in the rail you can click into, and the **Evaluations** count in the left nav moving off zero.
  </Step>

  <Step title="Read the result">
    {/* ACCURACY-AUDIT-PENDING: every label in this step is taken from the shipped surface, but the reading flow was not driven against a completed run during verification — see the note on the previous step. */}
    Open the run. Results land grouped: run detail opens on **By scenario**, one summary row per scenario carrying a rollup verdict and a passed-of-total reliability figure — `2/3` when two of three attempts passed. Expand a row for the individual attempts, labelled **Trial 1**, **Trial 2**, and so on; click one and the result fly-in opens. The **View** toggle switches to **Flat** when you'd rather sort across scenarios than within them.

    Inside a result, **Final verdict** is the headline, with a score card per evaluator beneath it and the transcript beside it.

    <Warning>
      **Read the amber count next to the pass rate before you read the pass rate.** Five outcomes leave the pass-rate denominator, and they are not all the environment's fault. Four are — they read under **Guardrail blocked**, **Environment problem**, and **Access blocked**. The fifth reads amber as **Couldn't test**: an action the agent itself runs returned an error, so the behaviour under test never happened. It is excluded for the same reason as the others, but it is deliberately *not* framed as an environment problem, because that failure is in the agent's own stack.

      The run list carries that amber count beside the pass rate so a green rate never renders uncaveated, and Run Detail adds a health strip headed **Couldn't test some conversations** with a **What happened in this run** dialog behind it. A run that is 100% passing over two conversations it could actually test is not a run that passed.
    </Warning>

    Three neutral labels do different jobs and are never interchangeable: **Not evaluated** means no evaluation exists, **Not graded** means something ran but produced no behavioural score, and **Not scored** belongs to the reliability lexicon above. A per-check **Needs review** is a fourth thing again — amber, recorded, and excluded from pass/fail gating.

    Then ask the agent about it:

    > What failed?

    On a completed run the answer renders as an inline **Failure analysis** widget rather than a paragraph: a header counting the failures, one clickable table per root-cause cluster with its share of them ("4 of 7 failures"), and a **View the run** link into the full results. Every row opens the failing result.

    [Evaluations](/concepts/evaluations) covers the results surface in full — the verdict states, the repeat selector, and what an excluded outcome does and doesn't mean.

    **You should see:** **By scenario** rows with rollup verdicts, an amber count beside the pass rate if anything couldn't be tested, a **Final verdict** inside any result you open, and one next-step chip under the agent's reply.
  </Step>
</Steps>

## Where the coverage picture lands

The reason for doing it in that order shows up on the **Requirements** list. Each requirement now carries its linked scenario and evaluator counts and a computed **Status** — **Passing**, **Failing**, **Partially covered**, **Uncovered**, or **Not yet run** — which the server derives from the evidence rather than from anything you asserted. Switch the list to **Gaps** to see what is still uncovered or only partly covered.

Nothing in that rollup is a claim. It is what the run proved, which is why the requirement had to come first. [Requirements](/concepts/requirements) explains the model.

## Pick up where you left off

The whole conversation is durable. The Trust Agent survives navigation — jump to **Evaluations** or **Scenarios** and back and the same thread is intact — and transcripts are persisted, so a reload gives you the real prior history rather than an empty pane. A pending approval rehydrates as still answerable, with the composer held until you decide. An unsent draft survives a reload, and a message you send while the agent is mid-reply is queued rather than lost.

A few states are worth recognising when they show up:

| What you see | What happened |
| --- | --- |
| **The Trust Agent hit an unexpected error and stopped. Please try again.** | The turn failed server-side. The card carries **Try again** and the model picker |
| **The Trust Agent couldn't finish this reply. Please check your connection and try again.** | The request never reached a server verdict at all |
| **This reply was interrupted.** with **Continue** | The reply was cut short — a dropped connection, or a turn you stopped with **Stop**. Continue picks up from saved context |
| **Couldn't load this conversation** with **Retry** | The history read failed. The conversation is not lost |

A failed-turn card also carries the hint *"You can try again, or pick a different model first."* — switching models is a real recovery, not a consolation.

Under every settled reply sits a collapsed timing line — **Answered in** a duration, followed by the biggest slice that wasn't answering — which expands into a proportion bar with per-phase totals: Thinking, Using tools, Writing the answer, Waiting for you. A turn still paused at an approval gate has not settled and shows no line at all.

One thing that does not persist: the mode is never remembered across chats. It is handed to a conversation's first turn from whatever the launcher read when you pressed send, and nothing restores it later — so check the toggle rather than assuming.
