This tutorial walks you from a brand-new TrustAI account to your first scored evaluation of a real agent, in roughly ten minutes. It assumes you're setting TrustAI up for a customer agent for the first time; the shape is the same when you add a new agent to an existing workspace.

Most of these steps you'll drive by asking the [Trust Agent](/concepts/trust-agent) — the in-app assistant — in plain language, then watching the results land in the UI. Where you'd rather do something by hand, the manual UI path is right there too. The Trust Agent is taught exactly this arc — connect, write down what the agent must do, create coverage, evaluate — and it re-reads the project's real state each turn, so it names the one next step rather than a generic checklist, and you can leave and come back days later without losing your place.

By the end you'll have:

- A [Project](/concepts/projects) connected to your agent's platform
- At least one [Requirement](/concepts/requirements) saying what the agent must do
- Real [Sessions](/concepts/sessions) you can read end to end
- Starter [Evaluators](/concepts/evaluators) and [Scenarios](/concepts/scenarios) adopted from the recommended catalogs
- One scored [Evaluation](/concepts/evaluations) run you know how to read

That's one complete pass through [the evaluation loop](/concepts/evaluation-loop). Once it works once, the rest of TrustAI is "do this same thing at scale."

## Before you start

You'll need:

- A TrustAI account with access to a workspace where you can create projects
- An agent on one of the four platforms TrustAI connects to — **AWS Bedrock AgentCore**, **Salesforce Agentforce**, **Claude Managed Agent**, or a **Conversational HTTP agent** — plus its connection credentials, or an admin who has them
- About 10 minutes

<Tip>
  **No credentials at hand?** Start anyway. When you ask the Trust Agent to connect your agent, it hands you a plain-English checklist of exactly what to gather — something you can forward to your admin. For AgentCore, the setup wizard produces an admin handoff package your AWS admin can deploy without you.
</Tip>

## The seven steps

<Steps>
  <Step title="Create your first project">
    A [Project](/concepts/projects) is the workspace boundary around one agent under evaluation. Members, connections, and every artifact downstream belong to it.

    Creating a Project is the one setup step you do before the Trust Agent comes into play — the conversation lives *inside* a Project, so you need one first. Open the project switcher at the top of the sidebar and click **Create new project** (on a workspace with no projects yet, you'll land on a **Create your first project** screen with a **New project** button instead). Name it after the agent under evaluation (e.g., "Acme Support Agent") — a description is optional — and click **Create project**.

    **You should see:** you land inside the new Project. The left nav shows its surfaces, top to bottom: **New chat**, **Playground**, **Requirements**, **Scenarios**, **Sessions**, **Evaluators**, **Evaluations**, and **Project Settings** — all empty for now. Scenarios, Sessions, Evaluators, and Evaluations each carry a count badge reading 0; **Requirements** is the one that stays blank at zero rather than shouting a 0 at you.
  </Step>

  <Step title="Connect your agent">
    Click **New chat**. The welcome screen greets you by name and shows the same four category pills in every project, new or not: **Evaluate agent**, **Improve requirements**, **Summarize evaluations**, and **Connect agent**. Clicking a pill expands two suggested prompts underneath it; clicking one of those pre-fills the message box — nothing sends until you do. On a project that has done nothing yet, the subtitle says so plainly rather than inventing activity: *"You haven't run any evaluations yet. Try one from the prompts below."*

    <Note>
      *Ask the Trust Agent:* "Walk me through connecting my agent so TrustAI can evaluate it." (It is the second prompt under **Connect agent**, so you can click it instead of typing.)
    </Note>

    {/* ACCURACY-AUDIT-PENDING */}
    Once the agent has replied, a project that has nothing in it yet should also offer a **Show me where to start** chip among the follow-up suggestions under the reply. It pre-fills the composer with a question about where this project is up to — it never sends on your behalf — and the walk it starts re-reads the project each turn, so it stays useful days later.

    <Tip>
      **Three composer controls worth knowing before your first turn.** The **Agent mode** chip reads **Ask**, **Plan**, or **Act** — and whichever you choose, a write that changes something stops for your approval first. Beside it is the model, picked from the Claude models your workspace offers, and a **Thinking** chip offering **Standard**, **Brief**, **Balanced**, and **Thorough**, on **Balanced** by default. While a turn is running, **Stop** replaces send; the halted reply is stored, and the transcript notes *"This reply was interrupted."*
    </Tip>

    The agent first checks whether an agent is already connected. If not, it opens a secure connection card **inside the chat** for either **Salesforce Agentforce** or **Claude Managed Agent**, and the connection completes there — you never leave the conversation. The card collects credentials directly; your key or secret is never shown to the model and never appears in the transcript. Once it resolves, the card's receipt names the agent you connected.

    For Salesforce, that card is a short guided wizard: confirm your org, choose **Authorize TrustAI (recommended)**, approve TrustAI in Salesforce with an administrator account, then pick the agent to test. If your workspace has already authorized the org you want, step one offers **Reuse a Salesforce connection you already have** instead — **Use this connection** clones it into this project with no second sign-in.

    Prefer the manual path, or connecting **AWS Bedrock AgentCore** or a **Conversational HTTP agent**? Open **Project Settings** and switch to the **Connections** tab — the project settings strip is **General · Connections · Members** — then click **Connect an agent**. The wizard opens inside the tab, with **Back to connections** as the escape at every step, and offers four platforms:

    - **AWS Bedrock AgentCore** — a guided setup wizard: prepare an admin handoff package, have your AWS admin deploy the cross-account role, then paste the role ARN back. It is the one platform that [cannot be profiled](/how-to/connect-agentcore#agentcore-is-the-one-platform-that-can’t-be-profiled), so the agent-led paths that write a grading contract from captured actions are closed to it. Full walkthrough: [Connect an AWS Bedrock AgentCore agent](/how-to/connect-agentcore).
    - **Salesforce Agentforce** — a two-step flow. Enter your org's URL, then click **Authorize in Salesforce with an administrator account**; Salesforce opens in a new tab and the connection is set up for you when the admin approves. Step two is picking the agent to test. Full walkthrough: [Connect a Salesforce Agentforce agent](/how-to/connect-agentforce).
    - **Claude Managed Agent** — a form for an Anthropic Managed Agent on Claude Platform on AWS. Full walkthrough: [Connect a Claude Managed Agent](/how-to/connect-claude-managed-agent).
    - **Conversational HTTP agent** — for any agent that accepts AG-UI run requests and streams AG-UI events over SSE. Use this when your agent isn't on one of the named platforms. Full walkthrough: [Connect a Conversational HTTP agent](/how-to/connect-http-agent).

    <Warning>
      The Salesforce authorize step deploys a connected app into whichever org you sign in to. Point it at a Sandbox, not production.
    </Warning>

    Secrets are write-only throughout — once saved, TrustAI shows a **Configured** pill and the placeholder `•••• configured — leave blank to keep existing`, never the value back.

    **You should see:** your agent as a card on the **Connections** tab, under the heading **Connections** and the subtitle *"The agents this project tests."* A strip above the cards counts what you have — *"1 agent connection · 0 test data stores"* — and each card carries a pill saying whether TrustAI can reach the agent right now (**Connected**, **Partly reachable**, **Can’t reach it**, or **Not checked yet**, which is what a brand-new connection reads until something probes it) plus a **Customize environment** expander. See [Manage a project's connections](/how-to/manage-project-connections) for everything that expander holds.
  </Step>

  <Step title="Write down what the agent must do">
    Before you can test an agent you have to say what "right" means. That is a [Requirement](/concepts/requirements): one thing the agent must do, or must never do, written in the language your business already uses.

    <Note>
      *Ask the Trust Agent:* "Help me capture requirements for this agent from our support policy." Attach the document you already have, and it drafts requirements from it and pauses at a single approval card before saving any of them.
    </Note>

    Or do it by hand: open **Requirements**. An empty project leads with **Add your first requirement** and two ways in — **Extract from your docs**, which pulls them out of a document you upload, and **New requirement**, which adds one at a time.

    <Warning>
      **This step is a gate, not a suggestion.** Requirements come straight after connecting an agent in the authoring order the Trust Agent enforces at run time. Ask it for scenarios before a requirement is saved and it refuses rather than guessing — *"Draft and save the requirements first. I can guide you through that now before we continue."* Everything downstream chains the same way, and the chain is longer than one link: scenarios must be linked to requirements, each requirement needs an evaluator created **and** attached, and every scenario needs expected actions or routes before the agent will simulate or run. A project that skips a link dead-ends at the first thing it tries to run. The whole chain is laid out in [The order is enforced, not suggested](/tutorials/evaluate-with-the-trust-agent#the-order-is-enforced-not-suggested).
    </Warning>

    **You should see:** the **Requirements** list with at least one row, each carrying a handle like `REQ-1` — a bare number, deliberately not zero-padded the way scenario ids are — and a health pill. With nothing linked yet that pill reads **Uncovered**; the other four states are **Passing**, **Failing**, **Partially covered**, and **Not yet run**.
  </Step>

  <Step title="Observe real sessions">
    With the agent connected, pull in the conversations it's already having.

    <Note>
      *Ask the Trust Agent:* "Pull in some of my real conversations so we have material to work from."
    </Note>

    Or do it by hand: open **Sessions** and click **Sync now** — it opens a per-agent picker, so choose your connected agent. Historical sync works for **AWS Bedrock AgentCore** connections only; on the other three platforms the picker lists your agent and then reports that sync isn't supported for it, so use the Trust Agent fallback below to produce your first sessions. Where sync does run, conversations pulled from your platform land in the list. By default the list shows **Session ID**, **Transcript**, **Routed To**, **Tools Called**, **Turns**, **Date**, and **Verdict** — the reserved human Pass/Fail column every project starts with. **Source** is one of the columns you add from **Add column**, and it reads exactly one of **Scenario**, **Playground**, or **External** (see [Sessions](/concepts/sessions)).

    Click any Session to open it. The fly-in leads with the full **Transcript** — every turn, tool calls included — and carries four more tabs: **Annotations**, **Evaluations**, **Test Data** (what TrustAI set up, read back, and cleaned up around this one conversation), and **Details**. Read one end to end; this is the raw material everything downstream grades. A session nothing has scored yet reads **Not evaluated**.

    <Tip>
      **Want a verdict on just this one conversation?** The fly-in's own **Evaluate** action starts a **quick evaluation**, which grades the conversation in place. A *"Quick evaluation started"* toast opens it, the Evaluations tab counts the checks as they land (*"Scoring check 2 of 3…"*) and keeps counting through a page reload, and a finish toast carries a **View** action. It mints no run record, so it appears on the **Evaluations** list as a row with a muted **Quick** pill that opens the conversation it graded rather than a run-detail page. Re-running it replaces the previous verdict.
    </Tip>

    <Tip>
      **Agent has no traffic yet?** Ask the Trust Agent: "Try my agent with a few example questions and show me how it responds." It runs one open-ended conversation against the live agent and summarises what the agent is for, what it can do, the tone it takes, and where its guardrails sit. Nothing is graded — the point is to understand the agent first-hand before you define what "good" means.
    </Tip>

    **You should see:** the Sessions list populated, and at least one Session you've read end to end.
  </Step>

  <Step title="Adopt starter evaluators and scenarios">
    A new project doesn't start from a blank slate: two curated catalogs ship ready to adopt in one move, and the Trust Agent can draft coverage specific to your agent. With a requirement saved, the agent will now generate scenarios instead of declining.

    <Note>
      *Ask the Trust Agent:* "Generate a first set of test scenarios for my agent." Then: "Add some security scenarios that probe for unsafe or off-policy answers."
    </Note>

    The agent proposes [Scenarios](/concepts/scenarios) — each a persona plus a goal, the test cases your evaluations will run, each linked to the requirement it exercises — and pauses with an approval card showing exactly what it will create before anything is saved. One batch of changes is one all-or-nothing card, never a card per item. Approve, and they land in your Scenarios list.

    The manual path is the two catalogs:

    - On **Evaluators**, click **Add recommended**. The modal is headed **Add recommended evaluators** and holds 11 presets — **5 Quality** and **6 Safety** — each a plain LLM judge that returns a pass or a fail. Most arrive pre-checked — untick anything that doesn't fit your agent. The confirm button counts whatever is currently selected (**"Add 4 evaluators"**), and anything already in the project is muted as **In your project**. Three presets carry a **Tailor first** badge, because their criteria depend on what *your* agent is allowed to do — it's a nudge, not a block.
    - On **Scenarios**, click **Add recommended scenarios** to adopt from the 10 [recommended security scenarios](/concepts/trust-library) — one per failure mode in the OWASP Agentic Top 10 (2026), each already paired with the safety checks that grade it. **Select all *N*** takes everything still selectable — all ten on a fresh project. The confirm step offers two actions and a way out: **Add & tailor to your agent** is the primary, **Add without tailoring** the secondary, and **Cancel** closes it. Tailoring finishes the adoption immediately and then runs unattended in the background, rewriting generic probes against what your agent actually does; with no agent connected the primary is disabled under the nudge **"Connect an agent to tailor these"**.

    Everything you adopt becomes an ordinary, fully editable evaluator or scenario — no special status. Adopted catalog scenarios arrive **unlinked** from your requirements, with **Expected actions** and **Expected routes** empty.

    **Link each scenario to the requirement it exercises before you go on.** Ask the Trust Agent — *"Link each scenario to the requirement it covers"* — or do it by hand from a scenario's fly-in, on the **Expected Output** tab under **REQUIREMENTS** → **Link requirement**. The authoring order the agent enforces at run time reads the link, so a project full of unlinked scenarios stalls the agent at the next step even though the records all exist.

    **Does your test need records to exist first?** A scenario that has to find an open case, an order, or an account before the conversation starts carries a [test data](/concepts/test-data) plan on its own **Test Data** tab — five step cards covering what the run creates, the conversation, what it reads back, what should have happened, and the cleanup that runs every time and cannot be turned off. **Set up with AI** drafts one from a sentence. None of the recommended security scenarios ships test data, so you can skip this on a first pass and come back when a scenario needs it.

    <Tip>
      Writing one from scratch instead? **New evaluator** offers two kinds: **LLM judge** (freeform criteria another model grades against) and **Groundedness judge** (checks every claim against the reference material attached to a scenario's **Expected Output**). Structural checks — **Expected routes** and **Expected actions** — are no longer something you create as an evaluator; they live on each scenario's **Expected Output** tab.
    </Tip>

    **You should see:** the Scenarios list populated, each scenario carrying a stable id like `SCN-000022`, and the Evaluators list showing your adopted judges.
  </Step>

  <Step title="Run your first evaluation">
    Now run those scenarios against your connected agent.

    <Note>
      *Ask the Trust Agent:* "Run my first evaluation against the connected agent."
    </Note>

    If you skipped the linking beat in step 5, the Trust Agent refuses here and names the missing step rather than guessing. The manual **Run** split button below is ungated, so it still launches — but the run grades against whatever expected output the scenarios actually carry.

    By hand: on **Scenarios**, use the **Run** split button (select specific scenarios first, or leave the selection empty to run the current view). Clicking **Run** launches **Run & evaluate**; the chevron beside it exposes both modes explicitly:

    | Mode | What it does |
    | --- | --- |
    | **Run only** | Simulate without grading |
    | **Run & evaluate** | Simulate + grade → creates an evaluation |

    Either opens the launcher, which previews the fan-out before anything starts — how many scenarios, how many conversations will be simulated, and how many evaluator runs that adds up to. Each scenario is simulated once per attached persona, then graded by the evaluators inherited from that scenario. **Repeat each test case** (1–4) reruns every case so you can see how reliably the agent passes. Confirm with **Run evaluation**.

    The same launcher opens from **New evaluation** on the **Evaluations** page, where you additionally choose what to evaluate — **Sessions** (each conversation's user message is replayed to your connected agent and the answer it gives *now* is graded) or **Scenarios**. See [Evaluate captured sessions](/how-to/evaluate-sessions) for what that replay does and does not cover.

    You stay on the Scenarios list while the run executes: each scenario shows a live progress badge that settles as it finishes.

    **You should see:** per-scenario badges settling, and a new run appearing on the **Evaluations** page.
  </Step>

  <Step title="Read the results">
    Open the run from **Evaluations**.

    The run header carries the completed count and the date it ran, led by the pass rate — or by **Not graded**, when the run carries no behavioural grade at all. Where the record can evidence *why*, the header says so: a deliberate simulation reads **Run only — nothing was graded**, and a graded run that inherited no evaluators reads **Not graded — no evaluators**. The results body then leads with a single headline stat, **Conversations passed**, e.g. "6 of 10 conversations". That stat reads **Not graded** too, captioned "No conversation has been scored yet", whenever nothing on the run was behaviourally graded. Neither place ever shows a fabricated number.

    A second headline, **evaluator accuracy**, appears once you've recorded human Pass/Fail verdicts on sessions — it measures how often the automated judges agree with a person, grading the judges rather than the agent. Until then it is absent from the header entirely, and the **Evaluator accuracy** column on the **Evaluations** list reads as empty.

    Below that is the results table. It opens **By scenario** — one summary per scenario and persona, expandable to its individual attempts. To flatten it, open the **Columns** menu in the results toolbar: the **View** toggle sits at the very top, offering **By scenario** and **Flat**. Each row names the persona that drove the conversation, and carries the **Final verdict** plus one column per evaluator, so you can see *which* check failed and *who* the agent struggled with.

    Open any result to read the full conversation. The transcript labels how the result was produced, and there are exactly two labels: **Simulated** (the run drove a fresh conversation with your agent and scored that) or **Replayed** (the run replayed the scenario's saved input and scored the agent against it).

    **Five outcomes leave the pass-rate denominator, and only four of them are the environment's fault.** The four environmental ones render grey under three headings — **Guardrail blocked**, **Environment problem**, and **Access blocked** — carrying the line *"Environment problem — not the agent · Excluded from the score."* The fifth is different, and reading it as an environment problem is the mistake to avoid: when an action the agent itself runs returns an error, the conversation reads amber as **Couldn't test**, summarised as *"Not scored because an action the agent runs returned an error."* Nothing outside the agent broke — the agent's own tool call did, and there was no answer left to grade.

    Because a run can hide either kind, the **Evaluations** list carries an amber count beside the pass rate, so a green rate never renders without its caveat. Read that count before you read the percentage.

    **You should see:** a scored run with a headline stat, a per-scenario results table, readable transcripts behind every verdict, and — if anything went wrong — an amber count that tells you how much of the run never got graded.
  </Step>
</Steps>

## What TrustAI knows about your agent

Alongside the loop above, TrustAI keeps a read of the agent itself — its **Agent Profile**. Open it from the **[Playground](/concepts/playground)** topbar: pick the build in the agent picker and press the info button beside it, tooltipped **Agent profile**. That is the only door at this release — the single **Connections** tab has no profile entry point yet. The fly-in opens over the conversation without navigating away, is headed **Agent profile**, and has three tabs — **Overview**, **Tools**, and **Sources**.

**You do not have to ask for the first one.** Connecting an agent queues its profile capture, so a freshly connected agent reads **Profile queued** or **Profile in progress** rather than sitting empty. The other lifecycle pills are **Profile available**, **Profile failed**, and **Profile out of date**. A capture that failed says why and offers **Try capturing again**; the empty state — "No profile has been generated for this agent build yet." with a **Generate profile** button — belongs to an agent whose capture never ran at all.

Coverage is reported in words, not percentages: **Captured**, **Partial**, or **Limited**. Each source the profile looked at reads **Available**, **Not exposed**, **Not sampled**, or **Not run** — four distinct answers, and collapsing them into one "unavailable" loses the thing you needed to know.

The profile is what makes the Trust Agent's exploration and scenario drafting specific to your agent instead of generic, and it is what a tailoring run reads when you adopt recommended scenarios with **Add & tailor to your agent**. Note the platform limit: capability discovery is implemented for Conversational HTTP, Claude Managed Agent, and Salesforce Agentforce connections. On an AgentCore connection the panel reports that agent profiling isn't available for this connection yet. See [Review an agent profile](/how-to/review-an-agent-profile).

## You've walked the loop once

Connect, specify, observe, define coverage, run, read — that's [the evaluation loop](/concepts/evaluation-loop), end to end, once. From here it's depth, not new shape: author expected outputs on the scenarios that matter, tailor the recommended evaluators to your agent's rules, work the **Gaps** view on [Requirements](/concepts/requirements) down, and [record human verdicts on sessions](/how-to/annotate-sessions) so evaluator accuracy has ground truth to grade against.
