FT's connection model has a discriminated set of auth postures (`auth_type` on a System's connection), and none of the credentialed ones ever puts a secret's bytes at rest anywhere a test or a read-back can see. Choose the posture for the authentication your test actually performs.

## A public site needs no credential

`auth_type: "none"` is a first-class posture for a target that needs nothing to reach — a public web page or a public API. It's not a placeholder or a workaround; it's the correct configuration for a public target, and it's what [Your first green test](/functional/get-started/first-green-test) uses.

```json
{ "auth_type": "none", "url": "https://example.com" }
```

The `none` connection accepts a target URL but no `username`, `credential_id`, or `login_strategy`. If the scenario signs into a browser form with a managed password, configure a browser-form connection instead, even when its login page is public.

## Managed browser sign-in

Use `auth_type: "basic"` with `login_strategy: "browser_form"`, the target `base_url`, the account's `username`, and the credential ID returned by the managed request. This posture supplies credentials for browser actions; `browser_form` distinguishes it from HTTP Basic authentication.

```json
{
  "auth_type": "basic",
  "base_url": "https://app.example",
  "username": "test-user",
  "login_strategy": "browser_form",
  "credential_id": "CRD-example"
}
```

Replace the example URL, username and credential ID with the actual target and managed request result. Write explicit sign-in steps that fill `{{credential.USERNAME}}` and `{{credential.PASSWORD}}`, submit the form, and verify the authenticated identity. The connection supplies the values; the browser steps establish the session. For SSO or other login mechanisms, consult the current connection schema and establish the required browser session explicitly.

## A real secret is referenced, never inlined

For a target that does need a stored credential — HTTP Basic, an API key, a bearer token, OAuth client credentials, or the Salesforce JWT-bearer posture — the System's connection carries only **non-secret config plus a pointer** to the secret in a secret provider. The pointer is sealed at rest; the plaintext secret is never echoed back, never logged, and never visible in a read of the System.

A test references a credential by **slot name**, using the placeholder:

```
{{credential.SLOT_NAME}}
```

`credential_slots` on the System's connection config names the bounded set of slot identifiers (case-sensitive, validated) a test may reference this way. A slot name is safe to write anywhere in an authored test — it's a name, not the value — and the resolved value is substituted only at run time, in the run's own process environment.

<Warning>
  A persisted test scenario is deep-swept for anything secret-shaped before it's ever saved — a key whose *name* looks like a credential (`token`, `key`, `secret`, `sid`, `cookie`, `authorization`, …) or a *value* shaped like one (a Bearer token, a PEM header, a long high-entropy string) is refused at the write boundary, wherever it appears in the structure. Don't try to work around `{{credential.SLOT}}` by pasting a real secret into a step's intent text or a setup field — it will be rejected, not silently accepted.
</Warning>

## Requesting a credential

Discover `functional_credentials_request` and request the form appropriate for the target. Send the returned URL to the customer, let them complete the managed form, and poll `functional_credentials_request_get` with the request ID. Continue when its status is `completed`; use the returned credential ID and slot names, never the secret values. An expired or declined request needs a new customer handoff, not a guessed password.

For a `username_password` form, use the `basic` / `browser_form` connection above, set its `credential_id` and username, omit `credential_slots`, and reference `{{credential.PASSWORD}}` in browser steps. The form's returned field names are not a bundle declaration. Use an explicit `credential_slots` list only for a `bundle` credential, following the current tool schema. Give requested fields clear labels identifying the account and whether the customer is supplying an existing secret or choosing a password for a new test account.

## Choosing a posture

| Your target | Posture |
| --- | --- |
| A public page or API, nothing to authenticate | `auth_type: "none"` |
| A browser form your test signs into with a managed username/password | `auth_type: "basic"`, `login_strategy: "browser_form"`, `base_url`, `username`, and `credential_id`; explicit sign-in steps |
| A stored API credential your test's own steps don't touch, but an [API check](/functional/concepts/verification) needs to call the target's API under | `configured_api_identity:<system>` on the check, backed by the System's credentialed connection |
| A secret value a browser step needs | `{{credential.PASSWORD}}` for a `username_password` credential; named `{{credential.SLOT}}` values and `credential_slots` for a `bundle` credential |
