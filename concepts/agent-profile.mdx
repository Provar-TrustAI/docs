An Agent Profile answers a question that is surprisingly hard to answer about a deployed agent: **what can this thing actually do?** Not what the spec says, and not what it did on one conversation — what tools it exposes, what knowledge it draws on, how it identifies itself, and how much of that TrustAI was able to see.

A profile is a **record**, not a probe. It was captured at a point in time against one build of your agent, and reading it never re-contacts the platform. That's the property that makes it reviewable: two people opening the same profile a week apart see the same thing.

<Note>
  **Agent Profile is not [Agent Version](/concepts/agent-versions).** An Agent Version is the agent build itself — the thing you evaluate against. An Agent Profile *describes* one of those builds. One version, one profile; a second version gets its own. If you're choosing what to run an evaluation against, you want an Agent Version. If you're asking what a given build is capable of, you want its profile.
</Note>

## What a profile captures

A profile records four kinds of fact about a build:

- **Identity and behavior** — how the agent presents itself, and how it's configured to behave.
- **Declared rules** — the operating rules the connected platform publishes for this agent, carried word for word and evidenced back to the exact place each one was read from. They render as **Critical behavioral rules**. Nothing is summarized into a rule: a platform that publishes a policy document has that document ride along as a source instead, because splitting a document into rules would be invention.
- **Tools** — the actions it exposes, each with the inputs it published at capture time and the platform's own answer to *does this action ask the person first?*
- **Knowledge sources** — the material it can draw on to answer.

Where the catalog groups into subject areas, the profile also carries **Topics this version covers**. A platform that declares its own groupings — Salesforce Agentforce does — has them carried across one for one; otherwise the topics are inferred by grouping the agent's own actions. The section names which of the two you are reading, and it is simply absent when nothing groups.

Tool inputs are worth a special note. Capture stores the exact bytes it recorded, content-addressed alongside the revision, and reading them later serves **those** bytes back. The provider is never re-contacted, so an input contract you read today cannot quietly have changed underneath a review you did yesterday.

The confirm gate has three answers, never two: **Asks the person first**, **Runs without asking**, and **Not published by the platform**. The third is not a quiet "no" — it means the platform never said, which is a different fact to plan an approval or a decline scenario around.

## The versioned unit is the revision

Capture doesn't overwrite. Each run produces a new **profile revision** — an immutable snapshot — and the build accumulates them.

That distinction shows up in a place that matters: **review is per-revision.** Approving a profile approves the exact revision you read, not the build's moving head. Regenerate afterwards and the new revision is unreviewed, because nobody has looked at it yet. This is deliberate; a review that silently carried forward onto content nobody examined would be worthless.

Your own edits work the other way. A **human overlay** — the corrections and notes you add on top of what capture found — belongs to the **build**, not to a revision, and there's one per build. Regenerating the profile doesn't discard it.

## Two different pins

Two things in TrustAI pin themselves to something in this area, and they pin to different things:

| What | Pins to | Why |
|---|---|---|
| An [Evaluation](/concepts/evaluations) | An **Agent Version** | The run grades a specific build's behavior |
| A [Trust Agent](/concepts/trust-agent) session | A **profile revision** | The session records exactly what it understood the agent to be |

A Trust Agent session resolves one effective revision at creation and holds it for the session's life, so its answers stay consistent even if the profile is regenerated mid-conversation. A build with no captured profile has nothing to pin, and says so plainly.

## Reading the states

The profile surface is built around one commitment: **absence is always a named state.** Nothing is left blank, and nothing collapses several different reasons into a single "unavailable".

### Lifecycle

You rarely start a capture by hand. Connecting an agent queues its first profile capture automatically, in the background, so a build is usually already capturing — or already captured — by the time you go looking. A queue that could not be placed never blocks the connection; the capture is still there to request from the profile panel.

A capture moves through five states, and the pill reads exactly:

| Pill | Means |
|---|---|
| **Profile queued** | Capture is waiting to start |
| **Profile in progress** | Capture is running |
| **Profile available** | A profile is ready to read |
| **Profile failed** | Capture ran and didn't succeed |
| **Profile out of date** | A profile exists, but the build has moved on |

One outcome deliberately moved out of the success column. A Salesforce Agentforce capture that reached the org but read no tools and no operating instructions is recorded as **Profile failed**, not as an empty profile stamped ready — an identity-only record presented as complete is worse than no record at all. The failure names the fix rather than the fault: check that the connected user can read the agent's active version and its topics and actions, then capture again.

One label differs by vantage point. **Profile available** is the capture lifecycle's own word for a healthy profile; the profile fly-in's header reads **Version-pinned profile** instead, naming the pinning contract rather than repeating a status you have already clicked through. Same healthy profile, two vocabularies — and since the fly-in is where a profile opens, **Version-pinned profile** is the one you actually see.

### Coverage

Each dimension a capture inspects carries a coverage level — **Captured**, **Partial**, or **Limited**. There are no percentages here, and no complete/incomplete. Coverage tells you how thoroughly TrustAI got to look, so you know how much weight the profile can bear.

### The four availabilities

Where a profile can't tell you something, it tells you *which kind* of nothing you're looking at:

| State | Means |
|---|---|
| **Available** | The material reached the capture |
| **Not exposed** | The connector never surfaced this kind of material at all |
| **Not sampled** | It exists, but no conversations covering it were sampled |
| **Not run** | The probe that would have found it wasn't run |

These are four different facts and the product never merges them. "The platform doesn't offer this" and "we didn't look" lead to opposite next actions — one is a platform limit you plan around, the other is a gap you can close by capturing again.

### Review

A revision sits in one of three review states — **Pending review**, **Approved**, or **Changes requested** — and the two actions available on it are **Approve** and **Request changes**. This page explains what the states mean; conducting a review is the subject of its own guide: [Review an agent profile](/how-to/review-an-agent-profile).

## Which platforms can be profiled

Capability discovery reaches **three** platforms:

- Conversational HTTP
- Claude Managed Agent
- Salesforce Agentforce

Anything else, including **AWS Bedrock AgentCore**, isn't profiled. An AgentCore connection says so directly — *"Agent profiling isn't available for this connection yet."* — and offers no retry, because retrying wouldn't change the answer. That's a platform limit, not a failure to work around.

Salesforce Agentforce capture reads through the same admin authorization every new connection is created with, records each action's declared inputs, and reads the agent version that is actually live in the org. Where several candidate versions exist and the live one can't be identified, capture says so rather than guessing at the highest-numbered one — a profile of the wrong version would be a confident, wrong answer.

A connection on a supported platform can still come back unsuccessful — an unreachable endpoint, a half-configured connector, missing credentials. Those are **Profile failed**, they carry a plain-language reason, and they *are* worth retrying — the revision offers **Try capturing again**. (An AgentCore connection offers no retry at all, as above.)

## Where you find one

**The Playground topbar.** Open the [Playground](/concepts/playground), pick the build in the agent picker, and press the info button beside it — its tooltip reads **Agent profile**. The profile opens as a fly-in over the conversation, so you never lose your place, and **Esc** closes it.

That is the only door at this release. A connection card used to carry a row that opened the profile beside the build it describes, but that row belonged to the retired two-tab connection settings; the single **Connections** tab that replaced them has no profile entry point yet.
