An [Evaluator](/concepts/evaluators)'s scores are worth trusting only if the judge agrees with informed humans. This how-to walks the **Calibrate** tab on an LLM judge: run the judge against scenarios you have already marked pass or fail, read the agreement, tighten the grading rules where you and the judge disagree, and re-check until the number holds. When you're done:

- You'll have a measured agreement rate between the judge and your own verdicts — the same judge, prompt, and parser your real [Evaluations](/concepts/evaluations) run
- Every check is kept in **Calibration history**, so you can show your team how agreement moved as the rules improved

The [Trust Agent](/concepts/trust-agent)'s evaluator authoring is calibration-first: ask it to *"tighten the goal-completion evaluator's rules"* and it proposes the edit as an [approval-gated write](/how-to/approve-agent-writes), so you see how the judge's scores match your own pass/fail judgments before relying on it at scale. Running checks yourself and working the disagreement table happens on the **Calibrate** tab, which is what this page covers.

## Which evaluators can be calibrated

The **Calibrate** tab is offered for **LLM judge** evaluators only. It is a positive allow-list on that one kind, not a rule about deterministic checks, so three of the four evaluator kinds have no **Calibrate** tab at all:

| Kind | Calibrate tab | Why |
| --- | --- | --- |
| LLM judge | Yes | A model applies your written criteria, so its agreement with you is worth measuring |
| Groundedness judge | No | It grades claims against the scenario's **Reference material** with a built-in rubric — you tune it through optional guidance and the source documents, not through calibration |
| Structured match | No | A deterministic comparison of what the agent did against the scenario's expectations — the same input always produces the same verdict |
| Outcome grounded | No | Scores against the connected system's end state captured at run time, not against a written rubric |

If the panel you opened has no **Calibrate** tab, that is the reason — the tab is hidden for those kinds, never shown disabled.

## Prerequisites

- **An LLM judge evaluator.** Build one in the create flow (see [Build your first Evaluator](/tutorials/build-first-evaluator)) or adopt one from the recommended library and tailor it.
- **Scenarios you have marked pass or fail.** Calibration compares the judge's verdict with yours on the same material, so your own verdicts are the ground truth.

You record those verdicts in the **Verdict** column on the [Scenarios](/concepts/scenarios#the-verdict-column) list: click the cell's **Pass** or **Fail** button, and click the active one again to clear it. That column is the labeling channel calibration reads. It is *not* the same thing as the **Verdict** annotation on a session, which grades evaluator accuracy on a completed run — see [Annotations](/concepts/annotations).

Aim for 10–20 marked scenarios spanning both passes and fails — don't label only the easy cases. Each check judges at most 20 anyway.

## Calibrate the evaluator

<Steps>
  <Step title="Open the Calibrate tab">
    Open **Evaluators** in your Project and click the LLM judge you want to check. Its side panel opens with the tabs **Overview**, **Criteria**, **Calibrate**, and **Runs** — in that order, with **Calibrate** sitting between the rubric editor and the run history. **Runs** appends a count (**Runs · 1**) once the evaluator has been used in an evaluation. Pick **Calibrate**.

    **You should see:** a **Check agreement** section — a one-line explainer, the sample pickers, and a **Calibrate** button. If you see **No verdicts to calibrate against yet** instead, the project carries no pass/fail column at all; the empty state links you to the Scenarios list rather than showing a dead button.
  </Step>

  <Step title="Confirm the sample">
    There is normally nothing to choose here. The **Scenarios** picker resolves to a single option, **All scenarios** — a project has exactly one calibration source, its own scenarios — and it is selected for you. The **Your verdicts** picker holds the project's pass/fail column, auto-picked when there is only one (there is one by default, named **Verdict**).

    Once both picks land, a census line under **Your verdicts** confirms the scope — for example, *"Your pass/fail column on All scenarios — 10 of 10 rows have a verdict."* If the project has a pass/fail column but nothing marked on it yet, that line is replaced by *"None of your scenarios are marked pass or fail yet."* and a link that takes you to the Scenarios list to mark some.
  </Step>

  <Step title="Run the check">
    Click **Calibrate**. Calibration never runs automatically — each check costs live judge calls, so you own the moment. While it runs the button reads **Calibrating…** and a progress strip names the real count being judged (*"Checking agreement on 10 scenarios — takes about a minute"*); the caption next to the button sets the ceiling up front: *"Checks up to 20 rows — takes about a minute."*

    <Note>
      Calibration runs the **exact production judge** — the same model, the same assembled prompt, the same verdict parser your evaluation runs use, pinned to deterministic scoring. The agreement you measure here is the agreement you'll get in real runs; there is no separate "preview judge."
    </Note>

    <Warning>
      **Calibration is metered.** Each sampled scenario is one billable check against your [workspace credit pool](/concepts/overview#workspace-credits), and the credit check runs *before* any judging starts. If your workspace has reached its credit limit the check is refused outright rather than running slowly — nothing is judged and no result is written. Your admin manages the pool, which resets monthly.
      {/* ACCURACY-AUDIT-PENDING: the refusal is verified in the API (services/api/src/domain/evaluators/service.py:1438-1451 gates admission and raises a 402 before judging). A credit-capped workspace is not reachable on the instance used for this pass, so how the Calibrate tab renders that refusal is described at behavior level only. */}
    </Warning>
  </Step>

  <Step title="Read the agreement">
    The result lands under **Latest check** as an **Agreement** headline — the percentage of sampled scenarios where the judge reached the same verdict you did, captioned *"Compared with your verdicts on 10 rows"*.

    Click **Show details** for the verdict breakdown, **How the verdicts break down** — four counts:

    - **Both said pass** and **Both said fail** — the agreements
    - **The judge passed it, you failed it** and **The judge failed it, you passed it** — the two directions of disagreement, which need different fixes

    Two plain-language lines below the breakdown give the directional rates: **When the judge said pass, you agreed** and **When you said pass, the judge agreed**.

    Aim for roughly **90%+ agreement** on a pass/fail rubric before relying on the judge at scale. Don't chase 100% — as the caption under the readout puts it, perfect agreement on a small set usually means the rubric over-fits those rows.
  </Step>

  <Step title="Work the disagreements">
    Below the readout, the **Row by row — disagreements first** table lists every sampled scenario across four columns — **Scenario**, **The judge**, **You**, and **Verdicts**, which reads *Agree* or *Disagree*. Disagreements sort to the top, because as the table's own footer says, the disagreements are the data: they show exactly where the rubric is wrong.

    For each disagreement, decide who's right:

    - **The judge is wrong** — the rubric is the problem. Switch to the **Criteria** tab and tighten the rules: add a **Passes when…** rule for behavior the judge wrongly failed, or a **Fails when…** rule for behavior it wrongly let through, then commit with **Save grading rules**. [Write an effective LLM-judge prompt](/how-to/write-llm-judge-prompt) covers the craft of rules that calibrate well.
    - **Your verdict is wrong** — it happens; correct the scenario's **Verdict** rather than bending the rubric around a bad ground truth.
    - **Genuinely ambiguous** — a healthy rubric tolerates a small disagreement rate on cases a second human reviewer would also debate. Don't add a rule for every edge.
  </Step>

  <Step title="Re-check and watch the history">
    Editing the grading rules after a check raises a quiet warning above the result — **Criteria changed since this check** — because the agreement on screen reflects the old rubric. Click **Re-calibrate** (the button keeps that name once a result exists) to check the current rules; the prior result is kept, not discarded. Renaming the evaluator doesn't trigger the warning — the app tracks rule edits specifically.

    Every check lands in **Calibration history**, newest first with a **Latest** pill: agreement, sample size, the evaluator revision it tested, and the date — *"90% agreement · 10 rows · Revision 1"*. Click an older entry to swap the result panel to that run — the history is your audit trail for *"which version of the rules earned this agreement?"*

    Repeat the check → disagreements → rules loop until agreement holds where you want it. Then run your [Evaluations](/concepts/evaluations) — the run detail's evaluator-accuracy headline keeps grading the judges against human verdicts in production.
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The tab shows 'No verdicts to calibrate against yet'">
    This state is about the *column*, not the verdicts: the project carries no pass/fail column for calibration to ground on. The empty state explains that and offers a single link — **Open scenarios to mark verdicts** — with deliberately no picker and no dead **Calibrate** button. A project ships with a **Verdict** column by default, so you'll usually see this only where that column was removed.
  </Accordion>

  <Accordion title="The pickers resolve, but the check button stays disabled">
    The column exists but nothing is marked on it. The line under **Your verdicts** reads *"None of your scenarios are marked pass or fail yet."* with a link — **Open All scenarios to mark rows** — straight to the Scenarios list. Mark a few passes and fails and the **Calibrate** button enables; the census refreshes without a reload.
  </Accordion>

  <Accordion title="The check fails with 'Calibration didn't finish'">
    The check didn't complete — the banner offers **Try again**, and your last successful result is unchanged (it stays collapsed underneath). Calibration is synchronous and bounded at 20 samples, so a retry is cheap. If retries keep failing immediately, check with your workspace admin whether the credit pool is exhausted — a run refused at the credit gate never reaches the judge.
  </Accordion>

  <Accordion title="My evaluator has no Calibrate tab">
    Only LLM judge evaluators offer it. A Groundedness judge, a Structured match evaluator, and an Outcome grounded evaluator all open without the tab — see [Which evaluators can be calibrated](#which-evaluators-can-be-calibrated) above.
  </Accordion>
</AccordionGroup>

Developers who want the calibration endpoints and the run history's response shape can find them in the [API Reference](/api-reference).
