FT's connection model has a discriminated set of auth postures (`auth_type` on a System's connection), and none of the credentialed ones ever puts a secret's bytes at rest anywhere a test or a read-back can see. Three postures cover most authoring decisions.

## A public site needs no credential

`auth_type: "none"` is a first-class posture for a target that needs nothing to reach — a public web page or a public API. It's not a placeholder or a workaround; it's the correct configuration for a public target, and it's what [Your first green test](/functional/get-started/first-green-test) uses.

```json
{ "auth_type": "none", "url": "https://example.com" }
```

**Signing in, when a scenario needs it, is an ordinary test step** — not a System-level credential. A public system with no stored credential can still carry a test whose first step is "sign in as a standard user," the same way any other browser action is a step.

## A real secret is referenced, never inlined

For a target that does need a stored credential — HTTP Basic, an API key, a bearer token, OAuth client credentials, or the Salesforce JWT-bearer posture — the System's connection carries only **non-secret config plus a pointer** to the secret in a secret provider. The pointer is sealed at rest; the plaintext secret is never echoed back, never logged, and never visible in a read of the System.

A test references a credential by **slot name**, using the placeholder:

```
{{credential.SLOT_NAME}}
```

`credential_slots` on the System's connection config names the bounded set of slot identifiers (case-sensitive, validated) a test may reference this way. A slot name is safe to write anywhere in an authored test — it's a name, not the value — and the resolved value is substituted only at run time, in the run's own process environment.

<Warning>
  A persisted test scenario is deep-swept for anything secret-shaped before it's ever saved — a key whose *name* looks like a credential (`token`, `key`, `secret`, `sid`, `cookie`, `authorization`, …) or a *value* shaped like one (a Bearer token, a PEM header, a long high-entropy string) is refused at the write boundary, wherever it appears in the structure. Don't try to work around `{{credential.SLOT}}` by pasting a real secret into a step's intent text or a setup field — it will be rejected, not silently accepted.
</Warning>

## Coming in this release: requesting a credential

A credential-request flow is being built (FUN-4914) so an agent authoring a test doesn't have to already know a workspace's slot names. The intended shape: the agent asks for a credential by describing what it needs, a human completes a short FT form out of band (the plaintext never passes through the agent), and the agent polls for the resulting credential id and the slot names it can now reference. This is the intended flow, not yet shipped — treat any current credential setup as something a human still configures directly on the System.

## Choosing a posture

| Your target | Posture |
| --- | --- |
| A public page or API, nothing to authenticate | `auth_type: "none"` |
| A login your test drives itself (a form, an SSO redirect) | `auth_type: "none"` on the System, sign-in as a test step |
| A stored API credential your test's own steps don't touch, but an [API check](/functional/concepts/verification) needs to call the target's API under | `configured_api_identity:<system>` on the check, backed by the System's credentialed connection |
| A secret value a step or a hook needs inline | `{{credential.SLOT}}`, backed by a slot on the System's `credential_slots` |
