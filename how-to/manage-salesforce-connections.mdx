A Salesforce org is authorized **once for the whole workspace**, not once per [Project](/concepts/projects). Several Projects can point at the same org, and they all share the one External Client App Trust AI deployed there. **Workspace Settings → Connected orgs** is where that shared picture lives: one row per org, the Projects using it, and the two ways to remove it.

This page covers reading and removing connections. Creating one belongs to a Project — either in chat with the [Trust Agent](/concepts/trust-agent) or from **Project Settings → Connections → Connect an agent** — and both routes are covered in [Connect a Salesforce Agentforce agent](/how-to/connect-agentforce). There is no **Connect** button on this tab; a workspace with none yet reads *"No Salesforce connections yet. Connect an org from a project's chat to see it here."* That sentence names only the chat because it predates the Settings route; the Settings route works too.

<Warning>
  **Disconnect** and **Delete** sit side by side and read alike. Only one of them reaches into your Salesforce org, and only one of them clears the connection out of every Project. They are not the same pair of ends — read [Disconnect vs Delete](#disconnect-vs-delete) before you use either.
</Warning>

## Prerequisites

- A **Trust AI account** in the workspace, and access to at least one Project that holds a Salesforce connection. The list is scoped to the Projects you can reach, so two admins can see different rows on the same tab.
- To **Disconnect**: **Editor** access on the Project the connection belongs to — plus a **Salesforce administrator** who can sign in, because the teardown needs a fresh admin token.
- To **Delete**: **Admin** on every Project listed under **Used by** — not just one of them. Delete removes each of those Projects' connection records in one action, and each removal is authorized on its own Project, so Admin on two of three Projects is not enough. Delete is the more restricted of the two.

## Open the Connected orgs tab

Click **Workspace Settings** in the sidebar footer, then the **Connected orgs** tab — fifth of the six, after **Credits**. It is a stable route, so a bookmark or a refresh lands back on it. See [Administer workspace access](/how-to/administer-workspace-access) for the rest of the tab strip.

The panel is titled **Connected orgs**, subtitled *"The Salesforce orgs your workspace is connected to, and the projects that use each one."*

<Note>
  The tab is deliberately **not** called "Connections". That word names a *Project's* settings tab, which lists the agents that one Project tests. One word cannot name both surfaces, and neither is a subset of the other.
</Note>

Under the subtitle sits a link back to the Project side: *"The agents a project tests are set up in that project — open **Connections in *\<project\>*** to manage them."* If you arrived here from a Project's Connections tab, that link returns you to the Project you left rather than to whichever one the folded list happens to name first.

## Read a connection row

A row carries five things, and two of them are verdicts that answer different questions:

| Field | What it is |
|---|---|
| Org | The org's **My Domain** host — for example `acme.my.salesforce.com`. Never a raw id. One exception: a connection that recorded neither a My Domain nor an org URL falls back to the connection's own name here, so a row labelled with a nickname rather than a host is a connection missing its org URL. |
| Setup badge | **Setting up**, **Needs admin**, or **Setup failed** — shown only while setup still has something to say. |
| Reachability pill | **Connected**, **Partly reachable**, **Can't reach it**, or **Not checked yet**. Always shown. |
| **Used by** | The Projects that use this org, by name, comma-separated. |
| **Sign-in** | How this connection authenticates. |

<Note>
  A row does **not** list the agents reachable through the connection. Release notes for this surface describe a reachable-agents list; the shipped row has no such field. The agents a Project drives live on that Project's own **Settings → Connections** tab.
</Note>

### Two verdicts, not one

The two pills are not interchangeable, and you read them in order.

**The setup badge answers "is setup finished?"** Three states render:

| Badge | Meaning |
|---|---|
| **Setting up** | Trust AI is still finishing setup in your Salesforce org. |
| **Needs admin** | A Salesforce admin has to finish authorizing this connection. |
| **Setup failed** | Setup didn't complete. Reconnect to try again. |

A finished setup shows **no badge at all**. That is deliberate: "Connected" is also the reachability pill's word, and a green setup badge sitting beside a pill that says the org can't be reached would be two verdicts contradicting each other. So once setup is done, the badge steps aside and the pill speaks.

**The reachability pill answers "can Trust AI reach it right now?"**

| Pill | Meaning |
|---|---|
| **Connected** | The last probe reached the org. |
| **Partly reachable** | Some of what Trust AI needs answered and some did not. |
| **Can't reach it** | The last probe failed. |
| **Not checked yet** | Nothing has been probed. Health is never assumed green. |

One org can be connected in several Projects, so this pill is folded across all of them and can never read healthier than the worst Project's own result. A green pill therefore means every Project using the org reached it.

These four words belong to the connection surfaces only. The Trust Agent's side rail has its own health vocabulary for the **Connected agent** card, and the two sets do not map onto each other.

### Sign-in methods

The **Sign-in** line names how the connection authenticates, in this surface's own wording:

| Label | Connection type |
|---|---|
| **Admin authorization** | An administrator signed in once and approved Trust AI. This is how new connections are made. |
| **App key & secret** | Legacy — wired to an app your admin created. |
| **Certificate (JWT)** | Legacy. |
| **Username & password** | Legacy. |

An unrecognized method falls back to the generic **Salesforce sign-in**, and a connection with no recorded method omits the **Sign-in** line entirely.

<Note>
  These four labels are specific to this surface. The in-chat connect card names the same methods differently, and so does a legacy connection's edit form. Read each surface in its own words rather than mapping one onto another.
</Note>

## One row per org, however many Projects use it

An org connected in five Projects mints five connection records — one per Project, all pointing at the same provisioned org. The tab folds them into **one row**, and lists all five Projects under **Used by**.

The fold is on the org's My Domain, so it holds even when the Projects were connected through different-looking URLs: a Lightning host (`acme.lightning.force.com`) and a My Domain host (`acme.my.salesforce.com`) resolve to the same org and land on the same row. A connection that recorded no host at all still folds if Trust AI knows which org it bootstrapped; only a connection with neither stands alone, labelled by its own name. Two rows usually mean two orgs — check the **Org** label on both before you assume it.

This is also why the removal actions read as org-level: whatever you click applies to the org named on the row, not to the Project you happen to be standing in.

## Reuse a connection in another Project

You never authorize the same org twice. Wherever you connect Salesforce in a Project — in chat with the Trust Agent, or from **Project Settings → Connections → Connect an agent** — step one carries the same offer when the workspace has already authorized an org you can reach:

- **Reuse an org the workspace has already authorized** — the card reads **"Reuse a Salesforce connection you already have"**: *"Your workspace already authorized this org. Reuse one here — no need to sign in or set it up again."* (It reads *"these orgs"* when more than one is on offer.) Each candidate names the connection, its org host, its availability — **Already connected in your workspace**, or *"Already connected in your workspace, in 3 projects"* — and its setup badge, with a **Use this connection** button.
- **The org you typed is already connected in *this* Project** — the more specific notice **"You're already connected to this org"** replaces it, naming the existing connection and offering the same **Use this connection**, alongside **Connect a new one**.

The two offers do different amounts of work, so read which one you got:

- **From the reuse card**, **Use this connection** *clones* the connection into the current Project, pointed at the same already-provisioned org. No admin signs in, nothing is re-provisioned, and this tab's **Used by** for that org grows by one Project. The clone starts with no agent selected, so you pick the agent for the new Project.
- **From the same-org notice**, **Use this connection** simply picks up the record that is already there. Nothing is cloned, no new record is created, and **Used by** does not change.

The reuse card is not scoped to *other* Projects. One admin authorization can back more than one agent in the Project that made it, so the org you are already using here can appear as a candidate too — it is hidden only when the org URL you typed raises the more specific same-org notice above.

Its eligibility filter is strict, and it is the one thing worth checking on this tab. An org is offered only when its setup finished *and* it was made by admin authorization — so on a row here, the candidates are the ones showing **no setup badge** with **Admin authorization** under **Sign-in**. An org still **Setting up**, waiting on **Needs admin**, or at **Setup failed** is withheld, because reusing it would drag an admin back into setup, and so are the three legacy sign-in methods. The same-org notice applies no such filter: it is raised by matching the org URL you typed against the Salesforce connections already in that Project, whatever their badge or sign-in method.

## Disconnect vs Delete

This is the distinction the surface exists for. Both buttons remove a connection, and each one does something the other does not.

| | **Disconnect** | **Delete** |
|---|---|---|
| Touches your Salesforce org | **Yes** — permanently removes the External Client App Trust AI deployed there | No |
| Needs a Salesforce admin | **Yes** — you are sent to Salesforce to authorize the removal | No |
| Removes the connection from every Project using the org | No — one connection record | **Yes** — all of them |
| Reconnect afterwards | Requires a fresh admin authorization | Straight away; the org-side app is still there |
| Who can do it | **Editor** on the Project the connection belongs to | **Admin** on every Project under **Used by** |
| Offered on | Connections made by admin authorization only | Every connection |

**Disconnect** appears only on connections Trust AI provisioned — the admin-authorization ones. A connection wired to an app your own admin created has nothing of Trust AI's to tear down, so it offers **Delete** alone.

### What each confirmation says

Both actions are confirm-gated, and the dialogs name what happens. Quoted here as shipped; the org name and the project count are filled in from the row.

**Disconnect** — the dialog is titled **Disconnect this Salesforce org?**

> This permanently removes the Salesforce app TrustAI created in **acme.my.salesforce.com** and deletes the connection from 3 projects. Anyone using it will lose access until you reconnect. You can't undo this.

Its buttons are **Keep connection** and **Disconnect**.

**Delete** — the dialog is titled **Remove this connection?**

> This removes **acme.my.salesforce.com** from TrustAI across 3 projects. The Salesforce app TrustAI created stays in place, so you can reconnect later. You can't undo this.

Its buttons are **Cancel** and **Remove connection**.

Both dialogs notice when your browser has no connection. The body gains a line — *"You're offline — this will be removed when the connection returns."* or *"…this will disconnect when the connection returns."* — and the action reads **Waiting to remove…** or **Waiting to disconnect…**. Cancelling at that point abandons the write rather than letting it fire later against a dialog nobody is watching.

### Read the Disconnect wording carefully

Confirming **Disconnect** does two things: it removes the External Client App from your Salesforce org, and it deletes **the one connection record that owns that app**. It does not delete the other Projects' records.

The practical consequence is still workspace-wide — every Project that reuses the org shares the app that just went away, so all of them stop working, exactly as the dialog warns. But the cleanup is not: if several Projects were listed under **Used by**, come back to this tab afterwards. Anything still listed now points at an org where Trust AI's app no longer exists, and **Delete** is what clears it.

If you want the connection gone from Trust AI everywhere and the org left untouched, **Delete** is the action that does that in one step — provided you are an Admin on every Project under **Used by**. If you are not, the action reports a failure — but the removals are not undone, so records in the Projects you *do* administer can already be gone. Check **Used by** before you click, and re-read the row afterwards.

### While a Disconnect is running

Disconnecting is not instant, because removing the org-side app needs a fresh administrator token. Confirming does not remove anything yet: Trust AI starts an admin authorization and hands your whole browser tab to Salesforce. Approve it there, and you land back on a Trust AI confirmation page — headed **Salesforce connection** — that runs the removal and reports it. This is a full page, not a toast on the **Connected orgs** tab.

While it runs, that page shows a **Disconnecting** pill under the heading *"Removing your connection"*. It then settles one of two ways:

- **It finishes** — a **Disconnected** pill, the heading *"Connection removed"*, and *"TrustAI removed the components it added to your Salesforce org and deleted the connection."* You are returned to **Connected orgs** automatically a moment later.
- **It doesn't** — a **Not disconnected** pill and *"We couldn't finish disconnecting"*, with the reason underneath. If the admin declines, the org can't be reached, or the External Client App itself can't be removed, the connection is **kept** rather than left half-removed, and you can try again. A **Return to Connections** button takes you back.

One caveat on the success wording: it reports that the External Client App is gone, which is what the connection record's removal is gated on. If some *other* component of the app bundle could not be removed, this page still reads **Connection removed** — so if the disconnect was retried or reported trouble earlier, have your Salesforce administrator confirm the org is clean.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The connection I expected isn't in the list">
    Two different reasons, and the tab distinguishes them.

    The list is scoped to Projects you can reach. A connection living only in a Project you have no grant on is not shown — that is the access boundary, not a missing row. Ask for **Viewer** access on that Project, or ask someone who has it to check.

    Separately, if the tab could not read every Project it was entitled to, it says so above the rows: *"Some projects couldn't be loaded, so this list may be incomplete."* That one is transient — reload before you go looking for a grant you already have.
  </Accordion>

  <Accordion title="There's no Disconnect button on a row">
    Only connections Trust AI provisioned by admin authorization have an org-side External Client App to remove. Check the row's **Sign-in** line: anything other than **Admin authorization** offers **Delete** alone.
  </Accordion>

  <Accordion title="An org I know is connected wasn't offered for reuse">
    The reuse card's filter is the place to look. A candidate must have finished setup *and* have been made by admin authorization — so on this tab it reads with **no setup badge** and **Admin authorization** under **Sign-in**. An org still **Setting up**, at **Needs admin**, or at **Setup failed** is withheld on purpose, and so is any legacy sign-in method. Reuse also requires **Editor** access on the Project you are connecting *into*.

    The same-org notice is not filtered this way, so an org that raises no reuse card in a new Project may still offer to be picked up where it is already connected.
  </Accordion>

  <Accordion title="Delete was refused">
    Deleting authorizes on project **Admin**, and Delete acts on every Project under **Used by** at once — so it is refused unless you are an Admin on all of them. Editor access is enough to disconnect, but never to delete. If the org is used by a Project you don't administer, ask one of its admins to remove their side, or disconnect instead.
  </Accordion>
</AccordionGroup>
