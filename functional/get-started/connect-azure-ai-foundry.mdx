## Use Functional in a story-to-results pipeline

This section maps one pipeline onto Functional Testing's tools, in order. The pipeline runs from a work item to test results. It carries one human review, at test design.

**a. Pick a story.** The agent reads an Azure DevOps work item with `wit_work_item`, a tool of the Azure DevOps remote MCP server. See [The Azure DevOps pattern](#the-azure-devops-pattern).

**b. Acceptance criteria.** Pass the story text to `functional_requirements_extract`, as `document_text`. When the call returns a job handle, poll `functional_inference_jobs_get`. Save the reviewed candidates with `functional_requirements_add_drafts`, with the work item id as `source_ref`. Promote more than one requirement at once with `functional_requirements_promote_batch`. Promote one alone with `functional_requirements_promote`. When the pipeline already wrote acceptance criteria, skip `functional_requirements_extract`. Pass those criteria directly to `functional_requirements_add_drafts` instead.

**c. Org context.** Read the Salesforce system's id with `functional_project_systems_list`. Pass that id as `system_id` to `functional_authoring_suggest` and to `functional_authoring_accept`. Functional Testing then reads the live org during authoring, and the saved test is bound to that system.

**d. Test design, the human gate.** Call `functional_authoring_suggest` for each requirement, with that `system_id`. When the call returns a job handle, poll `functional_inference_jobs_get`. Show the proposed scenario to the person. The design review is the Foundry approval request on `functional_authoring_accept`, in stage e. For that request, connect to the workflow endpoint and set the approval rule. See [Set approval for the write tools](#set-approval-for-the-write-tools).

**e. Test generation.** `functional_authoring_accept` saves an executable test. On the workflow endpoint, call it by its own name, so that the Foundry approval rule applies. Pass:

- The candidate's `accepted_scenario`.
- `source_channel` set to "requirement".
- `source_ref` set to the requirement's R- id.
- `system_id`, from stage c.
- A new unique `id`, for example `INT-0001`.
- An `external_test_id` and a `name`.
- `time_to_accept_ms`.

The two `source_ref` values mean different things. Here, `source_ref` names the requirement. On `functional_requirements_add_drafts`, `source_ref` names the work item.

The pipeline generates and maintains no test code and no page objects.

**f. Execution.** Create a suite of the accepted tests with `functional_suites_create`, with `project_id`, `id`, `name`, `schedule` set to manual, and `test_ids`. Run it with `functional_suites_run`, with `project_id` and `suite_id`. Poll `functional_runs_get` for the run-group's aggregate status, passing the returned `run_group_id` as its `run_code`.

**g. Results.** Read results only after the run-group settles. While a run is in progress, its coverage reads `not_adjudicated`, and that status is not a result. Read `functional_run_group_result_get` with that `run_group_id` for requirement coverage. For each failed run, read `functional_run_checks` and `functional_run_diagnosis` with that run's own run code. Read `functional_requirement_coverage_get` for each requirement. Then post a summary back to the work item with `wit_work_item_write`. The summary goes into the work item's history as a comment.

Every call above also takes `project_id`, to scope it to your project. `functional_inference_jobs_get` requires `job_id` beside it. `functional_requirements_add_drafts` requires `drafts`, the array of reviewed candidates, beside it.

## The endpoint

Functional Testing serves two MCP endpoints. Point your Foundry MCP tool at one of them, with the trailing slash.

| Endpoint | Tool list | Use it for |
| --- | --- | --- |
| `<your-ft-host>/v1/mcp/workflow/` | The default list, plus eight pipeline tools by name | A story-to-results pipeline. Foundry can then approve `functional_authoring_accept` by its own name. |
| `<your-ft-host>/v1/mcp/` | The default list | Any other agent. |

Both endpoints use the same tokens and the same access control. For the pipeline on this page, use the workflow endpoint.

Foundry needs a public host. It cannot reach a host on your own machine, for example `localhost` or `host.docker.internal`.

## Authenticate with a key-based token

1. Open the MCP access page in Functional Testing settings.
2. On the "Key-based clients" card, create a token.
3. Copy the token now. Functional Testing shows the token once.

A token is read or read-write. A token scopes to the whole workspace or to one project. A token also carries an expiry date.

In Foundry, add a key-based connection for the Functional Testing tool.

- Credential name: `Authorization`
- Credential value: `Bearer <token>`

Foundry stores that name and value on its own project connection. Every user of the agent then acts as the token owner. Foundry gives Functional Testing no separate identity per user today.

<Note>
  Foundry plans identity passthrough for a remote MCP server. Functional Testing does not support it yet, and no date is set.
</Note>

## Set approval for the write tools

Foundry's own `require_approval` setting defaults to `always`. It can also name tools. `{"always": [...]}` asks for approval on the named tools only. `{"never": [...]}` skips approval on the named tools only.

On the workflow endpoint, set this rule:

```json
"require_approval": {"always": ["functional_authoring_accept"]}
```

Foundry then asks a person to approve each `functional_authoring_accept` call. That approval is the design review for one test. Every other call runs with no Foundry approval step. This includes each call made through `functional_tool_call`, for example `functional_suites_create`.

The rule matches the tool name that Foundry sees. A call to `functional_authoring_accept` made through `functional_tool_call` does not match it, so it skips the approval. The starter instruction below tells the agent to call `functional_authoring_accept` by its own name.

Functional Testing adds no approval step of its own for a token call. A ruling settles this. An external, token-scoped call is Foundry-owned. Functional Testing's own default for that call is Auto, so Functional Testing never blocks, pauses, or clamps it.

Access control still applies:

- The token's own scope, read or read-write.
- The token's own project or workspace scope.
- Any workspace tool restriction a Functional Testing admin sets.

<Warning>
  On the default endpoint, `/v1/mcp/`, every write tool call reaches the server as `functional_tool_call`. A `require_approval` rule set on the wrapped tool's own name, for example `functional_authoring_accept`, never fires. Set the rule on `functional_tool_call` instead. This also asks for approval on every other call made through `functional_tool_call`, including each `functional_inference_jobs_get` poll. To approve `functional_authoring_accept` alone, use the workflow endpoint.
</Warning>

## Tools Foundry sees by default

Functional Testing hands over a bounded tool list, not its complete registry. The default list carries 30 read-only tools, reachable by name directly:

- List and get calls for `functional_projects_list`, `functional_project_counts`, `functional_project_systems_list`, `functional_systems_list`, and `functional_systems_get`.
- List and get calls for `functional_tests_list`, `functional_tests_get`, `functional_suites_list`, and `functional_suites_get`.
- List and get calls for `functional_requirements_list`, `functional_requirements_get`, `functional_requirements_tree_get`, and `functional_requirement_coverage_get`.
- List and get calls for `functional_runs_list`, `functional_runs_get`, `functional_run_checks`, `functional_runs_summary`, `functional_run_attempts_list`, `functional_run_diagnosis`, and `functional_test_runs_list`.
- List and get calls for `functional_datasets_list`, `functional_datasets_get`, `functional_environments_list`, `functional_environments_get`, `functional_workspaces_list`, and `functional_workspaces_get`.
- `functional_search`, `functional_records_resolve`, `functional_guide`, and `functional_docs_search`.

Three more tools sit in the default list by name, next to that read-only set:

- `functional_tools_search` describes the capability you need. It returns matching tool names.
- `functional_tool_call` calls the name and arguments `functional_tools_search` returned.
- `functional_autonomy_effective_policy` reads the autonomy mode an internal write in a project runs under right now.

Every other tool sits outside the default list. This includes every write tool, and it includes the read tool `functional_inference_jobs_get`. Reach each one through `functional_tools_search`, then `functional_tool_call`. On the default endpoint, every pipeline tool that this page names needs that pair, with six exceptions. The exceptions are `functional_guide`, `functional_project_systems_list`, `functional_runs_get`, `functional_run_checks`, `functional_run_diagnosis`, and `functional_requirement_coverage_get`.

## Tools on the workflow endpoint

The workflow endpoint lists the default tools, plus these eight by name:

- `functional_requirements_extract`
- `functional_requirements_add_drafts`
- `functional_requirements_promote_batch`
- `functional_authoring_suggest`
- `functional_authoring_accept`
- `functional_inference_jobs_get`
- `functional_test_runs_start`
- `functional_suites_run`

The agent calls each of these tools by its own name. Foundry can set approval on each one by that name.

Every other tool outside the default list still needs `functional_tools_search`, then `functional_tool_call`. On this page, that covers these tools:

- `functional_requirements_promote`
- `functional_suites_create`
- `functional_run_group_result_get`
- `functional_connections_authorization_start` and `functional_connections_authorization_get`
- `functional_credentials_request` and `functional_credentials_request_get`

## Time limits on a long-running call

Foundry limits a non-streaming MCP call to 100 seconds. Foundry's background mode lifts that limit for some models.

`functional_requirements_extract` and `functional_authoring_suggest` can run past 100 seconds. When a call has not finished after about 25 seconds, it returns a job handle instead of a result. The handle carries a `job_id`.

Poll `functional_inference_jobs_get` with that `job_id` until the job settles. Read the result once the job is ready, or the error once the job failed.

## Two steps a human completes

Two steps in this workflow need a person, not the agent.

**Salesforce authorization.** Call `functional_connections_authorization_start`. Send the returned authorization URL to a person. The person signs in and approves access in a browser. Poll `functional_connections_authorization_get` with the returned `authorization_id` for the outcome.

**The credential form.** For any other credential, call `functional_credentials_request`. Send the returned link to a person. The person fills in a one-time Functional Testing form. The link expires in 15 minutes. Poll `functional_credentials_request_get` with the returned `request_id` for the outcome.

Functional Testing never accepts a secret value over MCP. This rule holds for Foundry, and it holds for every other client.

## The Azure DevOps pattern

Pair Functional Testing with the Azure DevOps remote MCP server in the same Foundry agent.

1. Read a work item with `wit_work_item`.
2. Pass the work item's text to `functional_requirements_extract` as `document_text`.
3. Pass the work item's id to `functional_requirements_add_drafts` as `source_ref`.
4. After the run-group settles, post the result summary with `wit_work_item_write`. The summary goes into the work item's history (`System.History`) as a comment.

The saved draft requirements carry the work item id as their source. A reviewer can then trace each requirement back to it.

Set up the Azure DevOps server in Foundry this way:

- Put both `wit_work_item` and `wit_work_item_write` in the server's allowed tools. If `wit_work_item_write` is not in the list, the agent cannot post the result back to the work item.
- Set both tools to auto-approve. The one human review in this pipeline is the approval on `functional_authoring_accept`.
- Make sure that the Azure DevOps organization and the Foundry project use the same Microsoft Entra tenant. The Azure DevOps server signs in with the person's own identity. If the tenants differ, the first call fails with `VS30063`.

## Keep each chat short

Each tool result stays in the chat, so a long chat grows fast. In one full pipeline run, a single chat grew to about 93,000 tokens and reached the model's tokens-per-minute limit.

If the model reaches its limit, divide the pipeline into two chats:

1. Stage a to stage e: read the work item, then extract, promote, suggest, and accept.
2. Stage f to stage g: run the suite, read the results, and post the summary to the work item.

## Document links Functional Testing refuses

`functional_requirements_extract` takes a document as `document_text`, `document_file`, or `document_url`.

`document_url` refuses a link with a query part, for example an Azure Blob SAS link. Send the file bytes instead, as `document_file`.

## A starter instruction for the Foundry agent

Paste this into your Foundry agent's instructions. It states the story-to-results order, stage a to stage g.

```text
You are a Functional Testing agent connected over MCP, in a
story-to-results pipeline.

Call functional_guide with topic "getting-started" once per session,
before your first write.

Work in this order:

a. Read an Azure DevOps work item with wit_work_item.

b. If the work item carries no acceptance criteria yet, call
   functional_requirements_extract, with the work item's text as
   document_text. If the result carries a job_id, poll
   functional_inference_jobs_get with that job_id until the job
   settles. Either way, save the acceptance criteria with
   functional_requirements_add_drafts, with the work item id as
   source_ref. Promote more than one requirement at once with
   functional_requirements_promote_batch, or promote one alone with
   functional_requirements_promote.

c. Call functional_project_systems_list to read the Salesforce
   system's id. Pass that id as system_id in stage d and stage e.
   Functional Testing then reads the live org during authoring, and
   the saved test is bound to that system.

d. For each promoted requirement, call functional_authoring_suggest,
   with that system_id. If the result carries a job_id, poll
   functional_inference_jobs_get with that job_id until the job
   settles. Show the proposed scenario to the person.

e. Call functional_authoring_accept to save the test. If your tool
   list shows functional_authoring_accept, call it by that name, and
   never through functional_tool_call. Foundry asks the person to
   approve this call. Pass accepted_scenario, source_channel set to
   "requirement", source_ref set to the requirement's R- id,
   system_id, a new unique id such as INT-0001, external_test_id,
   name, and time_to_accept_ms. This source_ref names the requirement.
   It differs from the source_ref on
   functional_requirements_add_drafts, which names the work item.

f. Create a suite of the accepted tests with functional_suites_create,
   with schedule set to manual. Run it with functional_suites_run.
   Poll functional_runs_get, passing the returned run_group_id as
   run_code, until the run-group settles.

g. Do not read results before the run-group settles. While a run is
   in progress, its coverage reads not_adjudicated, and that status
   is not a result. Read functional_run_group_result_get with that
   run_group_id for requirement coverage. For each failed run, read
   functional_run_checks and functional_run_diagnosis with that run's
   own run code. Read functional_requirement_coverage_get for each
   requirement. Then post a summary back to the work item with
   wit_work_item_write, as a comment in the work item's history.

Every call above also takes project_id.
functional_inference_jobs_get requires job_id beside it, and
functional_requirements_add_drafts requires drafts beside it.

If your tool list shows a tool by name, call it by that name.
Otherwise, find it first with functional_tools_search, then call it
with functional_tool_call. Never guess a tool name or an argument
name.
```
