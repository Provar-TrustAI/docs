An Evaluation is a run: take one or more [Evaluators](/concepts/evaluators), apply them to the [scenarios](/concepts/scenarios) or [Sessions](/concepts/sessions) you select, against a specific [Agent Version](/concepts/agent-versions). The output is a scored, reviewable record per result — a verdict alongside the reasoning the Evaluator captured.

An Evaluation is **the artifact regressions get caught in**. It's also the artifact every other TrustAI surface ultimately serves: Sessions exist to become scenarios and evaluation targets, Annotations exist to grade the judges, scenarios and Evaluators exist to produce Evaluations.

## What an Evaluation can grade

An Evaluation targets one of two sources:

- **Scenarios** — TrustAI simulates each selected scenario live against the Agent Version (via the [Project's runtime connection](/concepts/projects)). Every persona attached to a scenario is simulated and scored on its own, so one scenario with three personas produces three results.
- **Sessions** — TrustAI grades conversations that already happened, by **replaying** them: each session's stored user message goes back to your connected agent and the reply it gives *now* is what the judges read. The stored session is never modified. (To grade the stored transcript itself, run a [quick evaluation](#quick-evaluations) from the session's own fly-in.) Because there's no live conversation to steer, session grading uses **LLM judge** evaluators only. The result is homed on the session itself, and **Open session** in the result's overflow menu takes you back to the exact session that was graded.

The second source is what makes Evaluations more than a synthetic-test tool: yesterday's real production conversations are as gradeable as your authored test cases.

## Launching a run

One **Evaluation Launcher** drives every run, and every entry point leads to the same modal. It opens from these seven places:

1. **Sessions list** — select sessions and click **Evaluate** (bulk).
2. **A single session's panel** — **Evaluate** in the header (a quick evaluation).
3. **Scenarios list** — select scenarios and use the **Run** split button (**Run & evaluate**, or **Run only** to simulate without grading).
4. **A single scenario's fly-in**.
5. **Evaluations list** — click **New evaluation** and pick the source yourself.
6. **A finished run's detail page** — **Re-run**.
7. **An Evaluator's panel** — evaluate with the judge you're looking at.

Nothing is enqueued by any of those clicks. They open the launcher; the run starts when you confirm inside it. However you arrive, the launcher shows a **fan-out preview** — exactly what will run, including the per-persona expansion for scenarios — before you commit.

An eighth path skips the launcher entirely: an [Automatic Full Run](/how-to/run-an-automatic-full-run) launches its own graded scenarios run at the end of its pass. What lands here is an ordinary run — the same lifecycle, the same results — listed under the name of the Automatic Full Run that produced it, with no separate badge to look for.

### The Environment step

A scenarios launch carries one more section below **This will run**: **Environment**, marked with a **New** pill. Its own line says what it selects — *"Selects the connected org or test data store, test identity, and cleanup used for this run."* You rarely start from nothing: the launcher preselects the first environment attached to the agent you chose and probes it in place, settling on **Ready to run** (or **Ready to run with limited trace data**) above a short list of what it checked — that the agent is active and ready, that the environment is available now, which test data store the run will use, and the cleanup promise **"Between tests: Removes only the records each test created."**

The run button waits on that probe. Until an environment resolves ready, the launcher won't start a scenarios run — and a scenario carrying a [test data](/concepts/test-data) plan turns the picker from a prefilled convenience into a requirement, because that plan has to be set up somewhere.

A sessions launch shows no Environment section at all — but it still needs a connected agent, because it replays each session against one.

## Quick evaluations

You don't need a named run to answer "does this one pass?". **Evaluate** on a single session grades it in place and the verdict lands on the session itself. Bulk runs are for measurement; a **quick evaluation** is for the check you want while you're already looking at the thing.

It still mints no run — but it is no longer invisible. While the judges work, the session's **Evaluations** tab carries a status chip reading **Queued** and then **Running**, with a caption counting the checks off — *"Scoring check 2 of 3…"*. Progress is tracked on the server rather than in your tab, so it survives a reload and a colleague watching the same session sees the same count. A **Quick evaluation started** toast confirms the launch and a **Quick evaluation finished** toast closes it out, carrying a **View** action.

When it finishes, the Evaluations page lists it as a row named **Quick evaluation** with a muted **Quick** pill beside the name. Clicking that row opens the conversation it graded rather than a run-detail page — there is no run behind it to open — and for the same reason the row carries no **Cancel** and no **Delete run**. Grade the same session again and the new verdict replaces the old one in a single step: the session never holds two, and never sits without one.

Grading a single scenario from its own fly-in takes the same path: it simulates one conversation, grades it, and mints no run either.

One limit is worth knowing: the sidebar's **Evaluations** count still counts full runs only, so a project with one run and one quick evaluation reads **1** in the rail and lists two rows on the page.

## The run lifecycle

- **Launched** — the run records a snapshot of your scenarios as they were at launch, so a finished run stays reproducible even after you edit or delete scenarios later.
- **In progress** — results fill in as they complete. If you launched a bulk run from the Scenarios list, you stay on the list and watch each scenario's live **Generating…** badge settle as it finishes. You can open the run and watch results arrive, or click **Cancel run** — the run stops at a clean boundary and keeps every result already scored.
- **Complete** — every result has settled. That doesn't guarantee a number, and where there is no number the header says *which* kind of ungraded it is rather than leaving you to guess:
  - **Run only — nothing was graded** — you deliberately simulated without grading.
  - **Not graded — no evaluators** — the run asked to be graded but inherited none, so there was nothing to grade with.
  - **Not graded** — the residual case, including runs recorded before that distinction shipped, which keep the neutral wording rather than claiming an intent their record can't evidence.

  A complete run and a graded run are not the same thing.

One caveat on "complete": a Salesforce run's score can still move afterwards. Where the platform publishes a conversation's full activity records late, those conversations are re-checked once the evidence lands, and the run carries the notice **"Results were updated after trace review"** so a shifted pass rate reads as a review rather than a bug.

Finished runs offer **Export** (download the results as CSV) and a primary **Re-run**; the **…** menu offers **Delete run**, which removes the run from your lists without destroying the sessions it produced.

## Reading the results

Run detail leads with **two headline numbers**, and they answer different questions:

- **Pass rate** grades the *agent*: of the results that count, how many passed.
- **Evaluator accuracy** grades the *judges*: how often the automated Evaluators agreed with a human's verdict on the same sessions. Human Pass / Fail verdicts, recorded as [Annotations](/concepts/annotations), are the ground truth here — on the **Verdict** annotation column a human verdict grades the judges and never overrides the automated verdict. Scope that to the column: on a Groundedness result a reviewer *can* override a per-claim verdict, and the score recomputes.

A high pass rate means little if evaluator accuracy is low: you'd be trusting judges that a human reviewer routinely disagrees with. The two numbers together tell you whether to believe the run.

### Pass^K reliability

The launcher's **Repeat each test case** selector chooses how many times each case runs: **1**, **2**, **3**, or **4**. Its own hint says why you'd raise it — *"Repeat each case to measure how reliably the agent passes. More repeats take longer to run."* It appears on every graded, run-minting launch.

Repeat more than once and the run leads with a **Pass^K** rate instead of a plain pass rate: the share of test cases that passed *every* attempt, rendered literally as `Pass^2`. Hover the headline for the full curve from pass-once to pass-every-time.

This is the honest number for a non-deterministic agent. One that passes 87% of cases on a single attempt can pass far fewer on all four, and the gap between those two figures *is* the reliability finding. A single-attempt run can't show it — which is the reason to reach for the selector before you conclude an agent is solid.

Raising the repeat count multiplies the work — but read the launcher's fan-out preview carefully, because it doesn't say so. The preview counts **one attempt**: "*10 sessions × 2 evaluators → 20 evaluator runs*" reads the same at a repeat of 1 as at a repeat of 4. Multiply it yourself. At 3 repeats, that 20 is really 60.

### Results are grouped by scenario

Run detail opens **By scenario**. Its top-level rows are one summary per scenario, each carrying a rollup verdict and a passed-of-total reliability figure — `2/3` when two of three attempts passed. Click a summary to expand it and see the individual attempts, labelled **Trial 1**, **Trial 2**, and so on. Clicking a summary row expands it; it doesn't open a panel, because there's no single record behind it.

A collapsed summary row aggregates its children rather than standing in for one of them. In every evaluator column — and in each structural-check column — the summary cell reads `2/3 passed`, with a muted **N not scored** line beneath it when some trials were excluded. Trials that left the score are dropped from the ratio, never counted as failures, and a summary whose trials produced no pass or fail at all leaves the cell empty — announced to a screen reader as **Not scored** — rather than inventing a zero.

Click a trial and the result fly-in opens. Where a scenario has more than one attempt, the panel header grows a **Trial N of K** switcher so you can step between that scenario's attempts without going back to the table.

The **View** toggle at the top of the column menu switches to **Flat**, where every row is one result and the grouping is gone. Use Flat when you want to sort or scan across scenarios rather than within them.

Because every attached persona is scored separately, divergence between personas shows up in this grouping with plain-English hints — when the same scenario passes for one persona and fails for another, the results point at it. That divergence is usually the most actionable finding in a run: the agent didn't break everywhere, it broke for a *kind of user*.

### Verdict states

A result's verdict is **Pass**, **Fail**, or one of three reads that are neither — and the differences between those three are the useful part:

| Verdict | Means |
|---|---|
| **Pass** | Every gating evaluation passed |
| **Fail** | At least one gating evaluation failed |
| **Not evaluated** | Nothing ran against it |
| **Not graded** | Something ran, but produced no behavioural score |
| **Couldn't test** | An action the agent itself runs returned an error, so there was no behaviour left to grade |

None of the three is silently a pass or a fail. **Not graded** and **Couldn't test** are the ones worth opening, because there is a result behind each. They differ in tone as well as meaning: **Not graded** reads in the same calm grey as the rest of the table, while **Couldn't test** reads amber, because it points at something in the agent's own stack rather than in the rig around it. While a run is still scoring, the cell reads **Scoring…**.

A summary row over mixed trials gets one more read. Where some of its trials couldn't be tested and every trial that *was* scored passed, the chip reads **Pass among scored**, with an amber **N couldn't test** caption beside the ratio — a pass rate that tells you what it is a pass rate *of*.

One more state exists a level down. An individual check can come back **Needs review** when the judge was uncertain. A needs-review check never gates: it is recorded and shown, but it can't flip the result's outcome or push a sibling evaluator's verdict out of the count. On a **Groundedness** check specifically, adjudicating the uncertain claims (see [Annotations](/concepts/annotations)) can resolve the needs-review and let the check gate normally — adjudication is scoped to Groundedness and exists nowhere else.

## When a result leaves the score

Not every non-pass means the agent got something wrong, and the results no longer pretend otherwise. **Five outcomes leave the pass-rate denominator, and only four of them are the environment's fault.** Leaving the score and being blamed for it are separate questions, and the product keeps them apart:

| Label | When |
|---|---|
| **Guardrail blocked** (grey) | A runtime content guardrail suppressed the response before the agent could answer |
| **Environment problem** (grey) | The supporting infrastructure failed — a gateway or network error, or a timeout — before the agent could answer |
| **Environment problem** (grey) | The evaluation harness itself errored before it could score the conversation |
| **Access blocked** (grey) | The platform authenticated the run but refused the selected test user |
| **Couldn't test** (amber) | An action the agent itself runs — a Flow, an Apex class, an API automation — returned an error, so the behaviour under test never happened |

**The first four are the environment's fault**, and only they carry that framing. Each gets its own plain-language explanation rather than one generic guardrail line, because "the network timed out" and "a guardrail fired" are different problems for you to act on. Open one of those results and the banner is headed by its own label — **Guardrail blocked**, **Environment problem**, or **Access blocked**. The per-persona matrix is the one place the three collapse: an excluded row there reads the single neutral keystone **Environment problem — not the agent · Excluded from the score**. All four render neutral in both places, and never a red Fail. The agent never got a fair shot at any of them, so the result is neither a pass nor a fail.

**Couldn't test is the fifth, and none of that framing reaches it.** The action that failed belongs to the agent's own stack, not to the rig around it, so the banner reads amber and says only what happened: *"Not scored because an action the agent runs returned an error."* It leaves the denominator for a different reason — a pass would claim that behaviour which never ran succeeded, and a fail would grade behaviour that never ran — not because anyone is off the hook. Read it as a finding about the agent, not as an environment excuse.

Voiding is asymmetric either way: only a would-be pass is voided. A conversation a judge had already failed keeps its verdict, annotated as degraded.

The pipeline also defends itself before classifying anything as an environment problem: model-capacity throttling is retried automatically with backoff, one bad result can't fail the whole run, and judge calls run in parallel within a safe bound. A capacity hiccup at 2 a.m. can no longer masquerade as a drop in agent quality.

### Reading a run's health

Three words carry the whole reliability story on these screens, and nothing else is coined for it:

- **Couldn't test** — an action the agent runs failed, so this conversation could not be scored.
- **Not scored** — what follows from that, said about the conversation itself. The one-line summary is *"Not scored because an action the agent runs returned an error."*
- **Unverified** — the trace evidence for this conversation is still pending, or never arrived. An unverified conversation **stays in the run** and is not treated as an action failure.

Where a run couldn't test anything, Run Detail carries an amber strip above the results, titled **Couldn't test some conversations**, with the counts beneath it — `3 couldn't test · 1 unverified` — and a **See details** action. That opens **What happened in this run**, which says how many of how many conversations couldn't be tested, why grading them would have been vacuous, and that each one stays visible with the failed step marked in its transcript. Where the run tested more than two conversations at once, the dialog names that load as a possible cause; above three, it offers **Re-run at concurrency 3** so you can find out whether the failures persist.

The Evaluations list carries the same signal one level up: an amber **N couldn't test** sits beside that run's **Overall pass rate**, so a green rate never renders uncaveated.

## What's in an Evaluation result

Open any result to see:

- **Transcript** — the full conversation, labeled **Simulated** (the run drove a live conversation) or **Replayed** (the judges graded a captured session). A simulated conversation closes with one plain-English line led by **"This conversation ended because "** — the customer got what they needed, the agent could not help with it, the customer gave up, the agent ended or transferred it, or it reached the length limit before finishing. Where the simulated customer explained itself, its own words follow underneath. A conversation with no recorded ending shows no line at all, so don't rely on one being there.
- **Final verdict** — the result's verdict, with per-Evaluator score cards beneath it.
- **Reasoning** — what you get depends on the kind of evaluator. An **LLM judge** shows the rubric reasoning behind its score. A **Structured match** shows the assertion that fired, or didn't. An **Outcome grounded** evaluator compares the backend state the run left behind against the expected end state. The **Groundedness judge** doesn't produce rubric reasoning at all — it produces a claim-by-claim report of what the agent asserted and whether the source material supports it.
- **End state** — a tab of its own, sitting between **Evaluation** and **Metadata**, on results the run actually graded on end state. It compares what the agent should have left behind against what it did leave behind, and links back to the scenario's plan with **View the test data plan**. The run's results table carries a matching **End state** column, present only when at least one result graded on end state; its absence on a transcript-graded run is correct, not a missing column. See [Test data](/concepts/test-data).
- **Open session** — in the header's **⋯** menu, alongside **Open scenario**. Both jump to the record behind the result, and each appears only when it resolves.

**An LLM judge reads the whole conversation, not just the closing reply.** Every agent turn is in scope: a criterion violated on any turn fails the conversation for that criterion even if a later turn puts it right, and the reasoning cites the turn that broke it. The judge is also held to the transcript in front of it — it is told the transcript is complete, and must not infer turns, tool calls, or results that aren't shown. If you wrote a rubric against "the final answer", expect it to grade a multi-turn conversation differently than it used to.

## Evaluation results are Sessions, too

The conversations produced when an Evaluation simulates scenarios are themselves Sessions — structurally the same as production Sessions. They appear in your Sessions list with a **Source** chip of **Scenario** (captured production traffic shows **External**; **Playground** is reserved for an interactive capture finalized without a scenario link — the [Playground](/concepts/playground)'s own save flow always attaches one, so a saved Playground conversation reads **Scenario**), and their **Simulated from** provenance shows which scenario and persona produced them.

This is what unlocks:

- **Re-grading without re-running** — evaluate those sessions again with different Evaluators; the judges read the transcript, no agent invocation needed.
- **Annotating them** like any other session, which feeds the evaluator-accuracy headline.
- **No special-case surface** — one Sessions list, filtered by Source when you want only one kind.
- **The test-data record travels with the conversation** — each session's fly-in carries its own **Test Data** tab reporting what TrustAI set up, read back and cleaned up around that one conversation, under the heading **"What TrustAI did"**. The grade stays on the result; the tab explains how the data got there. See [Test data](/concepts/test-data).

## Comparing Agent Versions

The regression-tracking pattern is two runs with one variable changed:

1. Run an Evaluation against **Agent Version A** (say, production).
2. On the finished run, click **Re-run**, switch the Agent Version to **B** (the candidate), and launch. Everything else carries over: the source, the exact items, the Evaluators, the run-only flag, the environment the run used, and the structural-grading mode. One field does **not** carry over — **Repeat each test case** resets to 1, so set it back before you launch if the original run was a repeated one. Change one variable and only that variable moves.
3. Read the two run details side by side: headline deltas first, then the per-persona matrices for where the movement happened.

There is no dedicated run-vs-run comparison view in the app today; the faithful Re-run is what makes the manual comparison trustworthy, because you know the only variable that changed is the agent.

## Working with Evaluations

You drive Evaluations from the TrustAI app, or by asking the [Trust Agent](/concepts/trust-agent). Tell the Trust Agent to evaluate your scenarios against an Agent Version — or click **New evaluation** on the Evaluations list and configure the launcher yourself. Evaluating captured sessions is launcher-driven: start it from the Sessions list or a session's panel (see [Evaluate sessions](/how-to/evaluate-sessions)). Open a run to watch progress, read results, cancel it mid-flight, or re-run it against a different Agent Version. The Trust Agent can also pull aggregate stats and slice results by persona for you.

Developers who want the underlying endpoints and request/response shapes can find them in the [API Reference](/api-reference).
