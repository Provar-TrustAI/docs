If your repo already has an `AGENTS.md` or `CLAUDE.md` that agents read on start, paste the block below into it. It's short on purpose — a handful of rules that keep an agent from reaching for a placeholder credential, missing a gate, or treating `needs_review` as generic flakiness, not a full explanation of Functional Testing.

<Note>
  This is a **repo-level default**, not a connection step. See [Setup prompt](/functional/get-started/setup-prompt) to connect an agent to FT over MCP in the first place.
</Note>

## The block

```markdown
## Functional Testing — rules for any agent working in this repo

- Read `functional_guide` with topic `getting-started` before your first
  write, and topic `why-needs-review` when a run settles `needs_review`.
- Investigate the app's source, docs, and UI. Save relevant app context
  in the requirement description and state acceptance criteria explicitly.
  Keep intended behavior separate from observed implementation.
- Before accepting an authored candidate, check that its actions and
  verification cover each criterion. Use fresh data for creation tests;
  establish identity, attempt the action, and prove refusal for denial tests.
- Testing a public target? Create the System with `auth_type: "none"`.
  If a scenario needs to sign in, that's an ordinary test step, not a
  System-level credential.
- Never type a real secret into a test. Reference a stored credential
  by slot name only: `{{credential.SLOT_NAME}}`. Request credentials through
  FT's managed credential form, let the customer enter them, then poll.
- Verify on-screen text and headings with a UI check using observed target
  and scope, a typed expectation, and an authored-step transition. UI checks
  count toward pass/fail; no extra perception clause is required.
- Read run and check evidence before repairing a failure; rerun the finished
  definition unchanged with fresh browser state before claiming success.
- If a run settles `needs_review`, read `why-needs-review` before
  assuming it's flaky — it's one of four distinct, fixable causes.
```

## What each rule is for

- **App context and acceptance criteria.** The connected agent researches the app and supplies what the test should do; FT formats that context for execution. Source code explains the implementation, but does not replace the customer's intended behavior. See [Getting started](/functional/get-started/getting-started).
- **`functional_guide`.** The MCP guide serves these product instructions directly. Read the topic named by a refusal or diagnosis before guessing a repair.
- **Public-site auth.** `auth_type: "none"` is the correct, credential-free posture for a public target — not a placeholder waiting for a real secret. See [Credentials](/functional/concepts/credentials).
- **No inline secrets.** A value shaped like a real secret is rejected at the write boundary wherever it appears in an authored test. `{{credential.SLOT_NAME}}` is the only safe way to reference one. See [Credentials](/functional/concepts/credentials).
- **UI checks.** A UI check produces comparison evidence for rendered content and counts toward pass/fail. Use perception clauses for their own supported observations, not as a second check for the same heading. See [Verification](/functional/concepts/verification).
- **`needs_review` isn't one bucket.** Assertion not observable, binding mismatch, no deterministic assertion, or target unreachable — each has its own fix. See [Why a result reads "needs review"](/functional/troubleshooting/why-needs-review).
