An Agent Version **names one build of the agent under test**. It is the pin an Evaluation carries: every scenario-driven [Evaluation](/concepts/evaluations) runs against exactly one Agent Version, and every regression-tracking workflow is a diff between two.

The record itself is deliberately thin — a label plus the metadata its connector supplied. It is an **identity**, not a configuration dump. What a build can actually *do* — its tools, its knowledge sources, how it identifies itself — lives in that build's [Agent Profile](/concepts/agent-profile).

One exception up front: an Evaluation can also grade [Sessions](/concepts/sessions) that already happened. Those runs judge recorded transcripts and never invoke your agent, so they carry no pinned Agent Version.

If Sessions are the raw material, [Scenarios](/concepts/scenarios) the test bed, and [Evaluators](/concepts/evaluators) the rubric, then Agent Versions are **what's being judged**. Server messages sometimes call one an "agent build" — for example, *"This agent build is not linked to a saved connection"*. Same thing.

<Note>
  **An Agent Version is not the Trust Agent.** They share the word "agent," but they are opposite ends of the evaluation:

  - An **Agent Version** (this page) is the *thing being evaluated* — the build of the customer's agent under test.
  - The **[Trust Agent](/concepts/trust-agent)** is the *in-app assistant* that helps you run those evaluations.

  The Trust Agent helps you judge Agent Versions; it is never itself "a version."
</Note>

## Agent Version and Agent Profile are different nouns

These two get confused constantly, because both are "about the agent." They answer different questions and they are pinned by different things.

| | **Agent Version** | **[Agent Profile](/concepts/agent-profile)** |
|---|---|---|
| Answers | *Which build was this?* | *What can this build do?* |
| Shape | A label plus connector metadata | A captured record of identity, tools, and knowledge sources |
| Versioned unit | The version row itself | The **profile revision** |
| Pinned by | An **Evaluation** | A **Trust Agent** session |

A profile is *about* a version and nests under it — one version, one profile, and a second version gets its own. If you are choosing what to evaluate, you want an Agent Version. If you are asking what a given build is capable of, you want its profile.

**Not every build can be profiled.** Capability discovery reaches three of the four connected platforms — Conversational HTTP, Claude Managed Agent, and Salesforce Agentforce. An **AWS Bedrock AgentCore** build has an Agent Version like any other, but no profile: its connection says *"Agent profiling isn't available for this connection yet."* and offers no retry. That is a platform limit, not a failure to work around.

## What an Agent Version records

An Agent Version record holds:

- **Label** — the human-authored version string ("Customer Service Assistant", "acme-cs-agent v1.8.2"). Free-form; no format is imposed. It is unique within the Project, and it is the only field you can edit.
- **Connector metadata** — whatever the connected platform supplied when the build was discovered: which connection it came through, and the platform's own identifiers for it.
- **Who created it and when** — an audit trail only. It does not gate access.
- **Archived state** — set when the build no longer matches the connected runtime. See [Lifecycle](#lifecycle).

That is the whole record. In particular, an Agent Version **does not** store your agent's prompt, its model, its tool schemas, or its retrieval configuration, and it has **no description field and no tags**. Those things are properties of the running agent, and Trust AI reads them by capturing an [Agent Profile](/concepts/agent-profile) against the build — not by copying them into the version row.

<Note>
  **The record is not immutable — the pin is by reference.** A version's label can be renamed, and a run stores a reference to the version rather than a frozen copy of its name. Rename a version and past runs pinned to it display the new label. What stays fixed is *which build* a finished run went against.
</Note>

## Where Agent Versions come from

Agent Versions arrive through **connectors**. Four platforms connect today — none of them flagged or gated — from **Project Settings → Connection → Add connection**. They are peers in that picker, though not in everything that follows: session backfill and Agent Profile capture each reach only some of them, and both limits are stated where they bite.

- **AWS Bedrock AgentCore** — a guided setup flow connects the runtime, and its builds sync into the Project automatically. Discovery stays reconciled with what's deployed: a build that no longer matches the connected runtime is archived, and pointing the connection back at it revives the record.
- **Salesforce Agentforce** — connect an Agentforce agent in your Salesforce org. See [Connect Salesforce Agentforce](/how-to/connect-agentforce).
- **Claude Managed Agent** — connect an Anthropic Managed Agent on Claude Platform. Trust AI observes the agent and relays its responses; the agent runs its own tools.
- **Conversational HTTP agent** — connect **any agent that accepts AG-UI run requests and streams AG-UI events over SSE**. This is the escape hatch for a platform Trust AI has no dedicated connector for: if your agent speaks AG-UI over HTTP, it connects like the rest.

### Connecting a Salesforce org

Salesforce connections are created by **authorizing Trust AI once as a Salesforce admin**. The new-connection form asks for the org URL and then hands you a single action — *Authorize in Salesforce with an administrator account*. There are no keys, no secret, and no certificate to hand over, and the form warns you to point it at a Sandbox rather than production, because approving Trust AI provisions a connected app in whichever org you sign in to.

Three older sign-in methods — **External Client App key + secret**, **Certificate-based JWT**, and **Username + password** — are each labelled **(legacy)** and appear only when you edit a connection that already uses one. They exist to keep existing setups working. Do not build a new connection around them.

### Discovering the agent

Once a connection can reach the platform, **Agent** is a discover-then-pick select rather than a field you type an id into. **Find agents** searches the org, reports how many it found, and lets you choose one by name. A manual-entry escape hatch is there if you already know the identifier.

One thing holds across every connector: **connection secrets stay secret.** Private keys, access keys, and API keys are write-only — once saved, they are never shown back.

**Pulling in past sessions does not hold across every connector.** The **Sync now** button in the Sessions page header opens a picker grouped by connected system, and that picker lists *every* connected agent — but only an **AWS Bedrock AgentCore** agent actually pulls anything. Pick a Salesforce Agentforce, Claude Managed Agent, or Conversational HTTP agent and the sync returns nothing, reporting that historical session sync is supported only for AWS Bedrock AgentCore. Sessions from those platforms arrive as they are produced — a scenario-driven simulation or a Playground conversation writes one as it runs — rather than by backfill.

The fastest path for the two platforms it covers is to ask the **Trust Agent** to connect your agent: its in-chat connect card handles Claude Managed Agent and Salesforce Agentforce, collecting credentials inside the card so no secret ever reaches the conversation. Every other platform is set up in **Settings → Connection**.

Archiving an Agent Version in Trust AI does not affect the source runtime.

## Pinned at run time

When you launch a scenario-driven Evaluation, the launcher's **Agent** step asks which connected agent simulates each scenario — the run pins that build, and its results carry the pin. When you drive the run through the Trust Agent instead, it confirms which agent build it will run against before simulating, and tells you plainly if none is connected. **Re-run** on a finished run restores the original run's full configuration, including its pinned agent and Evaluators.

Evaluations launched from Sessions skip this step entirely: grading a recorded transcript needs no agent, so no version is pinned.

You can also see the pin after the fact, on a session's **Details** tab — but the row is labelled differently depending on what the session ran against:

| Session ran against | Row label | Row shows |
|---|---|---|
| A model-backed agent | **Model** | The build descriptor, in monospace |
| A connected Salesforce Agentforce agent | **Agent** | The agent's name, linking into Agentforce Builder |

An Agentforce session goes further and renders the agent's authored configuration — its type, status, language, role, and instructions — as captured from the org at simulation time. A session that carries neither, such as an uploaded external transcript, shows an em-dash.

## Lifecycle

An Agent Version is **created** on discovery (or registration), **active** while it's the target of new Evaluations, and **archived** when superseded. Archiving doesn't delete:

- Historical Evaluations against the archived version remain readable, and **Re-run** can restore any finished run's configuration
- The version's results stay comparable against any newer run

Archiving follows discovery: reconciling against the connected runtime archives builds that are no longer deployed, and re-registering the same build revives the record. Versions don't expire on their own — a version stays active until the runtime it points at moves on.

## The regression-tracking pattern

The core regression-tracking pattern:

1. Pick a stable selection of **Scenarios**.
2. Pick the same set of **Evaluators**.
3. Pick **two Agent Versions** — the production one and a candidate replacement.
4. Run an Evaluation against each.
5. Read the two finished runs side by side and compare per-scenario results.

When the same Scenarios and the same Evaluators are held constant, **the only variable left is the agent itself**. Whatever changes in the Evaluation results between the two runs is attributable to the version change. That's the loop the Agent Version concept exists to make legible.

<Note>
  There is no dedicated run-vs-run comparison view in the product yet — you compare by opening the two run details. **Re-run** on a finished run restores its full configuration, including the pinned agent and Evaluators, so repeating the same setup against a different version is a one-field change.
</Note>

Hold any of those three constants and you get a different signal:

- **Hold the Agent Version, vary the Scenarios** → "does this version regress on a different slice?"
- **Hold the Agent Version, vary the Evaluators** → "does the new rubric judge this version differently?"
- **Hold both, vary the Agent Version** → **the regression diff**, the daily workflow

## Comparing more than two versions

The common pattern is a two-version comparison, but the underlying primitive supports more:

- **A vs B vs C** — the same Scenarios, three versions, three runs. Useful for evaluating prompt-A vs prompt-B vs prompt-C in parallel; reading each run's per-scenario results localizes where each version excels or fails.
- **A baseline + N candidates** — useful when iterating on a candidate replacement; the baseline run stays pinned, candidates rotate.
- **A vs A across time** — re-running the same Evaluation on the same Agent Version weeks apart. Surfaces non-determinism in the Evaluator (a calibration smell) and any drift in the agent's runtime behavior between the two runs.

All three reduce to the same primitive: Evaluation runs that held the Scenarios and Evaluators constant, read against each other.

## Working with Agent Versions

You do everything around Agent Versions from the app, usually by asking the Trust Agent:

- **See what's connected** — ask the Trust Agent which agent builds are connected in the Project; the manual view is **Project Settings → Connection**, where each connection card names its **Current agent version**.
- **Connect a new platform** — ask the Trust Agent to connect a Claude Managed Agent or a Salesforce Agentforce agent, or add any of the four platforms yourself from **Connection → Add connection**.
- **Backfill past sessions** — click **Sync now** in the Sessions page header and pick the connected agent. AgentCore only; every other platform writes its sessions as they happen.
- **Pin one at run time** — pick the build in the launcher's **Agent** step, or tell the Trust Agent which build to evaluate.
- **Check what a session ran on** — open the session's **Details** tab for its Model or Agent row.
- **See what a build can do** — open its [Agent Profile](/concepts/agent-profile) from the connection card's current-version row. Not available for an AgentCore build.

If you need the underlying endpoints — including registering a build for a platform without a connector — the [API Reference](/api-reference) is the authoritative source.
