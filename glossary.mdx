The vocabulary of TrustAI. Each entry is short on purpose: it fixes the term and points at the page that owns it. Where a term names something with its own row in the project sidebar — **Requirements**, **Scenarios**, **Sessions**, **Evaluators**, **Evaluations**, **Playground** — the card carries the icon you'll click on in product; the rest are chosen for reading, not for matching the app.

## Core entities

<CardGroup cols={2}>
  <Card title="Project" icon="sliders-horizontal" href="/concepts/projects">
    The top-level container for one body of evaluation work: its members, the agents it tests, and every Requirement, Session, Scenario, Evaluator, Evaluation, and Agent Version under it. Its settings strip reads **General · Connections · Members**, and the agents live on the [Connections tab](#connections) — four platforms connect today: AWS Bedrock AgentCore, Salesforce Agentforce, Claude Managed Agent, and the Conversational HTTP agent.
  </Card>
  <Card title="Session" icon="database" href="/concepts/sessions">
    One conversation between a user and an agent — a sequence of Turns and Tool Calls, and a first-class evaluation target in its own right. Each carries a readable id that reflects where it came from: `RUN-` for a conversation TrustAI generated, `SES-` for one synced or imported from elsewhere. Both forms resolve to the same record, so an older link or transcript may quote the other prefix.
  </Card>
  <Card title="Annotation" icon="tag" href="/concepts/annotations">
    A human-authored signal recorded on a Session through typed annotation columns. Every project starts with three — **Verdict** (pass/fail), **Severity** (minor / major / blocker), and **Reviewer note** — and you can add your own. On the Verdict column your judgment is the ground truth that grades your automated judges through [evaluator accuracy](#running-and-scoring-evaluations); it never overrides the automated verdict.
  </Card>
  <Card title="Requirement" icon="clipboard-list" href="/concepts/requirements">
    Something your agent must do, or must never do, written in the language your business already uses and carrying a handle like `REQ-7`. Its **health** rolls up to one of **Passing**, **Failing**, **Partially covered**, **Uncovered**, or **Not yet run** — and it is the gate the authoring workflow starts from, since the Trust Agent refuses to generate scenarios until at least one requirement is saved.
  </Card>
  <Card title="Scenario" icon="flask-conical" href="/concepts/scenarios">
    A first-class test case — name, goal, personas, expected output, and linked sessions — with a stable id like `SCN-000022`. Every project keeps one flat **Scenarios** list; curate scenarios from real Sessions, save them from the Playground, or adopt the [recommended security scenarios](#recommended-scenarios-and-evaluators). `/v1/scenarios` is the whole API surface — a scenario belongs directly to its project, with no container above it.
  </Card>
  <Card title="Evaluator" icon="ruler" href="/concepts/evaluators">
    A reusable judgment function that measures a conversation against your criteria. Two kinds are creatable today: an **LLM judge** (a no-code rubric of "Passes when… / Fails when…" rules) and a **[Groundedness judge](#judging-against-source-material)**. Kind names are sentence case throughout.
  </Card>
  <Card title="Structured match" icon="check-square" href="/concepts/evaluators">
    The deterministic **Routing match** / **Tool match** kind. **You no longer create one** — structural expectations are authored on a scenario's [Expected Output](#scenarios-and-simulation) instead, where they belong to the test case being graded. Evaluators created before the change keep working, stay editable, and keep scoring.
  </Card>
  <Card title="Evaluation" icon="chart-line" href="/concepts/evaluations">
    A single run of one or more Evaluators, scoped to a specific Agent Version and launched from the [Evaluation Launcher](#running-and-scoring-evaluations) — against the scenarios you selected (simulated live) or against already-captured Sessions (each session's user message replayed to the connected agent, and the new answer graded). Grading a stored transcript exactly as recorded is the single-session [quick evaluation](#running-and-scoring-evaluations) instead. The output is a scored, reviewable result per persona per scenario, or per session.
  </Card>
  <Card title="Agent Version" icon="git-branch" href="/concepts/agent-versions">
    A named pin identifying one build of the agent **under test** — a label plus whatever connector metadata the platform supplied. The pin is by *reference*, not a frozen copy: rename a version and past runs pinned to it display the new label. It stores no prompt, model, tool schema or retrieval configuration; what a build can actually do lives in its [Agent Profile](/concepts/agent-profile). Comparing two Agent Versions on the same scenarios under the same Evaluators is the core regression-testing loop. Not to be confused with the [Trust Agent](#the-trust-agent), which is your assistant inside TrustAI.
  </Card>
  <Card title="Agent Profile" icon="id-card" href="/concepts/agent-profile">
    A versioned, human-reviewable record of what one Agent Version could actually do — its identity, the tools it exposes, and the knowledge sources it draws on, captured at a moment in time. A profile *describes* a version; it is never itself a version. Its versioned unit is the **profile revision**, and review is per-revision.
  </Card>
</CardGroup>

## Session internals

<CardGroup cols={2}>
  <Card title="Turn" icon="corner-down-right">
    One message exchange inside a Session — the user message and the agent's response. The smallest unit an Evaluator can score.
  </Card>
  <Card title="Tool Call" icon="terminal">
    An invocation of an agent tool inside a Turn — function name, arguments, and the returned value. A scenario's **Expected actions** assert on these.
  </Card>
  <Card title="Source" icon="signpost" href="/concepts/sessions">
    Where a session came from — exactly one of **Scenario**, **Playground**, or **External**. It renders as a chip wherever the value is shown: the session's **Details** tab always, and the Sessions list's **Source** column once you turn it on from **Add column** → **Hidden columns**. Scenario-born sessions add a **Simulated from** provenance card.
  </Card>
  <Card title="Picture" icon="image" href="/concepts/playground">
    An image carried by a message, attached from the composer's **Attach images** control and rendered in the transcript bubble, where a click opens it full-window. Accepted formats are **PNG**, **JPEG**, **WebP**, or **GIF** — and while the agent under test receives the actual image, a simulated user decides from your written description alone and an LLM judge cannot see it.
  </Card>
  <Card title="Ending reason" icon="flag" href="/concepts/sessions">
    The one sentence that closes a simulated conversation, always led by **"This conversation ended because "** — the customer got what they needed, the agent could not help with it, the customer gave up, the agent ended or transferred it, or it reached the length limit before finishing — falling back to *the customer chose to stop* where the reason isn't one this build recognises. A conversation with no recorded ending shows no line at all.
  </Card>
</CardGroup>

## The Trust Agent

The in-app assistant that does evaluation work alongside you. Everything in this section is the **Trust Agent** — your assistant inside TrustAI. It is *not* an [Agent Version](#core-entities), which is the customer's agent under test. The two share the word "agent" and nothing else.

<Note>
  **Trust Agent vs Agent Version.** The **Trust Agent** is the assistant that operates *on* your project — it finds Sessions, builds scenarios, and runs Evaluations for you. An **[Agent Version](/concepts/agent-versions)** is the agent *under test* — a pinned snapshot every Evaluation is scoped to. The Trust Agent helps you evaluate Agent Versions; it is never itself "a version."
</Note>

<CardGroup cols={2}>
  <Card title="Trust Agent" icon="sparkles" href="/concepts/trust-agent">
    The in-app AI assistant that helps you do evaluation work. It lives at `/projects/:id/agent`, streams its reasoning and replies in the open, surfaces real records you can click into, and asks before it writes. Available by default on every project, with no feature flag required.
  </Card>
  <Card title="Ask, Plan, Act" icon="messages-square" href="/concepts/trust-agent">
    The three modes on the composer's toggle. **Ask** clarifies real ambiguity first, then asks before each write. **Plan** researches and proposes a task list to confirm — it performs no writes at all. **Act** plans and executes end to end, and still does **not** skip approvals: every mutating write stops for you unless a standing approval covers it. Two other things share the word — MCP [act mode](#integrations), which is a property of a connected client's token, and the Playground's separate **Chat / Simulate** toggle.
  </Card>
  <Card title="Model" icon="cpu" href="/concepts/trust-agent">
    The language model a chat turn runs on, picked on the new-chat launcher or in the composer and remembered from the last turn that ran. You pick from the models your workspace offers — a deployment decision, not a fixed list.
  </Card>
  <Card title="Thinking depth" icon="brain" href="/concepts/trust-agent">
    How hard the Trust Agent works a problem before answering, set per message on the composer's **Thinking** chip: **Standard**, **Brief**, **Balanced** (the default), or **Thorough**. Only the depths the chosen model declares are offered, the chip hides for a model with one, and each model's depths are its own scale rather than a ranking across vendors.
  </Card>
  <Card title="Stop" icon="square" href="/concepts/trust-agent">
    Ends a turn you no longer want. It appears only while a turn is genuinely running, halts the reply immediately, and stores the partial turn rather than leaving it looking finished — the transcript then reads **"This reply was interrupted."** with a **Continue** action, the same note a dropped connection gets.
  </Card>
  <Card title="Shell" icon="layout-panel-left" href="/concepts/trust-agent">
    One of the three forms the Trust Agent takes from a single instance — **full page**, **docked panel**, or **collapsed pill** — with your conversation state preserved as you switch between them. When a project has no active agent task, the Trust Agent resolves to the minimized pill.
  </Card>
  <Card title="Streaming transcript" icon="text-cursor" href="/concepts/trust-agent">
    The running record of a Trust Agent conversation. Markdown-formatted turns stream token by token with a typing indicator and an accent caret, alongside a collapsible reasoning rail, tool-call cards, and a history-compaction marker. Transcripts are persisted, so reopening a chat shows its real prior history.
  </Card>
  <Card title="Side rail" icon="panel-right-open" href="/concepts/trust-agent">
    The Trust Agent's contextual panel, in four sections: **Progress** (the live plan and step counts), **Context** (referenced entities, led by a **Connected agent** card and its **Not checked / Healthy / Degraded / Unreachable** health chip), **Outputs** (per-entity rows of what the agent created, updated, or ran), and **Attachments** (files on the task). Each section hides itself when it has nothing to show.
  </Card>
  <Card title="HITL approval" icon="hand" href="/how-to/approve-agent-writes">
    A human-in-the-loop decision the agent surfaces as a card that replaces the composer and **halts the run** until you answer. **Permission cards** gate writes; **single-** and **multi-question cards** gather clarification. One batch of changes is approved at a single, all-or-nothing card, and the resolved decision is recorded in the transcript as an audit trail.
  </Card>
  <Card title="Standing approval" icon="shield-check" href="/how-to/approve-agent-writes">
    The durable, chat-wide version of a write approval, granted from a card's for-this-chat option. From then on the same **kind** of write commits with no card at all, and a chip in the composer shows the grant while it is live — its **turn off** control takes it back. Four things it can never cover: deleting items, saving an agent profile, bulk edits or deletions to requirements you already filed, and starting an unattended full run — a capability your workspace may not have.
  </Card>
  <Card title="Write preview" icon="file-diff" href="/concepts/trust-agent">
    The rich preview on a permission card that shows a proposed write before you approve it — the **diff**, the **dependencies**, and the **proposed end state** — not a bare ID you'd have to trust blindly. Pairs with the [Approve an agent write](/how-to/approve-agent-writes) guide.
  </Card>
  <Card title="Skill" icon="puzzle" href="/how-to/manage-trust-agent-skills">
    A reusable recipe the Trust Agent can invoke — for example, drafting an LLM judge rubric or summarizing Sessions that match a filter. **Built-in skills** ship with the product and are read-only; **workspace skills** are the ones your team writes. Both are workspace-scoped, both back the composer's **/** palette, and a transcript receipt reads **Reviewed *&lt;skill name&gt;*** beside a **Core skill** or **Workspace skill** chip.
  </Card>
  <Card title="Task" icon="list-checks" href="/concepts/trust-agent">
    A unit of work the Trust Agent plans and executes by composing Skills — how the assistant gets things done without you leaving the product. Each conversation is backed by a task, and recent chats live on the project's canonical task list.
  </Card>
</CardGroup>

## Scenarios and simulation

A **scenario** — one goal-driven test case — is defined under [Core entities](#core-entities). The supporting terms live here.

<CardGroup cols={2}>
  <Card title="Persona" icon="circle-user-round" href="/concepts/scenarios">
    A reusable synthetic-user profile that role-plays the user side of a scenario or simulation. Personas are managed in a **Manage personas** modal; at most one persona per project can be the default. In an evaluation, every persona attached to a scenario is scored on its own.
  </Card>
  <Card title="Goal" icon="target" href="/concepts/scenarios">
    The objective the simulated customer is trying to accomplish. A non-empty goal is what makes a scenario simulatable: personas shape who the simulated customer is, but a goal-only scenario still simulates when you run it.
  </Card>
  <Card title="Expected Output" icon="clipboard-check" href="/concepts/scenarios">
    A scenario's grading contract for what the agent should *do*, edited on the **Expected Output** tab of its fly-in, in three sections: **Expected behavior** (the judges that score it), **Expected actions** (tool calls the agent must or must not make), and **Expected routes** (where the conversation should land). Actions and routes are **required** or **disallowed** — there is no third state. It is a different contract from a plan's [Expected end state](#test-data), which is about data.
  </Card>
  <Card title="Reference material" icon="book-open" href="/how-to/check-answers-against-source-material">
    The source documents a [Groundedness judge](#judging-against-source-material) grades answers against — a policy, an article, the knowledge the agent is meant to stay inside. It attaches **per scenario**, nested under Expected behavior, and appears only once a judge that needs it is attached. A scenario bound to a Groundedness judge with no material attached will not run.
  </Card>
  <Card title="Playground" icon="play" href="/concepts/playground">
    A per-project surface for chatting with and simulating against a connected agent. An agent picker and a **Chat / Simulate** mode toggle: **Chat** is live manual conversation; **Simulate** auto-drives a customer-to-agent conversation from one persona and one goal. **Save as a scenario** turns a conversation you like into a project Scenario, with the conversation attached as its first Session.
  </Card>
  <Card title="Simulation" icon="messages-square" href="/concepts/playground">
    An automated customer-to-agent conversation. The same primitive powers the Playground's **Simulate** mode and every scenario-sourced evaluation — running scenarios always simulates a fresh conversation per scenario. The captured transcript is saved as a real scenario-linked Session.
  </Card>
</CardGroup>

## Recommended scenarios and evaluators

<CardGroup cols={2}>
  <Card title="Recommended scenarios" icon="library" href="/concepts/trust-library">
    The starter catalog of 10 adversarial security probes — one per [OWASP Agentic Top 10 (2026)](#recommended-scenarios-and-evaluators) category — so a new project never begins from a blank slate. Adopt them from **Add recommended scenarios**; each lands as an ordinary, fully editable scenario. None arrives with expected actions, test data, or reference material, so plan to give it your own before you read its verdicts as coverage.
  </Card>
  <Card title="Recommended evaluators" icon="list-plus" href="/concepts/evaluators">
    The matching starter catalog of checks: **11 presets — five Quality and six Safety**, all LLM judges, adopted from **Add recommended** in the Evaluators header — or the **Add recommended evaluators** hero on an empty project — under a CTA that counts what you selected. Two of them are authored on a 1–5 shape with a pass cutoff of 3, but the judge is asked for pass or fail, so do not expect a graded 1–5 score on a result.
  </Card>
  <Card title="OWASP Agentic Top 10" icon="shield-alert" href="/concepts/trust-library">
    The industry list of agent failure modes the starter security scenarios map to, one scenario per category — shown throughout the product by its friendly name (**Goal hijack**, **Tool misuse**, **Identity & privilege**, and so on), never by a framework code. Those friendly names are ours, not the standard's own titles, and a mapping is a pointer rather than a claim of coverage.
  </Card>
  <Card title="Provenance chip" icon="stamp" href="/concepts/evaluators">
    The small label on a recommended or adopted check saying where it came from — always a plain category such as **Answer quality**, **Factual accuracy**, **Task success**, **Safety & security**, **Stays in bounds**, or **Fairness**, with the framework and citation kept in the tooltip. An adopted evaluator also carries a **Recommended** chip; an adopted scenario carries no chip at all.
  </Card>
  <Card title="Tailoring" icon="scissors" href="/how-to/adopt-recommended-security-scenarios">
    The optional pass that rewrites adopted security scenarios against the agent you actually connected — keeping checks that already grade well, tailoring judges to your agent's own rules, and pinning hard disallowed-action contracts. Start it with **Add & tailor to your agent**; adoption completes immediately and tailoring finishes in the background, so it never blocks you. With no agent connected the primary action disables under **Connect an agent to tailor these**, and **Add without tailoring** still works.
  </Card>
  <Card title="Tailor first" icon="pin" href="/concepts/evaluators">
    The nudge badge on the three recommended evaluators whose criteria defer to rules only you can state — **Accomplished the goal**, **Stays within scope**, and **No unauthorized commitments**. It is advice about writing your rules down first, never a block on adopting them.
  </Card>
  <Card title="Internally consistent" icon="check" href="/concepts/evaluators">
    The Quality preset that checks a reply against the conversation it sits in, flagging answers that contradict what was already said. It was renamed from "Does not hallucinate", which promised a check on the world that a transcript alone cannot deliver — a project that adopted the preset earlier still holds its copy under the old name.
  </Card>
</CardGroup>

## Judging against source material

<CardGroup cols={2}>
  <Card title="Groundedness judge" icon="file-check" href="/concepts/evaluators">
    The evaluator kind that checks every factual claim in a reply against the scenario's [Reference material](#scenarios-and-simulation), catching hallucinated and contradicted answers with quoted evidence. It never penalises leaving something out, and it never judges tone or style — use an LLM judge for those. Its metric chip reads **N% grounded**.
  </Card>
  <Card title="Groundedness report" icon="search" href="/how-to/check-answers-against-source-material">
    What a Groundedness check returns: every claim the reply made, the plain-language reasoning behind each verdict, and the verified source quote. Claim verdicts read **Supported**, **Contradicted**, **Unsupported**, **Unknown**, or **Conversational**, and a reviewer can override one with a note — the one place a human judgment changes an automated result.
  </Card>
  <Card title="Needs review" icon="triangle-alert" href="/concepts/evaluators">
    The amber third verdict on a single check, used when the grade can't be trusted as-is rather than guessing — an unverifiable claim, a truncated response. It is recorded and shown, and it is **excluded from pass/fail gating**: it can never quietly become a pass or read as a red fail.
  </Card>
</CardGroup>

## Running and scoring evaluations

<CardGroup cols={2}>
  <Card title="Evaluation Launcher" icon="rocket" href="/concepts/evaluations">
    The one modal every evaluation starts from, wherever you begin it — the Sessions list, a session's fly-in, the Scenarios list, a scenario's fly-in, an evaluator's panel, or **New evaluation** on the Evaluations page. It shows a fan-out preview of exactly what will run before you launch, and nothing is enqueued until you confirm inside it. **Re-run** on a finished run restores its full configuration.
  </Card>
  <Card title="Quick evaluation" icon="zap" href="/concepts/evaluations">
    Grading one conversation in place from its own fly-in: it says it started, counts the checks as they score, and finishes with a **View** action. It lands on the Evaluations page as a row with a muted **Quick** pill that opens the conversation it graded, and since it mints no run record there is nothing to cancel or delete.
  </Card>
  <Card title="Evaluator accuracy" icon="gauge" href="/concepts/evaluations">
    How often your automated judges agreed with a person's session-level **Verdict** annotation. Run detail leads with two numbers: **Pass rate** grades the agent; evaluator accuracy grades the judges. It covers LLM judges against human labels and excludes structural checks.
  </Card>
  <Card title="Repeat each test case" icon="repeat" href="/concepts/evaluations">
    The launcher control that runs every test case more than once — **1**, **2**, **3**, or **4** — to measure how reliably the agent passes rather than whether it passed once. Repeats read as **Trial 1**, **Trial 2**, and so on under their scenario, and **Trial N of K** in the result fly-in's switcher.
  </Card>
  <Card title="Pass^K" icon="refresh-cw" href="/concepts/evaluations">
    The reliability headline on a run whose cases were repeated: the share of cases the agent passed on **every** repeat, so an agent that passes once and fails on retry can't hide behind a lucky attempt. It replaces the plain pass-rate headline on a repeated run.
  </Card>
  <Card title="End state" icon="milestone" href="/concepts/test-data">
    What a run actually left behind in the connected system, read back and graded. It is a run-detail column and a tab in the result fly-in, and it appears only where a result was really graded on it — which is why a run with no [test data plan](#test-data) shows neither.
  </Card>
  <Card title="Calibration" icon="scale" href="/how-to/calibrate-an-evaluator">
    A check of an LLM judge against scenarios you already marked pass or fail, run from the evaluator's **Calibrate** tab. It uses the exact judge that runs in production, reports a plain-language agreement headline with disagreements listed first, and keeps a history so you can see whether rubric edits helped. The tab is offered for LLM judges and withheld everywhere else.
  </Card>
  <Card title="Run comparison" icon="git-compare" href="/api-reference">
    Asking whether one run beat another and being told plainly — **Better**, **Worse**, **Too close to call**, or a refusal reading **"We can't compare these fairly."** when the rules moved between the two. It is an API capability today with no screen in the product, and its shape is provisional.
  </Card>
</CardGroup>

## Reliability and excluded outcomes

<CardGroup cols={2}>
  <Card title="Couldn't test" icon="circle-slash" href="/concepts/evaluations">
    The amber outcome on a conversation whose own agent action returned an error before the behaviour under test could run. It leaves the pass rate's denominator rather than quietly passing — and unlike an environment problem, it is never excused as somebody else's fault.
  </Card>
  <Card title="Excluded outcome" icon="filter-x" href="/concepts/evaluations">
    Any of the five results that leave a run's pass-rate denominator because grading them would be meaningless: a guardrail block, an environment problem, a harness misconfiguration, blocked access, or the agent's own action failing. Exclusion says the score cannot count the conversation; only the first four also say the fault was the environment's.
  </Card>
  <Card title="Not scored" icon="circle-dashed" href="/concepts/evaluations">
    The neutral read on a conversation the run could not put a behavioural score against — on an agent-side failure the one-line summary is **"Not scored because an action the agent runs returned an error."** It is not interchangeable with [Not graded](#ui-patterns), which belongs to the verdict pill.
  </Card>
  <Card title="Unverified" icon="eye-off" href="/concepts/evaluations">
    The third and last term in the reliability vocabulary: a result whose evidence did not arrive in a form the run could stand behind. Like **Couldn't test** and **Not scored**, it is counted and shown rather than rounded into a pass or a fail — nothing else may be coined on these screens.
  </Card>
</CardGroup>

## Test data

<CardGroup cols={2}>
  <Card title="Test data plan" icon="file-text" href="/concepts/test-data">
    One reviewable document describing everything a scenario does to data on every run: what gets created, what gets read back, what the end state should be, and what gets cleaned up. It renders as five step cards — **"Create what this test needs"**, **"Run the conversation"**, **"Read back what the agent created"**, **"Check what should happen"**, and **"Clean up everything this test created"**.
  </Card>
  <Card title="Test data store" icon="server" href="/how-to/manage-project-connections">
    The connected system a plan's records actually live in. Stores hang off an agent connection under **Customize environment** — a Salesforce connection arrives with one named **This agent's Salesforce org**, and every other platform starts with none — and the launcher's **Environment** step confirms the one a run will use before anything starts.
  </Card>
  <Card title="Expected end state" icon="check-check" href="/how-to/author-test-data-for-a-scenario">
    What the records should look like once the agent has finished — the data half of a test's contract, checked in the plan's **"Check what should happen"** step, where a value can allow a tolerance so close-enough still passes. It is a different contract from a scenario's [Expected Output](#scenarios-and-simulation), which is about behaviour.
  </Card>
  <Card title="Run report" icon="receipt" href="/concepts/test-data">
    The per-run record of what actually happened to a scenario's test data — setup, read-back, structural results, and cleanup. Its heading is **"What TrustAI did"**, and it links back to the plan the run followed, so a failed comparison can be traced to the data it ran against.
  </Card>
  <Card title="Cleanup" icon="trash-2" href="/concepts/test-data">
    What a run removes when it finishes. The Connections surface states it as **"Removes only the records each test created."**; the plan's own card is more exact — **"Removes the records this test created and tagged for the run — seeded records included."** Cleanup runs on every run and no surface offers to turn it off.
  </Card>
</CardGroup>

## Connections

<CardGroup cols={2}>
  <Card title="Connections tab" icon="plug" href="/how-to/manage-project-connections">
    The one place a project's agents live — the middle tab of **General · Connections · Members** in project settings, where each agent is a card and the action is **Connect an agent**. A card answers two different questions in two vocabularies: whether setup is finished (**Connected / Setting up / Needs admin / Setup failed**) and whether TrustAI can reach it right now (**Connected / Partly reachable / Can’t reach it / Not checked yet**).
  </Card>
  <Card title="Customize environment" icon="settings-2" href="/how-to/manage-project-connections">
    The expander that extends a connection card downward in place, holding that connection's [test data stores](#test-data), its reset behaviour as a plain sentence, how many tests may run at once, and its optional test users.
  </Card>
  <Card title="Test user" icon="user-check" href="/how-to/manage-project-connections">
    The Salesforce user a test signs in as, so a scenario can run as someone with less access than the connection itself. On a connection card the section reads **Run tests as different users (permission sets)**, and inside it each row is **Test user *N***, added with **Add test user** and committed with **Save test users**. The field labels **Default test user** and **Additional test users (permission sets)** belong to the connection *edit* form — see [Projects](/concepts/projects#connecting-an-agent) for which sign-in details appear there.
  </Card>
  <Card title="Connected orgs" icon="cloud" href="/how-to/administer-workspace-access">
    The workspace-level inventory of the Salesforce organizations your workspace has authorized — the fifth of the six workspace admin tabs. It is deliberately not called "Connections": that name belongs to the project tab listing the agents one project tests. The two cross-link.
  </Card>
</CardGroup>

## Access and tenancy

<CardGroup cols={2}>
  <Card title="Organization (tenant)" icon="building-2" href="/concepts/multi-tenancy">
    The top-level account boundary every Project belongs to. A single fail-closed authorization engine decides who can see and act on every record, scoped to the current organization, and every access decision is written to a durable, append-only audit trail. The sidebar footer shows your workspace name and role — **Workspace · Role**.
  </Card>
  <Card title="Project role" icon="users" href="/concepts/multi-tenancy">
    What someone may do on one project: **Viewer**, **Editor**, or **Admin**, all three grantable — Editors own the whole authoring loop including deletes, and Admins add project administration on top. Workspace roles (**Owner / Admin / Member / Guest**) are a separate ladder, and a workspace Guest cannot create a project.
  </Card>
  <Card title="Transfer ownership" icon="arrow-right-left" href="/how-to/administer-workspace-access">
    How a project's **Owner** seat moves. Ownership is conferred at creation and is the one tier you cannot grant — it changes hands only through this explicit action, after which the outgoing owner steps down to Admin.
  </Card>
</CardGroup>

## UI patterns

<CardGroup cols={2}>
  <Card title="Saved View" icon="bookmark" href="/concepts/saved-views">
    A named, persisted combination of filters, sort order, and column configuration for a list surface. **Every saved view belongs to the project, not to you**: anyone on the project sees all of them, and anyone who can edit project content can rename, reconfigure, or delete the ones your team saved. The built-in starting points are read-only, and the only per-person part is which view opens by default for you.
  </Card>
  <Card title="Fly-in panel" icon="panel-right" href="/concepts/tables-and-panels">
    A slide-out detail panel that opens from the right when you click a record in Sessions, Scenarios, Evaluators, or Evaluations. Shows the full transcript, metadata, and contextual actions without leaving the list. On Scenarios it stacks two levels: the scenario panel, with a nested session-detail panel over it. **J**/**K** step between records; **Esc** closes the top panel first.
  </Card>
  <Card title="Verdict pill" icon="badge-check" href="/concepts/tables-and-panels">
    The badge on results and sessions, never blank: a green **pass** leg, a red **fail** leg, and a neutral leg carrying **Not evaluated** (nothing ran) or **Not graded** (something ran but produced no behavioural score) — which a run header can refine into **Run only — nothing was graded** or **Not graded — no evaluators**. Neither is the reliability lexicon's [Not scored](#reliability-and-excluded-outcomes), and an agent-side failure reads amber as **Couldn't test** rather than neutral.
  </Card>
  <Card title="Results matrix" icon="grid-3x3" href="/concepts/evaluations">
    The grid on a run's detail page. Two pinned columns lead and cannot be hidden — **Transcript** and **Final verdict** — followed by [End state](#running-and-scoring-evaluations) where the run graded on it, then one column per evaluator, then any structural checks, with **Duration** closing the set. Results default to a **By scenario** grouping that expands to each repeat; **Flat** lists every result on its own row.
  </Card>
</CardGroup>

## Integrations

<CardGroup cols={2}>
  <Card title="MCP server" icon="cable" href="/concepts/mcp-integration">
    TrustAI speaks the Model Context Protocol, so an agent in your own client can author requirements, personas, scenarios and judges, launch an evaluation and adjudicate the result without opening the product. The surface is six coarse tools — `trustai_project`, `trustai_requirements`, `trustai_evaluators`, `trustai_scenarios`, `trustai_runs`, and `trustai_adjudicate` — each taking an operation name plus that operation's arguments.
  </Card>
  <Card title="MCP consent" icon="key" href="/how-to/connect-mcp-client">
    The single screen you approve when an outside client connects: it names the app, the account and the workspace, and offers exactly three answers — **Read only**, **Read and write**, or **Read and write, act mode**. Sign-in is your workspace's SSO identity provider, and the token it issues is revocable. There is no in-app screen for managing tokens yet, and parity with the REST authoring surface is deliberately incomplete.
  </Card>
  <Card title="Act mode (MCP)" icon="lock" href="/how-to/connect-mcp-client">
    The widest consent answer: the connected client makes changes without being asked each time, and every change is still recorded. Only a person can grant it, at the consent screen — a client can ask for read and write, but can never demand act mode or escalate itself into it. It is not the Trust Agent's [Act mode](#the-trust-agent), and neither is a [standing approval](#the-trust-agent).
  </Card>
</CardGroup>
